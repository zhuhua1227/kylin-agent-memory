# 知识冲突处理模块 —— 说明报告

> 对应评分：技术创新性 30 分的三个点名子项之一 + 性能指标「知识冲突处理正确率 ≥88%」
> 设计依据：`知识冲突处理-设计方案.md`（v2，2026-08-16 接口勘探后修订）
> 代码位置：`知识检索/mine_conflicts.py`（挖掘+判定+裁决+回溯）、`知识检索/review_and_freeze_conflicts.py`（评测集冻结）、`可复现性体系/measure_conflicts.py`（M-301~M-305）

## 〇、一句话结论

**不做"新的覆盖旧的"，做"给旧知识标注适用边界，检索默认返回新的、但旧的仍可追溯"。**

本模块从本项目自身的 `memory/*.md` 真实修订历史里挖出了 29 条结构候选（v1.3.0，`_find_origin()` 起源查找修复后的数字；修复前"先 Read 再 Edit"的修订被系统性误判为同会话，只挖出 19 条），其中 1 条（K-0052）经盲测规范裁定纳入冻结评测集，冻结成 36 对（19 正 + 17 负）评测集；规则裁决器在"谁生效"这个核心判断上 19/19=100%。判定准确率分三个口径报（详见 §5.2）：**开发集** n=36，35/36 = 97.2%，Wilson 95% CI 下界 85.8%；**留出集** n=60，56/60 = 93.3%，下界 84.1%（规则于该批数据产生之前即已冻结、从未见过）；**合并** n=96，91/96 = 94.8%，下界 **88.4% ≥ 赛题 88% 门槛、达标**。合并口径达标来自样本量由 36 增至 96、不是泛化优于开发集——点估计 94.8% 落在开发集 97.2% 与留出集 93.3% 之间，留出集单独下界仍未过门槛，两句必须并读。挖掘过程中两次真实的方法修正（长驻会话跨天恢复导致的误杀、案例签名过粗导致的假阳性聚类）+ 一次起源查找 bug 修复（同会话 Read 误当起源）本身就是本模块最有说服力的部分，比最终数字更能说明这套判定机制是认真验证过的，不是拍脑袋定的规则。

## 一、⚠️ 自指声明（先说清楚数据从哪来）

本模块挖掘冲突对的主矿脉是 `多源数据整合/dataset/memory_source_records.jsonl` 里对 `memory/*.md` 文件的 Read/Write/Edit 工具调用记录。**这批 `memory/*.md` 是本项目自己的记忆系统文件**——是 Claude Code 在本项目历次会话里为了记住项目状态而写下的笔记，跨天被反复修订。

需要说清楚的两条边界：

1. **知识单元是真实的、修订是真实发生的，只是它们恰好是本项目的工作记录。** 不是构造的实验数据，也不是从别处借来的测试语料——是本项目 41 天真实开发过程中自然沉淀下来的知识版本演化史。这个矿脉与赛题要解决的问题（新旧知识冲突）同构：都是"同一件事，先这么记，后来改了主意/发现变了"。
2. **环境边界**：老数据来自 Windows 环境的真实工作（本项目在 Windows 笔记本上用 Claude Code 开发），新的 Kylin 目标机数据（VM102@100.50）目前跨度太短、冲突尚未长出（`每日锚点15条.md` 描述的 A 组锚点需要多天重复执行才会积累出可比较的版本历史）。本报告的全部实测数字来自 Windows 环境数据。

## 二、数据挖掘：两轮真实的方法修正

### 2.1 输入与分层（设计方案 §0.2）

冲突来源分两层，不在同一处代码路径：

| 层 | 内容 | 冲突类型 | 数据位置 |
|---|---|---|---|
| **dataset 层** | `tool_execution` 原始记录（Read/Write/Edit） | T1 事实过期、T3 环境失效、T4 局部修订 | `多源数据整合/dataset/memory_source_records.jsonl` |
| **知识单元层** | `cases.jsonl`（`mine_cases.py` 挖掘产出） | T2 方法推翻 | `知识检索/cases.jsonl`（本模块内部重新调用 `mine_cases.mine()` 现算，不读盘上的文件） |

`Edit` 工具调用的 `tool_input` 直接带 `old_string`/`new_string`——这是段落级 diff 的现成两端，不需要自己实现跨天全文 diff。内容字段随工具名不同：`Read` 在 `tool_output`（带行号前缀，需先剥掉）、`Write` 在 `tool_input["content"]`、`Edit` 在 `tool_input["old_string"]`/`["new_string"]`。

### 2.2 第一次真实修正：长驻会话跨天恢复被误判成"同一次调试"

最初的判据（照抄 `mine_cases.py` "同一次调试里的连续尝试不算冲突"的思路）是"新旧两侧 `session_id` 相同就不算冲突"。实测发现：本数据集里 **Claude Code 会话可以跨天恢复**（`--resume` 或长驻会话），最长一个会话 `session_id=1cd1ff9f` 横跨 **23 天**（2026-07-13 至 2026-08-13，`pttime-seedbox.md` 的大半修订史都发生在这一个会话里）。

按"同 session_id 即排除"的老判据，这类跨天但同会话的真实修订会被整体误杀。改成**"同会话 且 同一天"**（同一次"坐下来写"的操作时间窗）后：

```
doc_revision_candidates: 4 → 19（+375%）
```

同时也证明了一件事：`pttime-seedbox.md` 里"之前判断有误"这类自我修正（见 §三 T2 举例）之所以在老判据下被漏掉，不是因为数据里没有，而是判据本身用"会话身份"错误代理了"是不是同一次操作"这个真正想问的问题。

### 2.3 第二次真实修正：MEMORY.md 索引行插入被误判成冲突

最初的"纯追加"判据是`new_text.startswith(old_text)`（只挡"接着往后写"这一种模式）。实测发现 `MEMORY.md` 这类索引文件常见"在已有内容**前面**插入一条新记录"的写法——旧文本一个字没改，只是不再是文件开头。这类插入被误判成"内容被替换"，产出了假阳性候选（如把"- [N100 外部USB口报废](...)"这一整行原样保留、只是前面新插了一行"- [J盘希捷老盘濒死](...)"的编辑，误判成 J 盘这条覆盖了 USB 那条）。

改成"旧文本整体是新文本的子串"（覆盖前插/后插/中间插三种插入位置）后，这两条假阳性被正确剔除。

### 2.4 挖掘产出（`知识检索/conflicts.jsonl`，149 条记录，含全部正负证据）

```
doc_edit_total(memory/*.md 的 Edit 事件总数): 148
  ├─ rejected_by_append_only（纯追加，负例）:      91
  ├─ rejected_by_same_session（同一次坐下来写，负例）: 37
  ├─ skipped_unknown_origin（起源不明，不产出记录）:  1
  └─ doc_revision_candidates（结构候选，正例）:      19

case_total（mine_cases.mine() 现算的案例数）: 31
  case_signature_groups（按签名分组、组内≥2条）: 4
  rejected_by_low_text_overlap（签名分组假阳性，见2.5）: 5
  case_conflict_candidates: 0

user_reversal_signals（S4，用户输入含环境重置表述）: 2
```

⚠️ 149 条**不是**"149 条冲突"——`conflicts.jsonl` 刻意把结构层判定为"不是冲突"的记录（append_only/same_sitting）也带着完整原文一并写出，这是**有意的设计**：负例要拿去和正例一起构成评测集，必须有和正例同等完整的原文证据，不能只留一个计数器（见 `mine_conflicts.py` 里 `mine_doc_revisions()` 的文档字符串）。真正的结构候选（可能是冲突、交人工复核）只有 19 条。

### 2.5 一个未达设计预期、但诚实报告的空结果：S3 案例签名分组

设计方案原估算 S3（"细签名多解法"）能产出 5~8 组真冲突。实测按 `(tool_name, 归一化错误文本前60字)` 分组后确实分出了 4 组、5 对跨会话候选，但**逐对核查源头后全部是假阳性**：

```
SIG=('case', 'Bash', 'FATAL ERROR: Network error: Connection r')
  A: ssh 到 device_b（08-03）  B: plink 到某VPS:31879（08-09）
  → 两次毫不相关的连接失败，只是错误消息本身通用

SIG=('case', 'Bash', 'Command timed out after 2m 0s')
  三条：写 litellm 测试文件超时（07-31）/ docker kill 卡住超时（08-08）/
        跑 reproduce_L1.py 超时（08-13）
  → 三件完全不相关的长跑命令，共同点只是都是 exit code 143
```

根因与设计方案 §三预警的"exit code N 当签名会聚出无关问题"是同一类问题的更隐蔽版本：即便剥掉了退出码前缀，签名截断窗口仍然落在"Traceback (most recent call last): File "<string>", line 3, in <module>"这类**所有 Python 一行式报错共享的样板文本**里，没有任何区分度。

修法：追加一道**失败命令本身**的文本重叠度过滤（复用 `mine_cases.py` 的最长公共子串占比方法，阈值 0.3——4 组假阳性实测重叠度全部落在 0.04~0.20）。修复后 **S3 实测 0 条正例**，与设计方案估算的"5~8组"不符。这不是要调低阈值凑数的信号，是这批数据里 case 类知识本身还没有真实的"同一问题、不同修复"矿脉——`知识检索/cases.jsonl` 目前只有 31 条案例，规模尚不足以支撑这类信号显现。如实报告，不强行产出正例。

### 2.6 S4（用户推翻信号）：2 条低置信度信号，不直接产出裁决对

扫描 `user_input` 记录里的环境重置表述，命中 2 条（"我重装了一下系统"、"我换了个线"）。这类信号**不产出**"旧claim vs 新claim"配对——用户只说了一句话，没有指明具体哪条知识失效，只能标记"这个时间点之后需要人工复核批量失效范围"，`auto_confidence="low"`，不计入可裁决的候选池。

### 2.7 S1（命令输出漂移）：当前实测 0 条候选，及其原因（不是实现问题）

§2.1~2.6 的 S2/S3/S4 三条矿脉都不依赖任何自然语言措辞去猜"是不是环境变了"。补第四条矿脉 **S1（`mine_command_output_drift()`）**：不看措辞，直接比对"同一条命令跨天执行、输出是否变了"——这是 T1（事实过期）/T3（环境批量失效）唯一的客观读数来源。

判据四条（缺一不可）：`tool_name=="Bash"`、归一化后命令字符串完全相同、至少跨 2 个不同日期**且**至少跨 2 个不同 `session_id`、首末两次输出 `difflib` 相似度 < 0.70。

```
rejected_by_non_bash（非 Bash 工具调用，见下方"必须避的坑"）: 5498
（Bash 里出现≥2次的命令，按跨天/跨会话门槛过滤后）
  ├─ rejected_by_same_day（未跨够 2 个不同日期）:              44
  ├─ cmd_rejected_by_same_session（跨天但未跨够 2 个会话）:     8
  ├─ rejected_by_high_similarity（输出没有实质变化）:           0
  └─ cmd_drift_candidates（结构候选）:                         0
```

（`cmd_rejected_by_same_session` 加了 `cmd_` 前缀，与 §2.4 doc_revision 路径自己的 `rejected_by_same_session=37` 区分开——两条矿脉挡的是完全不同的东西，`mine_conflicts.mine()` 合并统计时不让重名 key 互相覆盖，见 `mine_conflicts.py` 里 `mine()` 的合并逻辑注释。）

**实测 0 条候选，原因是数据还没到，不是判据写错了**：这条矿脉的主要供给方是《每日锚点16条.md》——13 项固定读数每天在新会话里跑一遍，靠"跨天 + 跨会话 + 命令字符串一字不差"才能被认作"同一条命令"。当前数据集里还没有任何一条命令真正满足"同一条命令、跨 2 天、跨 2 个会话"这三条同时成立（上面 44+8=52 组多次执行的命令，全部倒在"跨天"或"跨会话"任一门槛上，说明它们是调试过程里的临时重试，不是锚点式的每日定期读数）——《每日锚点16条.md》要求的重复执行尚未开始积累。判据本身的正确性不依赖这批数据是否已经到齐：`可复现性体系/test_detectors.py` 的 `test_cmd_drift_negatives()` 用手造反例独立验证了五类假冲突被拦住、两类正例（环境探针翻转判 T3、普通读数变化判 T1）被正确放行，`可复现性体系/mutate.py` 的变异测试独立验证了这道拦截确实在真实代码路径上生效（不是"写了测试但代码没接上"）。

⚠️ 必须限定 `tool_name=="Bash"` 是这条矿脉最容易踩的坑：早期探针版本把 `tool_input.get("command") or tool_input.get("file_path")` 当作命令键，会把"Write 同一个文件"和"Read 同一个文件"误判成"同一条命令跑了两次"——旧输出是`File created successfully at: ...`，新输出是文件正文，相似度必然接近 0，产出的全是假阳性。上表 `rejected_by_non_bash=5498` 正是这道过滤在真实数据上拦住的非 Bash 工具调用总量。

## 三、冲突类型学（T1~T4，全部用真实案例）

| 类型 | 定义 | 本模块的真实例子 | 裁决规则 |
|---|---|---|---|
| **T1 事实过期** | 同一事实槽位，值变了 | J盘诊断"疑翻新盘维权"→"已物理拔除退役"（`seagate-j-drive-failing.md`，07-29→07-31） | 新值生效，旧值标注 `as_of` |
| **T2 方法推翻** | 同一问题，后者否定前者的解法 | "PTTime 是 ratioless、不用做种"→"先前的说法是错的（那是我07-13的错误结论，别再信）"（`jellyfin-baidu-media.md`，07-13→07-14） | 新法生效，旧法保留适用条件 |
| **T3 环境变更批量失效** | 环境标识变了，一批知识同时过期 | "做种盘已物理拔除...架构总览记录的是拔盘前状态"（`pttime-seedbox.md`，07-28→07-31） | 该环境下的知识批量标记待重验 |
| **T4 局部修订** | 同一知识文件某段被改写，不含强烈否定 | MEMORY.md 索引摘要随项目进展滚动更新 | 段落粒度，新的生效 |

T2 是设计方案点名的最高价值类型——"PTTime ratioless"这条正是 §一.1 引用的教科书案例：一条记录里同时含旧知识、推翻它的新事实、以及自我纠正的措辞（"别再信"），是本项目自己数据里长出来的、不是编的。

另一个值得记录的真实发现：**同一现实事件（做种盘拔除）在人工裁决时被标成了不同类型**——描述整体架构的记录（K-0024）标了 T3（环境前提消失），而描述磁盘诊断状态的记录（K-0025/K-0137）标了 T1（事实槽位的值变了）。这不是标注失误，是 T1/T3 在"事实因环境变化而更新"这类场景下的边界本身就是模糊的——同一个物理事件，从"这段架构描述还成不成立"的角度看是 T3，从"这块盘现在是什么状态"的角度看是 T1。§四.2 会说明这个模糊边界如何反映在裁决器的实测准确率里。

## 四、三层判定机制与裁决器实现

### 4.1 架构（设计方案 §三）

```
L1 结构层（mine_conflicts.mine()，确定性，可复现，被 mutate.py 变异测试保护）
   同签名 + 跨会话/跨天 + diff 非空  →  候选池（19 条正例 + 128 条负例）
        ↓
L2 语义层（本次由 Claude Code 通读候选池排序/解释，不产出 ground truth）
        ↓
L3 人工裁决（review_and_freeze_conflicts.py 的 ADJUDICATIONS，冻结成 ground truth）
```

`mine_conflicts.py` 提供四个可独立调用、可测试的函数：

- `mine(recs) -> (conflicts, stats)`：L1 结构层挖掘，见第二节
- `is_conflict(pair) -> bool`：判定器，"这对知识值得进入裁决"（对应"判定准确率"子指标）
- `adjudicate(pair) -> dict`：规则裁决器，"已确认冲突的一对，谁生效/什么类型/为什么"（对应"裁决正确率"子指标）
- `retrieve_old(stable_key) -> dict`：回溯，查不到必须报错（对应"回溯完整性"子指标）

### 4.2 ⚠️ 为什么裁决 ground truth 不能由 LLM/规则自己产出

设计方案 §三给出三条理由（可复现性铁律 / 生成"事实"不合法 / 会重蹈评测集 E-1 出题方绑架指标的覆辙），本模块严格照办：**`review_and_freeze_conflicts.py` 里的 36 对裁决不调用 `adjudicate()`**，是逐条通读 `conflicts.jsonl` 原始证据后手写的决定，与 `adjudicate()` 是完全独立的两条代码路径。

必须诚实披露的一点：`ADJUDICATIONS` 里的判断由 **Claude Code（本次会话）逐条通读原始证据后写出，用户没有逐条复核**。这与设计方案理想中的"人工裁决"有真实差距。但它与"L2 LLM 自动裁决"不是同一类风险：

- 不是被测系统本身——被测的是 `adjudicate()` 这段确定性规则代码，本次裁决不调用它；
- 每条判断都可回溯——`stable_key` 指向原始记录（见 §四.4 的回溯完整性实测），任何人都能重新核对；
- 判断依据写清楚了具体引用了原文哪句话，不是泛泛的"看起来像冲突"（完整理由见 `review_and_freeze_conflicts.py` 的 `ADJUDICATIONS`/`DEMOTED_TO_NOT_CONFLICT` 列表）。

这条披露本身就是"诚实边界"的一部分——不写清楚裁决者是谁，比裁决本身不完美更损害可信度。

### 4.3 一个被人工复核否决的结构候选：K-0067

19 条结构候选里，`music-sweep` 那条（把"每30分钟对全库跑一遍**organize+lyrics**"精简成"每30分钟对全库跑一遍"）结构上满足全部三条候选规则（同文件、非纯追加、跨会话跨天），但通读原文后两条内容实质相同——只是删掉了几个字，没有任何信息增删或立场变化。人工复核判定：不算冲突。

这条本身就是"信号只能提示值得看一眼、真正判断要看原文"这条方法论（`评测集/说明报告.md` 第 239-244 行，v1.1.0/v1.2.0 评测集 0.60 阈值扫出 16 对候选、逐一核查后发现多数是误判——同一方法论在本模块上第二次得到验证）的直接实证，是本模块交付的正面结果之一，不是缺陷。

### 5.2a 标注方法与可靠性（留出集单人全量盲测，2026-09-07）

留出集 60 对 + 开发集复核 13 对 + 5 条重复题（共 78 题）由项目负责人本人单人全量盲测标注，依据《冲突判定标注规范》v1.0.2、《留出集抽样与裁决-协议》v1.0（2026-09-03 冻结）。完整结果见 `知识检索/留出集裁决结果记录.md`，机器可读版 `知识检索/全量单人复核-裁决.json`（M-306 的输入）。

**这批标签为什么可信**：

| 证据 | 数值 |
|---|---|
| 重复题前后一致（intra-rater） | **5 / 5 = 100%**（C-323） |
| 逐条写了裁定理由 | **78 / 78** |

**重复题设计**：5 条题目在卷中出现两次、间距 29~70 题，标注者事先知道存在但不知道是哪几条。它测的是**同一人前后标准是否漂移**——这是单人标注唯一能自证的可靠性指标，不论往哪边偏，前后不一致都会暴露。

**为什么不用诱饵**：冻结集的正例与负例本轮标注者此前均已见过，诱饵会被认出而失效；且上一轮盲测实测发现**反向诱饵抓不住"全部判 not_conflict"这个方向**。重复题没有这个盲区。

**开发集复核**：那 13 条此前只有 Claude 裁决过（冻结标注全为 `conflict`），本轮人工盲测复核 **13/13 维持 `conflict`、改判 0**（C-324）。**→ 报告中"开发集由 AI 裁决、未经人工复核"这条已知限制可以撤下，改为"全部 36 对均经人工盲测复核"**；冻结集正例仍为 19 条，19 正 / 17 负比例不变。

```
提示词 B 组⑤ 要求笔记写「读数：<值>（原为 <旧值>，已不再是）」
挖掘器 append_only 用「旧文本 ⊂ 新文本」子串匹配
两者交互 → 双向失效
```

| 方向 | 条目 | 表现 |
|---|---|---|
| **史注漂移** | HO-K-0053 / HO-K-0036 | 当前值未变、只有史注变 → 误判为冲突（A 层，C-321） |

### 6.2 ⚠️ 诚实的适用范围声明：这套过滤机制在当前真实数据上是 no-op

supersedes/superseded_by 边表理论上对**任何**能算出 `stable_key` 的知识单元通用（case/workflow/template 皆可），但 `stable_key()` 目前只对 `case`/`doc_revision` 两种 `kind` 有定义。而本模块实测确认的 **19 条冲突全部是 `doc_revision` 类型**——S3（case 签名分组）在 §2.5 已经交代：实测 0 条正例。`doc_revision` 指向的是 `memory/*.md` 的段落快照，**不是** `cases.jsonl`/`workflows.jsonl`/`templates.jsonl` 索引里的条目。

结论：`apply_supersede_filter()` 在当前真实索引上**找不到任何一条现有 case/workflow/template 单元的 `superseded_by` 边**，因为触发过滤所需的 case 类冲突数量是 0。这不是实现的缺陷（机制本身正确、可测、可复用），是数据结构决定的：本项目能验证到的"新旧知识冲突"矿脉主要来自 `memory/*.md`（dataset 层），而可检索的知识单元主要来自 `case`/`workflow`（知识单元层），两者当前交集为空。要让这条机制在真实检索结果上产生可观察的过滤效果，需要 S3 矿脉先长出真实的 case 类冲突（当前 `cases.jsonl` 只有 31 条，规模不足）。

`build_knowledge_index.py` 向量化步骤依赖官方 KYSDK embedding（`~/rag/serverd/emb_serverd`），只能在部署好 embedding 服务的机器（麒麟目标机或已配置该服务的开发机）上运行——本次交付的 Windows 笔记本环境没有这个服务，**没有实际执行索引重建**，`conflict` 类型的 19 条知识单元目前只是"代码已就绪、`load_units()` 已验证正确，但生产索引 `knowledge_docs.jsonl` 里还没有它们"。这与本项目一贯的 L1/L2 分层方法论一致（`可复现性体系/measure_L1.py` 的文件头）：本报告涉及的挖掘/判定/裁决/回溯/过滤逻辑全部是 L1（纯 Python，本报告已验证），索引重建与真实语义检索效果是 L2（需要麒麟环境），如实标注边界，不假装本地已经验证过。
