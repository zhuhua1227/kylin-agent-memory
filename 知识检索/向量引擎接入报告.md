## 三、查明的关键事实（后人不必再查一遍）

### 3.1 它是什么

`kylin-ai-vector-engine` 1.2.0.1-0k1.0，包描述原文：**"A lightweight vector database fork from Milvus Lite"**。客户端 API 是 Milvus 的 C++ 形态（`VectorDB` 命名空间、`ConnectParam` / `CreateCollection` / `Insert` / `SearchArguments` / `Search` / `Query` / `Upsert` / `Delete`）。

依赖链印证：client `.so` 链接了 `libgrpc++` + `libprotobuf` + `libsqlite3`。

### 3.2 服务端早就在跑（这是原计划里的"头号未知"）

```
/usr/bin/kylin-ai-vector-engine \
    /home/<USER>/.local/share/kylin-ai-vector-engine/default.db \
    unix:/tmp/kylin-ai-vector-engine-1000.sock  ERROR
```

- **它是 systemd 的「用户级」服务**（`/usr/lib/systemd/user/kylin-ai-vector-engine.service`），随桌面会话自启，`Restart=always`。
  ⚠️ **所以 `systemctl list-unit-files | grep vector` 查不到它** —— 那是 system 作用域。必须加 `--user`：
  ```bash
  systemctl --user is-enabled kylin-ai-vector-engine   # enabled
  systemctl --user is-active  kylin-ai-vector-engine   # active
  ```
- 通信走 **Unix socket + gRPC**，不监听 TCP 端口（所以 `ss -lntp | grep 19530` 也是空的，Milvus 的默认端口在这里不适用）。
- 配置 `/usr/share/kylin-ai-vector-engine/vector_engine.json`：`max_count: 400000`（**单库上限 40 万条，本项目 14047 条记录远在范围内**）、`release_time: 300`。

### 3.3 默认字段名（`types/Constants.h`）

```c
#define DYNAMIC_FIELD_NAME       "$meta"
#define DEFAULT_ID_FIELD_NAME    "id"
#define DEFAULT_VECTOR_FIELD_NAME "vector"
```

快捷建集合 `CreateCollection(name, dim)` 会自动创建 `id`（自增）与 `vector` 两个字段并开启动态字段。**插入时必须同时给一个动态字段的数据**，否则不合法——本项目用 `$meta`（JSON）存原文，好处是检索命中后直接拿回文本，不必再回查别的存储。

### 3.4 `LoadDBFile` 的行为（踩坑）

传自定义路径 `/home/<USER>/rag/ve/work/rag_b1.db` 会失败：

```
[失败] LoadDBFile 打开数据库文件  code=1002  msg=
```

`1002` 对应 `StatusCode::SERVER_FAILED`（枚举顺序：`INVALID_AGUMENT=1000` → `RPC_FAILED` → `SERVER_FAILED` → `TIMEOUT`；头文件里只显式赋值了 1000，后面靠递增，容易看漏）。

**原因**：向量引擎是**独立的服务端进程**，db 路径由**服务端**解析，不是客户端本地打开文件。服务端不接受其数据目录之外的任意路径。

**解法**：直接使用守护进程启动时已加载的默认库 `~/.local/share/kylin-ai-vector-engine/default.db`，用**集合名**做隔离即可，不必自建 db 文件。程序里已把 `LoadDBFile` 改成非致命——一个可选步骤不该中断整个流程。

### 3.5 数据确实落盘且持久

| 验证项 | 结果 |
|--------|------|
| 插入后 `default.db` 体积与时间戳 | 15376384 → **15384576 字节**，mtime 更新 |
| 换一个进程重跑 | 报「集合已存在，先删除」→ **跨进程持久** |
| db 文件所在分区 | `/home`（sda6）—— **重启不回滚**（与 `/usr` 不同） |

头文件取自 dev 包**解压目录**（未安装），链接直接指向系统已装的 `.so` 实体文件：

## 七、规模化性能实测（2 万条）

> ⚠️ **用随机向量测量的说明**：检索耗时只取决于数据规模与向量维度，与向量数值无关，
> 因此用随机向量测**延迟**是有效的。但随机向量**不能**用于评估召回质量——
> 那需要真实向量与标注评测集（任务 C）。本节只回答"快不快"，不回答"准不准"。

### 7.1 官方向量引擎（`ve_bench.cpp`，20000 条 × 768 维，top-10）

```
插入完成，总耗时 6.86 秒，平均 0.343 ms/条

================ 检索延迟（top-10）================
  最小 12.93ms   P50 13.34ms   P95 14.15ms   最大 15.15ms

对照硬指标 ≤500ms：
  检索 P95 = 14.15ms，占预算 2.83%
  加上查询向量化（实测 30 字 P95 = 68.4ms），端到端约 82.55ms，占预算 16.51%
```

**结论：端到端检索响应约 82.5ms，占 500ms 预算的 16.5%，余量 83%。硬指标稳稳达标。**

插入 2 万条只要 6.86 秒，说明**建索引的时间瓶颈完全在向量化那一侧**（约 56 分钟，见《向量化常驻服务》报告），写入向量库的开销可以忽略不计。

### 7.2 与暴力检索的对比（`bench_bruteforce.py`，同为 20000 条）

回答一个必须回答的问题：阶段01 那种暴力检索，在真实数据规模下还够不够用？

| 检索做法 | P50 | P95 | 对照 500ms |
|---------|-----|-----|-----------|
| ① 阶段01 原样（每次比较都归一化两个向量） | 2898.7ms | **3176.9ms** | ❌ 超标 6.4 倍 |
| ② 预归一化 + 纯 Python（只做点积） | 632.1ms | **828.3ms** | ❌ 超标 1.7 倍 |
| ③ 预归一化 + numpy（矩阵乘法） | 2.9ms | **3.4ms** | ✅ 占 1% |
| ④ **官方向量引擎** | 13.3ms | **14.2ms** | ✅ 占 2.8% |

**三点结论**：

1. **纯 Python 暴力检索在 2 万条规模下确实撑不住**，阶段01 的实现超标 6.4 倍。这证明了「阶段01 骨架必须做实」不是走过场。
2. **①→② 的 3.8 倍差距，全部来自一个实现细节**：阶段01 的 `cosine_similarity()` 每比较一条就把**查询向量重新归一化一次**，2 万条数据就白算了 2 万次。把归一化提前到建库时做，算法完全等价，但省掉了绝大部分重复劳动。这是个值得写进报告的典型例子——**性能问题往往不在算法复杂度，而在实现里的重复劳动**。
3. **numpy 暴力检索（3.4ms）反而比官方引擎（14.2ms）更快**。这不奇怪：2 万条 × 768 维只有 6100 万次乘加，BLAS 用向量化指令一次矩阵乘法就算完了；而官方引擎要走 gRPC 序列化、跨进程通信、索引结构查找，这些固定开销在小数据量下反而占了大头。

**那为什么仍然选官方引擎？** 因为在本项目里它的优势不在速度：
- **「麒麟端侧适配」是本项目的差异化护城河**，全栈使用官方组件本身就是交付价值；
- **持久化开箱即用**，数据落在 `/home` 重启不丢，不必自己实现落盘与加载；
- **单库上限 40 万条**，而 numpy 方案的内存占用随数据量线性增长（2 万条 float32 已占约 61MB），扩展性受限；
- 14.2ms 相对 500ms 预算完全不构成压力，用 2.8% 的预算换上述三点，划算。

**如实记录**：如果单纯追求速度，numpy 方案更快。选官方引擎是**工程与项目定位的权衡**，不是因为它性能更优。这一点在答辩时应当直说，而不是包装成"官方引擎性能更好"。

### 7.3 一个运维注意点

基准测试插入 2 万条后，`default.db` 从 15MB 涨到 **97MB**。跑 `ve_cleanup` 删掉集合后，**文件大小不会自动缩回**（SQLite 不自动回收空间），但这部分空间会被后续写入复用，不是泄漏。默认库是全系统共用的，测试用集合**用完应当及时删除**。
