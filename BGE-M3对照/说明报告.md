# BGE-M3 对照实验 · 说明报告

> 依据《BGE-M3对照-实施方案.md》。数据与脚本同目录，`results.md` 为结果，`预登记.md` 为跑前预登记。

## 1. 定位：对照实验，不是替换方案

赛题直播 PPT **slide 13** 硬性规定：必须使用银河麒麟指定的 `kylin-coreai-embedding` 接口，
不满足视为 0 分。**slide 24 Q3** 补充："必须使用指定接口。但可以在对比实验中加入 BGE-M3
作为对照组进行性能与效果对比。"

本实验据此进行，**BGE-M3 不进入任何生产路径**：

- 不写入 `rag_knowledge*` 向量集合，不改 `search_knowledge.py` / `vector_store.py` / `render_units.py` 的默认行为；
- 所有产物只在 `BGE-M3对照/`，不覆盖任何既有 `.npy` / `.tsv` / 评测集 / 语料文件；
- 系统 `kylin-coreai-embedding`（模型 `ensemble-embd_gte-base_uint8-text`）仍是且只能是本作品唯一的生产 embedding。

## 2. 公平性怎么保证的

不靠"我记得是一样的"，靠可机器验证的三件事：

1. **同一份被嵌入文本**：`00_build_inputs.py` 从冻结产物抽出 86 条 doc + 227 条 query 到 `texts.jsonl`，
   每条带 sha256。其中：
   - 86 条 doc 文本 = 冻结 `knowledge_docs.jsonl`（`/data/RAG/RAG`，filehash `d253231a…`）的 `text` 字段，
     已逐条验证"经 `fixate_vectors.py` 的一行化转义后 == `可复现性体系/vectors/docs.tsv` 第 1 列"，
     即确认这就是产出系统固化向量的那段原文（含 `\r\n`）。
   - 227 条 query 文本 = `eval_queries.tsv` 第 5 列，已逐条验证 == `eval_set.jsonl` 的 `query` 字段。
   - BGE 侧编码前逐条再校 `sha256(text) == texts.jsonl 记录值`。
2. **同一份检索代码**：`retrieve.py`（纯 numpy）两侧共用，余弦、L2 归一化、top-k、并列打破规则完全一致。
3. **同一批题**：227 题、77 个 gold doc，两侧逐题配对。

### ⚠️ 冻结 eval_set 的 `source_rendered_sha256` 口径差异（如实记录，非本实验引入）

`eval_set.jsonl` 每条有 `source_rendered`（保留 `\r\n`）与 `source_rendered_sha256`。逐条核对发现：
**77 个 gold doc 里有 7 条（doc_id 3/4/5/15/18/25/27）含 `\r\n`，它们的 `source_rendered_sha256`
是对「`\r\n→\n` 归一化后」的文本算的，而 `source_rendered` 字段本身保留 `\r\n`。**
其余 70 条 raw-utf8 sha256 与登记值一致。

- 这是冻结产物既有的记账口径差异（当初算哈希前做了行尾归一化，但存文本时没有），**不是本实验改动引入的**。
- 对本对比**无影响**：两侧都嵌入 `knowledge_docs.jsonl` 的 `text` 原文（含 `\r\n`），逐字节一致。
- 系统侧固化向量正是用这段含 `\r\n` 的原文算的（`retrieve.py` 用它逐位复现了 R@1=0.5242 / R@10=0.8634 两个锚定值，
  见 §3），所以 BGE 侧也必须用同一段原文——已如此。

## 3. 已知答案自检（方案 §2.3）

先用新写的 `retrieve.py` 跑**系统侧固化向量**，核对 `claims.json` 里有独立主张、有 anchor 的两个指标：

| 指标 | 锚定 | 实测 | 结果 |
|---|---|---|---|
| R@1（C-265） | 0.5242 | **0.5242**（119/227） | ✅ 逐位一致 |
| R@10（C-266） | 0.8634 | **0.8634**（196/227） | ✅ 逐位一致 |
| R@5（仅 C-265 note，非硬门） | 0.8238 | 0.8238（187/227） | ✅ |

两个锚定值逐位复现 → 检索代码正确，BGE 侧的数才可信。

## 4. 三个坑各自怎么处理的（方案 §三）

| 坑 | 处理 |
|---|---|
| **L2 归一化** | `retrieve.py` 对两侧**无条件** L2 归一化再算余弦（`l2norm()`，代码内写死）。实测两侧固化/生成向量本就都是单位向量（`\|\|v\|\|` 恒 = 1.0000），retrieve 再归一化幂等；BGE 侧"直接点积"与"归一化后点积"结果逐题一致。报告已写明。 |
| **只用 dense** | `model.encode(..., return_dense=True, return_sparse=False, return_colbert_vecs=False)`，取 `dense_vecs`。不用 sparse / colbert，不做多向量混合。 |
| **截断长度** | 用 BGE-M3 tokenizer 统计：86 条 doc 最长 **393 token**，227 条 query 最长 62 token，**均 < 512 < 8192**，两侧都无截断（见 `results.md` §二）。系统侧 `MAX_SAFE_QUERY_CHARS=200` 为延迟告警非截断（源码 + 说明报告 §5 明确）。 |
| **指令前缀** | BGE-M3 **不加**任何指令前缀（BGE-v1.5 系列才需要 `"为这个句子生成表示…"`，BGE-M3 加了掉点）。`make_vectors_bge.py` 直接传原文。 |

### "结果对我们有利"的自查（方案 §五第三种）

R@3 / R@5 系统侧多命中 12–14 题，属"对我们有利"。按方案 §五"这恰恰是最该自查的时候"，
逐条查过上表四项，均无问题。非坑的可能解释：

- 这是**单一窄领域**（86 条中文报错→修复 / 多步流程），与 BGE-M3 擅长的通用 / 长文 / 跨语言检索
  不是同一分布；`ensemble-embd_gte-base` 本身也是一个较强的多语言基座。
- 按类型拆（`results.md` §四）：系统在 `case`（精确报错串 + 路径）上更强，BGE-M3 在 `workflow`
  （多步意图叙述）上更强，R@10 的持平是这两个相反效应抵消的结果——两个模型各有所长，不是一边倒。

## 5. 结果

**主对比（naive，227 题）**

| | 系统 kylin-coreai-embedding | BGE-M3 (dense) |
|---|---|---|
| R@1 | **52.42%** (119) | 50.66% (115) |
| R@3 | **76.21%** (173) | 70.04% (159) |
| R@5 | **82.38%** (187) | 77.09% (175) |
| R@10 | 86.34% (196) | **87.22%** (198) |

**McNemar 不一致对**：R@10 → 只系统 14 / 只 BGE 16（无方向）；R@3 → 29 / 15（偏系统）。

**对照实验预登记的三种结果里，落在「B. 基本持平」**（R@10 差 2 题、McNemar 无方向）：
→ **系统指定 embedding 接口已达开源 SOTA（BGE-M3）水平，用它不牺牲检索效果**；在 top-1~5 精度上还略优。

## 6. 局限

1. **227 题只覆盖 77 个不同 gold doc**（约 2.95 题/文档），**有效样本量远小于 227**，
   Wilson 区间偏乐观；本报告只报 McNemar 不一致对的条数与方向 + 参考性 p 值，**不下显著性结论**。
2. **单一语料、单一领域**（本项目自身 86 条知识单元，中文报错处理 / OS Agent 场景），
   **不构成对 BGE-M3 通用检索能力的评价**——BGE-M3 在 MTEB 等通用基准上的表现与此无关。
3. 系统侧向量为固化产物（`ensemble-embd_gte-base_uint8-text`，uint8 量化 ONNX），
   本次直接复用、未重算；BGE-M3 侧为本次 CPU 新算（torch 2.14.0+cpu，FlagEmbedding）。
4. 生成侧 / 检索策略未变，仅换 embedding；`meta_prior` / `MMR` / `BM25` 等系统档会稀释
   embedding 本身的贡献，故 headline 用 naive；系统档对照未做（时间盒内优先 naive）。

## 7. 可复现性

```
BGE 侧 + retrieve.py    纯 Python + numpy（+ FlagEmbedding 生成向量一次）   → L1，评委可复现
系统侧固化向量           ensemble-embd_gte-base_uint8-text，需 KYSDK           → L2（本次为"读已固化记录"）
retrieve.py --side kylin  会当场核对 C-265 / C-266，对不上即 SystemExit
```

主力是 `复现.md` 里那三条命令（纯 Python，一旦跑出不同结果即证伪）。产物清单见 `复现.md` 末表。
