## 一、先说这套东西**不能**做什么

**它不能证明我们没有造假。**

测量记录、日志、哈希，这些文件我们都能写，拿 AI 生成一份格式完全正确的记录毫无难度。
任何声称"有证据文件所以数据可信"的说法都是自欺欺人。

我们提供的是另一样东西：

| 提供的 | 含义 |
|--------|------|
| **可复现** | 你可以自己跑一遍。L1 层无门槛：一条命令、纯 Python、不需要麒麟环境 |
| **可证伪** | 主张精确到硬件、输入哈希、随机种子、命令行，验起来只要几分钟 |
| **环境透明** | 每个数字产自什么硬件与包版本写得清清楚楚，也解释了为什么别人会得到不同的数字 |
| **造假成本高于诚实成本** | 一旦有人重跑得到不同结果，全盘皆输 |

> **可信度不来自「无法伪造」，而来自「容易被验证」。**

这就是为什么本方案把力气**主要花在一键复现脚本上**，而不是花在设计精致的证据格式、
哈希链、防篡改校验上——后者对一个能改整个文件的人来说毫无意义，只会营造虚假的严谨感。

## 二、方法可复现 ≠ 数据可复现

这个区分必须讲清楚，不能含糊：

- **方法可复现** ✅ —— 数据提取脚本任何人拿自己的 Claude Code 装机跑一遍，
  能产出同样格式的数据集。整条处理管线是公开、可审查、可重跑的。
- **数据不可复现** ❌ —— 本项目的 9,807 条记录来自项目成员自己机器上的真实使用历史，
  **没有任何人能重新采集到同一份**。

因此凡是依赖这份具体数据的数字（记录条数、可挖掘知识量等），
第三方验证的方式是：**用我们随交付物提供的那份数据集重跑**，
核对处理结果是否一致——而不是重新采集一份数据来比对。

## 五、三类校验，为什么不能一刀切要求"数字相同"

实测发现：同一段代码在麒麟虚机（2 vCPU）与开发机（24 核）上，
**相似度分数与磁盘占用完全一致，内存接近，但延迟差了约 2 倍**。

如果一律要求精确匹配，性能类主张会全部误报为"不一致"，反而掩盖真正的问题。
因此按主张的性质分类校验：

| 类型 | 适用 | 判定方式 |
|------|------|---------|
| `exact` | 记录条数、向量维度、相似度分数、脱敏用例 | 必须完全相等 |
| `close` | 内存、磁盘 | 允许相对容差（5%~20%） |
| `bound` | 延迟 | 只验证不等式（如"是否远低于 500ms"） |
| `ratio` | 倍数关系 | 验证比值落在区间（比绝对值可移植得多） |

`bound` 与 `ratio` 类，读者验证的是**结论成立**而非**数字相同**。
报告里的绝对延迟只在其记录的那台机器上成立，环境指纹写在 `records/*.json` 的
`environment` 字段里。**这一点在报告与核对输出中均已注明，不做模糊处理。**

### 统计口径必须写明

每条主张显式声明用 `p50` 还是 `p95`：
- **延迟上界、达标判定 → p95**（保守，代表最坏情况）
- **倍数关系、趋势比较 → p50**（稳健，不受预热离群点影响）

这不是吹毛求疵。实测中曾因用 P95 算 numpy 与纯 Python 的倍数关系，
把 329× 压到 49×——因为 n=10 时 P95 恰好落在 numpy 的预热那一次上。
详见《勘误与修正记录》2.2 节。

## 六、交叉验证：同一结论，两条独立路径

单一测量的说服力有限。以下结论各由两条互不依赖的路径得到（详见 `crosschecks.json`）：

| 编号 | 结论 | 路径一 | 路径二 |
|------|------|--------|--------|
| **X-001** | embedding 输出 768 维 | 读模型元数据 `_get_model_dim()`（推理前的配置） | 数实际输出 `_get_vector_length()`（推理后的结果） |
| **X-002** | 相似度 0.9441 / 0.7118 / 0.5326 | 阶段01 纯 Python 暴力遍历 | 官方向量引擎 **+** numpy 后端（**三方一致**） |
| **X-003** | 向量数值逐位一致 | `emb_test` | `emb_vec` / `emb_serverd` / `dim_crosscheck`（四个独立程序） |
| **X-004** | 数据集 9,807 条 | 各提取脚本自行计数 | 合并脚本独立校验计数 |

X-001 的两条路径在 SDK 内部不共用数据源：一个读模型描述文件，一个数推理结果。
两者一致，"768"这个结论就不再依赖于我们是否读对了某一个字段。

## 七、原始数据一并提供

每条测量记录（`records/M-xxx.json`）包含：

- **每次运行的原始值** `runs` 数组 —— 报告里的任何统计量都能从它重新算出来，
  读者不必相信我们给的 P95，可以自己换口径重算
- **完整的原始 stdout** —— 报告里的表格是从输出里摘的，留原文供逐项对照，看有没有摘错摘漏
- **环境指纹** —— 主机、系统、内核、CPU 型号与核数、内存、Python 与 numpy 版本、关键包版本
- **输入文件 SHA256 与体积** —— 确认用的是不是同一份输入
- **随机种子** —— 随机测量可精确复现；没有种子的会如实留空

## 八、失败也留档

**一份只有漂亮数字、没有失败记录的报告反而可疑。**

《勘误与修正记录》完整列出了：4 个被推翻的技术判断、3 次方法缺陷修正、
3 次脱敏事故、以及重跑与原报告的全部数字出入（延迟系统性偏慢 16~53%）。

其中特别值得读者注意的一条：**重跑数字与首测有出入，我们没有把它抹平**。
真实测量必然波动，一组毫无波动的数字反而应该引起怀疑。
