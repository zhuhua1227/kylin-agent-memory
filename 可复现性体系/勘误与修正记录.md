## 一、数字修正

### 1.1 向量化延迟：重跑后系统性偏慢 16~53%

| 档位 | 原报告（2026-08-03） | 重跑（2026-08-04） | 差异 |
|------|-------------------|------------------|------|
| 查询 10 字 P95 | 36.4 ms | 49.1 ms | +35% |
| **查询 30 字 P95** | **68.4 ms** | **84.9 ms** | **+24%** |
| 文档块 128 字 P95 | 239.5 ms | 276.9 ms | +16% |
| 文档块 256 字 P95 | 417.9 ms | 538.3 ms | +29% |
| 文档块 512 字 P95 | 823.8 ms | 1195.1 ms | +45% |
| 文档块 1024 字 P95 | 1764.7 ms | 2542.9 ms | +44% |
| 整条记录 2048 字 P95 | 4169.7 ms | 6371.8 ms | +53% |

**这是系统性偏差，不是随机噪声**——七个档位无一例外地变慢。

**可能原因**（如实说明：未做控制变量实验，无法确定归因）：
- 两次测量之间，向量引擎的共用库 `default.db` 从 15MB 涨到 97MB，
  引擎守护进程常驻内存随之上升，而该虚机只有 3.9GB 内存，可能造成内存压力；
- 宿主机（PVE）上其他虚机的负载差异；
- 测量时机不同带来的系统状态差异。

**结论是否受影响：不受影响。** 「知识检索响应 ≤500ms」这条硬指标看的是**查询**向量化，
84.9ms 仍只占 500ms 预算的 17%，余量 83%。长文本档位属于离线建索引，不计入该指标。

**处理方式**：报告中的绝对延迟已更新为重跑值，并注明测量时间与环境。
可复现性核对（`reproduce_L1.py`）对延迟类主张**只验证结论是否成立**（如"是否远低于 500ms"），
不比对绝对毫秒数——因为这类数字本就随机器与时刻变化。

### 1.2 存储后端资源占用：重跑值略低

| 指标 | 原报告 | 重跑 | 差异 |
|------|-------|------|------|
| 官方引擎常驻内存 | 157.1 MB | 141.6 MB | −10% |
| numpy 后端常驻内存 | 62.6 MB | 59.3 MB | −5% |
| 官方引擎建索引 | 15.30 秒 | 14.58 秒 | −5% |
| 内存倍数关系 | 2.51× | 2.39× | 结论不变 |

差异在可接受范围内，**核心结论（numpy 后端内存约为官方引擎的 40%）不变**。

### 1.3 磁盘占用 0.0MB 是测量假象，不是优势

《存储后端选型对比报告》初稿中，官方引擎的磁盘占用读数为 0.0MB。

**这不是官方引擎不占磁盘**，而是：此前的基准测试已把共用库 `default.db` 撑到 97MB，
删除集合后 SQLite 不自动回收空间，本次写入直接复用了这些空闲页，所以文件没有增长。

两个后端存的是同样的约 58.6MB 向量数据，真实磁盘成本相当。已在报告中更正说明。

## 二、方法缺陷修正

### 2.1 拿中位数比 P95 —— 苹果比橘子

测量框架初版把「代表值」定为**中位数**，而此前报告记录的是 **P95**。
重跑后拿新的中位数去比旧的 P95，看起来"数字对不上"，实际只是口径不同。

**修正**：框架改为同时保存 `p50` 与 `p95`，代表值统一取 P95（与报告口径一致），
并保留每次运行的原始值 `runs` 数组。

**没有重新测量**——用已保存的原始值直接重算（`recompute_stats.py`）。
这正体现了保留原始数据的价值：**报告里的任何统计量都应该能从原始运行值重新算出来**。
读者也因此不必相信我们给的 P95，可以自己换任何统计口径重算。

### 2.2 用 P95 算倍数关系，把结论低估了 6.7 倍

核对「numpy 比纯 Python 快多少倍」时，用 P95 算出 **49×**，
低于报告声称的"两个数量级以上"，一度判定为不符。

**根因**：numpy 首次调用要付出预热代价（BLAS 线程池初始化、缓存冷启动）。
在 n=10 的样本里，**P95 实际上就是"第二慢的那次"，几乎必然落在预热那一次上**——
numpy 检索 p50 = 1.3ms 而 p95 = 9.8ms，差了 7 倍。分母虚高，比值被压扁。

用 p50 重算得 **329×**，与报告一致。

**修正方式**：不是放宽容差（那是掩盖问题），而是**让每条主张显式声明统计口径**：
- 延迟上界、达标判定 → 用 **p95**（保守，代表最坏情况）
- 倍数关系、趋势比较 → 用 **p50**（稳健，不受预热离群点影响）

口径写在 `claims.json` 每条主张里，核对结果也会打印出来，读者一眼能看到用的是哪个。

### 2.3 首轮新旧架构对比用了不可比的样本

《向量化常驻服务》首轮测量中，新架构测了 100 条样本（含 4342 字长文本），
旧架构只测了前 10 条（都是短文本），**样本集不同，结论无效**。

当时得出"新架构 P95 = 3348ms"的吓人数字，其实是长文本拉高的，
既不代表查询延迟也不代表建索引吞吐，两头不着。

**修正**：改用同一批样本重测，得到新旧架构 P50 分别为 486.7ms / 484.2ms，**提速 1.0×**。
并另做按长度分档的测量，把查询文本与文档文本分开统计。

## 三、被推翻的技术判断

### 3.1 ❌「每次调用 emb_vec 都要重载 339MB 模型」

**原判断**：常驻服务能大幅提速。
**实测**：同批样本下新旧架构 P50 为 486.7ms vs 484.2ms，**提速 1.0×，收益约等于零**。
**根因**：模型常驻在 `kylin-ai-runtime` 守护进程里，客户端的 `init_model()` 只是握手，
并不真的加载模型文件（证据：常驻服务从启动到 READY 只花 0.1 秒）。
**教训**：**性能优化必须先测量再动手**，否则可能在优化一个根本不存在的瓶颈。

### 3.2 ❌「装 dev 包会触发 undefined symbol 地雷」

**原判断**：依据部署报告的历史记录，安装 `vector-engine-client-dev` 会破坏 AI 后端。
**实测**：那是 runtime 1.1.0.1 时代的事；现在整套栈都是 0k1.1、版本一致，dev 包与已装运行时库**版本完全相同**，装它不会顶任何 `.so`。
**教训**：**历史踩坑记录要标注"当时的版本上下文"**。环境演进后同一操作的风险可能完全不同，照着老记录一味回避会白白放弃可行方案。

### 3.3 ❌「官方向量引擎作为专业向量库，可能更轻量」

**实测**：numpy 后端在冷启动、建索引、检索延迟、常驻内存四项上**全面占优**，内存只占官方引擎的 40%。
**根因**：2 万条 × 768 维只有 6100 万次乘加，BLAS 一次矩阵乘法即可；而引擎要走 gRPC 序列化与跨进程通信，这些固定开销在此数据量级反成主要成本。
**专业向量库的优势要到千万级数据才显现。**
**处理**：仍默认使用官方引擎，但理由改为端侧适配完整性与可扩展上限，**不再声称它性能更好**。

### 3.4 ❌「一条工具调用记录 = 一个知识单元」

**原设计**：把 14,047 条记录切成 2~3 万个"知识卡片"建索引。
**问题**：那样做出来的是**日志**不是知识——「第 8347 条：执行了 `ls -la`」检索出来毫无用处，约等于 grep 命令历史。
**修正**：单条工具调用是一个**事件**，知识产生于**事件之间的关系**（失败→修复、意图→序列、跨会话重复）。知识单元改为挖掘产出，规模约 600 条而非 2~3 万条。
**这个错误是用户提问「知识检索不是像 wiki 那样一问一答吗」时发现的**，否则很可能要到建完索引才暴露。

## 四、数据处理事故（脱敏假阳性，同类问题三次）

### 4.1 `session_id` 被误伤（首版）

UUID 命中"32 位以上长随机串"规则被打码。教训已记录在首版报告：
**脱敏应只作用于内容字段，不要整条记录一起过。**

### 4.2 展平操作绕过递归脱敏（第二版，最危险）

把嵌套配置展平成 `{"config_path": "apiKey", "config_value": "sk-xxx"}` 后，
原字段名 `apiKey` 降级成普通字符串值，承载密钥的字段改叫 `config_value`——不含敏感词，
**递归脱敏的保护被展平操作绕过了**。

同时还有个假阳性：字段名 `config_key` 含 "key"，导致配置项的**名字本身**被打码。

**修正**：字段改名 `config_path`；新增 `redact_if_sensitive()`，拿**原始路径**逐段重新判定。
已验证首版真实泄漏过的 `memorySearch.remote.apiKey` 路径展平后仍会被打码。

### 4.3 过度脱敏切断数据关联（第二版）

`extract_user_history.py` 对**整条记录**调 `anonymize()`，`session_id` 被打成
`[REDACTED_LONG_TOKEN]`，导致「用户意图 ↔ 工具调用序列」的关联链路被切断，
两侧会话交集**从 28 掉到 0**，「工作流程知识」这一整类将挖不出来。

**首版报告已明确警告过这一点，第二版仍然踩了。**

**教训**：
1. 脱敏粒度必须精确到字段，"整条过一遍"是危险的偷懒；
2. **过度脱敏不报错、不崩溃，只是悄悄抹掉数据关联**，代价要到下游模块做不出东西时才暴露；
3. 改变数据形状的操作（展平/转置/重命名）会让依赖数据结构的安全规则失效；
4. **光"记录教训"不够，写新脚本时要主动回查已有的教训清单。**

## 六、案例挖掘器的多轮方法修正（2026-08-04，由用户追问"数据规模够不够"引出）

完整过程见《知识检索/说明报告.md》第二节，此处只记要点与数字演变，供快速查阅。

### 6.1 数字演变全过程

| 阶段 | 案例数 | 触发原因 |
|------|-------|---------|
| 第一版启发式（同工具+5步内成功调用） | 461 | 立项时的粗估 |
| 人工抽查后：91.3% 出错记录其实是权限拒绝 | — | 发现 461 基本是噪声 |
| 加第一、二步（错误分类 + 修复判定） | 231 候选 | 方法重设计 |
| 第一轮抽样（25条）：约60%是无关下一步 | — | 需要更强过滤 |
| 加第三步（相似度过滤，阈值0.4） | 65 | 精度回升到约75~80% |
| **头部统计"91.3%"被发现是单日污染** | — | 用户追问数据规模引出的深挖 |

| 加第五步（共享修复动作去重） | **55** | 当前最终值 |

**这条数字曲线本身就是诚实工作的证据**——一条从 461 直接落到 55、中间没有任何
波动的曲线才应该让人怀疑；真实的过程是反复的、非单调的（65→84→61→55，中间有涨
有跌），每一次变化都有可查的具体原因，其中最后一次变化甚至不是在"挖掘阶段"发现的，
而是**下游任务（评测集生成）使用过程本身倒逼出的**——这比事先想好所有检验规则
再去测，更接近真实工程里发现问题的方式。

### 6.2 头部统计被单日污染（核心发现）

`mine_cases.py` 首版报告中"5174 条出错记录，91.3% 是权限拒绝"这个头部统计，
经查**90.1% 的错误来自单独一天**（2026-07-27，仅 2 个会话，一次批处理任务产生
约 4628 条几乎逐字相同的拒绝记录）。这不是分类错误——这些记录确实是真实的权限
拒绝事件，只是**用含这一天的聚合数字代表"典型情况"具有误导性**。

排除这一天后，正常日子的技术故障占比是 **20.5%~34.4%**（两次测量口径略有差异，
均远高于被污染的 2.4%~3.9%）。

**处理方式**：没有把这个发现只写进文档了事，而是给 `mine_cases.py` 加了一个
**通用的异常日检测函数** `detect_outlier_days()`——判据是"单日错误占比超过阈值
且涉及会话数极少"，不是硬编码排除某个日期。理由：数据集会持续增长，硬编码只能
治一次，通用检测能长期生效。现在每次跑挖掘器都会自动报告有没有异常日、并给出
"含异常日"与"排除异常日"两组对比统计。

### 6.3 一次真实的规则 Bug

人工抽样第二轮（20条）时发现：一条 Claude Code 自身的安全护栏拦截记录
（`Blocked: sleep 60 followed by: ...`）被误判成了技术故障、混进了案例库。
原因是 `PERMISSION_PATTERNS` 只写了 `is blocked`，漏掉了不含 "is" 的裸露写法
`Blocked: xxx`。**这类 bug 的危险之处在于它不报错、不崩溃**——挖出来的"案例"
看起来完全正常（有失败、有"修复"），只有真的去核对这条记录的语义才会发现
它压根不是一次技术故障。已修复（简化为 `\bblocked\b` 词边界匹配）。

### 6.4 一次几何直觉驱动的过滤器改进

相似度过滤（第三步）挡不住一类具体噪声：`pscp`/`plink` 命令天然带很长的连接
字符串前缀，传输**不同文件**时这段共享前缀就能让相似度冲到 0.4~0.6、通过第三步
门槛。分析真实修复与这类噪声的**最长公共子串位置**发现清晰规律：真实修复的
公共子串会跨过改动点延伸到命令结尾；这类噪声的公共子串从开头算起但到不了结尾。
这个观察被抽象成一条可复用的规则（`is_shared_template_not_fix()`），不是针对
这一批数据的一次性补丁。

### 6.5 一个下游任务倒逼出的挖掘算法漏洞（第五次修正）

用 `generate_eval_candidates.py` 给知识单元反向出题时，人工核对生成的问句发现
异常：`doc_id=45/46/47` 三条案例生成的问题几乎逐字相同。查真实数据发现——
**这不是出题环节的问题，是挖掘算法本身的漏洞**：用户连续三次用不同关键词
（`grep path`/`port`/`webui`）读同一个不存在的配置文件、连续三次失败，随后
**只有一次**真实的重试（换成 `tail -n 20`）。挖掘算法的逻辑是"每个失败独立
往后 5 步找修复"，三次失败各自的搜索都命中了同一个后续调用，于是产出了三条
"案例"，实际只有一次真实的解决尝试。

实测：61 条案例里有 10 条（16.4%，分 4 组）受影响。加了第五步
`deduplicate_shared_fix()`：按 `(工具名, 修复动作)` 分组，同组只保留
`steps_between` 最小的一条。去重后：**55 条**。

**这次修正的特殊之处**：不是靠更细致的人工抽样发现的，是**下游任务
（评测集生成）的正常使用过程**自然暴露的——出题时"两个不同问题问法撞车"
这个现象本身就是信号，不需要专门设计检测规则去找它。这提示一个更一般的
方法论：**让数据的下游消费者（评测、检索、答辩演示）持续充当质量检验，
比试图在挖掘阶段一次性穷尽所有检验规则更现实**。

由于 `doc_id` 编号在去重后发生了变化（不是简单地减少几个，因为去重会让
排在后面的知识单元编号前移），**这次修正发生后，此前生成的 258 条评测问句
全部作废，必须用去重后的 55 条案例重新生成**——这也是为什么评测集必须等
知识库真正定型后再生成，过早生成会导致返工。

### 6.6 附带产出：冷启动可行性证据

用户追问"其他没有这么多历史记录的用户怎么办"，据此做了模拟：把数据集按工具
调用记录真实起点切成"用了1/2/3周"的子集，重跑挖掘器。结果：**1 周数据（987
次工具调用）就能产出 62 条真实知识单元，不是 0**。这回答了方案的泛化性问题——
不需要造数据，系统按增量积累的方式跑，从空的记忆开始逐步长起来即可，这正是
roadmap"短中长期记忆流转"要解决的问题。详见《知识检索/说明报告.md》第一点五节。

## 七、`mine_workflows.py` 的非确定性输出 bug（2026-08-04，召回率实测时发现，比案例挖掘的问题更严重）

### 7.1 现象：手动搜索正常，自动化召回率测试却显示 workflow 类几乎 0% 命中

任务 C 冻结评测集后跑真实召回率测试，`case` 类（来自案例挖掘）召回率
`recall@10=85.6%`，接近硬指标；但 `workflow` 类（来自流程切分）
`recall@1=0.0%，recall@10=1.5%`——**137 道题几乎全部"未命中"**。

这个断崖式落差不该出现在正常工作的语义检索系统里。**没有直接把这个数字
写进报告**，先手动验证：拿评测集里一条 workflow 类查询原文直接跑
`search_knowledge.py`，结果 **top1 精确命中、相似度 0.9063**——检索系统
本身完全正常。

### 7.2 根因：`set()` 遍历顺序不确定，doc_id 编号跨进程不一致

逐层排查后定位到 `mine_workflows.py` 第69行：

```python
shared_sessions = set(tools_by_session) & set(inputs_by_session)
for sid in shared_sessions:
    ...
```

Python 的 `set` 遍历顺序受进程级哈希随机化影响（`PYTHONHASHSEED` 默认每次
进程启动都不同）。**同一份输入数据，两次运行这个脚本，产出的
`workflows.jsonl` 里条目顺序可能不同。** 而全部下游环节（建索引、生成
评测集）的 `doc_id` 都是按文件行号顺序编的——直接验证发现：评测集里
`doc_id=55` 记录的源内容是"备份塞尔达存档"，但**当时索引里真正的**
`doc_id=55` 是完全不相关的另一条流程"那你就使用非交互的方式连接"。

评测集的 `doc_id` 编号和最终建索引时的 `doc_id` 编号，来自这个脚本两次
不同的运行——每次都读同样的数据，却写出了不同顺序的文件。

### 7.3 与 `mine_cases.py` 的处理方式对比

`mine_cases.py` 此前也做过确定性验证（第五版修正时，三次独立进程运行
md5 一致），因为它的关键排序逻辑用的是**字典**（Python dict 自 3.7 起
保证插入序），不是 set。`mine_workflows.py` 这次是**同一类风险在另一个
脚本里没被查到**——教训是：写新脚本、改已有脚本时，只要用到
`set()`/`{}`（字典推导式对值不影响顺序，但用 set 做遍历对象就有风险），
就要检查是否用在了"决定输出顺序"这件事上，不能假设"反正数据一样，跑几次
结果都一样"。

### 7.4 处理

```python
# 只用 set 做成员判断（O(1)查找），不用它决定遍历顺序——
# 顺序改为跟随 tools_by_session 的字典插入序（来自文件读入的行序，确定性的）
shared_set = set(inputs_by_session)
shared_sessions = [sid for sid in tools_by_session if sid in shared_set]
```

验证：三次独立进程运行，`workflows.jsonl` 的 md5 完全一致
（`c48d6dda940fc407c303ae1f942a453f`，三次相同）。

**修复后重做了整条下游链路**：重新挖掘流程 → 重建两个后端的索引 →
重新生成评测集（因为 doc_id 编号必须与新的、稳定的 `workflows.jsonl`
重新对齐）→ 重新人工复核冻结 → 重新实测召回率。旧的 248 条候选、241 条
冻结集、第一次召回率结果全部作废。

### 7.5 这次发现的意义

**如果没有做真实的召回率测量，这个 bug 会一直潜伏下去**——`mine_workflows.py`
本身跑起来不报错、产出的知识单元内容也是对的（只是顺序不稳定），静态地看
一切正常。只有当"评测集的 doc_id 编号"与"当次索引的 doc_id 编号"这两者
被放在一起核对时，错位才会暴露。这印证了 B2 报告里已经提炼过的方法论：
**光靠挖掘阶段的人工抽样不够，必须让数据的下游消费者（这次是召回率测量）
持续充当质量检验**。

### 8.1 P-6 固化查询向量：一个只在真实数据上才会暴露的转义遗漏

整改清单的 P-6 要求把召回率也升级为 L1 可验证（此前 100% 依赖麒麟环境的
M-207）。做法是固化导出官方SDK产出的向量：95条知识单元的文本+向量存进
`vectors/docs.tsv`，169条评测问题的文本+向量存进 `vectors/eval_queries.tsv`，
新增 `measure_L1.py` 的 M-111 在纯 Python 里复算 recall@k。

固化脚本对文本做单行化处理：`text.replace("\t"," ").replace("\n"," \\n ")`
——把真实的换行符转成字面文本 `\n`，避免破坏 TSV 的行结构。**遗漏了同样
需要转义的 `\r`（回车符，0x0D）**。开发阶段用旧的 5 篇玩具语料测试时没有
暴露——那批语料是手写的干净短句，不含终端控制字符。换成真实的95条知识
单元后才暴露：其中 34 条案例文本捕获自真实终端输出（文件传输进度条、sudo
密码回显等场景常用 `\r` 做同行覆盖式刷新），这些裸 `\r` 字节原样写进了
`docs.tsv`。

**症状**：Python 默认文本模式（`open(path, encoding="utf-8")`）用"通用
换行"规则读文件，把裸 `\r`、`\r\n`、`\n` 都当作行结束符——95行的文件被
读成129"行"，用 `for line in f` 逐行解析向量的代码在这些多出来的"行"上
读到残缺的浮点数片段，直接报错或（更危险的）静默解析出错误的向量。

**发现过程**：不是靠人工审查代码发现的，是在把 `docs.tsv` 换成真实语料后
主动做了一次字节级核对（`data.count(b'\r')`，34处，且都不与`\n`成对出现）
才确认。**如果没有做这次核对，这个 bug 会一直潜伏到某次因为文本内容偶然
包含 `\r` 才复现**，症状还会因偶然性显得很像"环境问题"，难以定位。

**修复**：转义规则补上 `.replace("\r", " \\r ")`（与 `\n` 的处理方式对齐，
写进字面 `\r` 文本而不是留原始控制字符），修复 `fixate_vectors.py` 与
`fixate_query_vectors.py` 两处固化脚本（remote-only，随 `vectors/` 一并
交付），已生成的 `docs.tsv` 用同样规则做字节级修复重新固化，不需要重新
调用KYSDK（向量数值本身未受影响，只是文本列的转义有遗漏）。修复后 95行
读回95行，169行读回169行，M-111 复算的 recall@10 与 L2 的 M-207
逐位一致（`claims.json` C-233）。

> 📌 **2026-08-14 整链重跑后该交叉验证仍成立，数字已更新**：固化向量
> 重新导出为 86 条知识单元 + 227 条查询，M-111 与 M-207 的 recall@10
> 均为 **86.34%**，逐位一致（v1.3.0 时为 91.72%）。这条交叉验证的价值
> 不在具体数值，而在"两条独立路径给出同一个数"这件事本身——换了一整套
> 语料与题目之后它依然成立，说明验证的是机制不是巧合。

**方法论意义**：这是本项目又一个"只在真实数据规模/真实数据分布下才暴露"
的 bug（与第七节 `mine_workflows.py` 的非确定性 bug 同一类教训）——用
干净的玩具数据测试代码路径本身没问题不代表规则完备，真实数据里的噪声
（这里是终端控制字符）恰恰是最容易被开发时手造的测试用例漏掉的那一类。

## 九、行尾转换差点让"证据被改动过"对每一位复核员误报（2026-08-07，第三轮整改中自己踩出来的）

### 9.1 起因：一处修复暴露了一个一直存在的隐患

第三轮整改的 R3-36 把交付物 sha256 清单接进了 `reproduce_L1.py` 开头，
并把覆盖面从 `records/*.json` 扩到 `claims.json` 与各模块关键脚本。

接完之后准备提交，`git add` 刷出一屏警告：

```
warning: in the working copy of '可复现性体系/records/M-101.json',
LF will be replaced by CRLF the next time Git touches it
```

本机 `core.autocrlf=true`（Windows 上 git 的默认值），含义是：**仓库里存
LF，检出到工作区时换成 CRLF**。而清单算的是**工作区文件的字节**。

实测确认后果：

| 文件 | 仓库 blob | 检出后的工作区 |
|---|---|---|
| `知识检索/cases.jsonl` | 0 处 CRLF | 27 处 CRLF |
| `可复现性体系/measure_L2.py` | 0 处 CRLF | 570 处 CRLF |

也就是说，**任何人克隆这个仓库后跑一键复现，开头就会看到一整屏
"证据被改动过"**——而且这个措辞是最糟的那种：它看起来像我们篡改了证据，
实际只是行尾不同。这个隐患一直存在，只是 R3-36 把清单接进主流程之后，
它才从"没人会撞上"变成"每个人第一步就撞上"。

### 9.2 修法与随之踩到的两个坑

加 `.gitattributes` 钉死 `* text=auto eol=lf`（优先级高于各人本地的
`core.autocrlf`，不需要复核员先去改自己的 git 配置），并把工作区已有的
46 个文件统一转成 LF。**然后连着踩了两个坑，都是同一个形状**：

**坑一：冻结的评测集文件被一起归一化，外部锚定当场作废。**
`评测集/eval_set.jsonl` 的 sha256 `2e198716fa14b587…` 已经发成 GitHub
issue 评论、由服务端时间戳背书。哈希算的是原始字节，而它当初是以 CRLF
落盘并被锚定的——归一化成 LF 后算出 `9923f49c…`，`reproduce_L1.py` 的
C-221 立刻报红。**这条锚定一旦作废是补不回来的**：重新锚定只能证明
"今天冻结了"，证明不了"当初先冻结后跑模型"。

**坑二：三份知识语料同样被哈希登记过，只是不显眼。**
`eval_set_frozen.json` 的 `knowledge_base_sha256` 字段登记了
`cases/workflows/templates.jsonl` 的 sha256，`measure_recall.py` 的 E-3
语料哈希卫每次跑都核对。归一化之后 `test_detectors.py` 的
"E-3守卫-正常路径(未篡改)不应误报拒跑" 当场变红。

两个坑都靠把这 6 个文件在 `.gitattributes` 里标成 `binary` 解决——
它们保持锚定时的原始字节，其余文件跨平台统一为 LF。

### 9.3 教训

**"整个仓库统一行尾"这种听起来纯属整洁性的改动，会直接改变文件的
sha256，因而会直接击穿任何以 sha256 为锚的机制。** 本项目恰恰有三套这类
机制（交付物清单、评测集外部锚定、E-3 语料哈希卫），改之前一个都没想到。

真正救回来的不是谨慎，是**那三套机制自己报了红**：C-221 报冻结哈希不符、
E-3 守卫报正常路径被拒、清单报字节不符。如果当时它们中任何一个是"永不
报错的检查器"，这次就会以"仓库更整洁了"的面貌安静地把锚定毁掉，等到有人
去核验时才发现，而那时已经补不回来了。

这也是对整个第三轮主题（"检查器守着过去，没人守当下"）的一次正面印证：
**检查器的价值不在它平时全绿，而在你自己犯错时它敢红。**

顺带留下两处改进：
- `generate_manifest.py` 在哈希不符时会先试着把 CRLF 折成 LF 再算一次，
  对上了就明确写"内容逐字一致，只是行尾不同，**不是证据被改动**"——
  仍判失败（清单锁的就是字节），但不让一次环境问题以造假的措辞出现。
- 该脚本写清单时显式 `newline="\n"`，否则它自己会成为全仓库唯一一个
  "工作区字节 ≠ 入库字节"的文件。一份用来核对字节的文件，自己的字节先
  不稳定，说不过去。

## 十、脱敏器吃掉了自己产生的标记，12,332 处语料内容被销毁（2026-08-07 第四轮整改中发现）

### 10.1 现象

`_scrub_string()` 在**同一趟**里会先把 `AKIA…` 这类值替换成 `[REDACTED_LONG_TOKEN]`，
而**标记名里的 `TOKEN` / `SECRET` 本身就在关键词表里**，紧接着关键词上下文规则
（分隔符字符类含 `]`）又命中这个刚生成的标记，把右括号连同后面的正文一起吃掉：

```
原文  Abcdefghij0123456789Abcdefghij0123":"nextvalue123"
输出  [REDACTED_LONG_TOKEN[REDACTED_SECRET]          ← 尾部内容全部丢失
```

**全量实测：7 个语料文件 37,179 条记录中，5,709 条（15.36%）含这种残缺嵌套，
共 12,332 处。** 其中主数据集 `memory_source_records.jsonl` 有 2,470/6,927 条
（35.7%）受影响。

损坏已传播进冻结产物：`cases.jsonl` 10 处（`failed_input.command` ×8、
`fixed_output` ×1、`fixed_input.command` ×1，**正是被索引被检索的知识正文**）、
`eval_set.jsonl` 2 处、`eval_candidates.jsonl` 2 处、固化向量 `docs.tsv` 1 处。
所幸 169 道题的**题面 `query` 字段干净**，那 2 处落在 `source_rendered`
（溯源字段），召回率测量的输入本身没有被污染。

### 10.2 为什么三轮的幂等性修复没能发现它

第三轮 R3-00 给出的判据是"**对同一段文本连续脱敏两次，结果必须逐字相同**"，
并据此加了按标记切段的保护。这条判据是对的，但它**测不出这一类**：

> 残缺在**第一趟**就已经定型，第二趟起结果稳定不变——**幂等性成立，
> 而数据已经坏了**。

切段保护只保护**输入里已经存在的**标记，不保护**本趟新产生的**标记。
这是一个典型的"判据覆盖了它自己命名的那个性质，却没覆盖真正要防的后果"。

### 10.3 修法与它修不了的部分

`_apply_rules_marker_safe()`：把"按标记切分"从**规则链前做一次**改成
**每条规则前各做一次**——第 N 条规则产出的标记，对第 N+1…M 条不可见。
复用同一套已验证的切分机制，不引入新占位符（第三轮试过 `\x00`，
`\S` 照样匹配它，此路不通）。7 组触发形态残缺产出 0/7，代价是全量脱敏
22.7s → 30.9s（+36%）。

⚠️ **但这修不回已经丢的内容。** 那 12,332 处原文在历史 rescrub 里就没了，
只能重新从原始来源（`~/.claude/projects/**/*.jsonl` 等）抽取。因此
「重跑全链路」这件事的性质变了：它不再只是刷新过期数字，而是**唯一能挽回
这 12,332 处内容的途径**，且链条要从**重新抽取**开始，不是从 merge 开始。

### 10.4 教训

**一条规则的输出，会成为下一条规则的输入。** 规则链里任何"替换成某个标记"
的动作，都必须同时回答"这个标记会不会被后面的规则再吃一次"。本项目的标记
恰好用了 `SECRET`/`TOKEN` 这些词——而它们就在自己的关键词表里，等于给规则链
埋了一个自噬循环。命名与规则表的这层耦合，四轮复核、三次脱敏事故都没人注意到。

## 十一、有人往代码注释里写了一个从未跑过的"实测数字"（2026-08-07）

第四轮整改期间，一个中途因额度耗尽掉线的执行者，在 `anonymize.py` 的
关键词分隔符规则旁写下：

> 「真实语料 36,999 条全量实测：加宽前后 `_scrub_string` 输出差异 **0 处**」

**接手复核的执行者实测是 36 处，逐条查看全是误伤**，无一真实凭据。形态统一：
sudo 的中文提示 `[sudo] xxx 的密码：` 之后的整段日志 / JSON / 时间戳被吞掉。

根因是把全角冒号并进了那个带 `*` 的分隔符字符类，使分隔符能**连续跨过
全角冒号与其后空白**，起点落到下一段正文上；而 `_looks_secretish()` 用
`.search()`，`openclaw-gateway`（正好 16 位）之类轻松过关。**加宽了入口
却没同步收紧判据——与第三轮 279→1109 那次是同一个形状。**

已改成并列两分支（半角分支与旧版逐字符相同，保证旧路径行为零变化；
CJK 分支不得夹半角标点，且额外要求值以 ASCII 字母/数字开头），
真实语料误伤回到 **0 处 / 36,999 条**，标注集召回仍 27/27、负例误伤 0/19。

### 为什么这条要单独记一节

这个项目通篇在讲"数字必须可证伪、报告里的每个数都要能被五分钟重跑验证"。
而**它自己的源码注释里出现了一个没跑过的实测数字**——如果不是接手的人
起了疑心去复算，它会一直躺在那里，且比报告里的错误数字更隐蔽：
没有任何检查器会去核对注释。

留下的做法约束：**注释里凡出现"实测/全量/N 条"这类字样，就必须是真的跑过的**。
写不出实测就写"未测"。这一条无法机器强制，只能靠留档提醒。

## 十二、`.scrub.json` 的跳过判据只看规则、不看数据（2026-08-14 整链重跑时暴露）

### 12.1 现象

`rescrub_strings.py` 用旁路文件 `<产物>.scrub.json` 记录"上次是用哪个版本的
脱敏规则处理的"，下次运行时比对规则指纹，一致就跳过——避免规则没变时无意义
地重扫几十 MB。这个设计本身是对的（R2-12 加的）。

**但判据只有规则指纹这一半。** 整链重跑之后：

| 产物 | 旁路文件记的 | 文件实际 | 判定 |
|---|---|---|---|
| `generation_raw_log.jsonl` | total=152 | **86 条全新内容** | 跳过 ✗ |
| `generation_skipped.jsonl` | total=28 | **9 条全新内容** | 跳过 ✗ |

规则确实没改，所以指纹一致、判定跳过——**而文件里的内容已经整批换掉了**。
补上内容指纹后重跑，实测 `generation_raw_log.jsonl` **86 条全部因规则而变化**，
`memory_source_records.jsonl` 151 条、`dataset_user_history.jsonl` 150 条。
也就是说，整链重跑产出的新内容**一次都没有过脱敏**，而它承载的正是发给
出题模型的知识单元原文。

### 12.2 为什么旁路文件自己记的 total 对不上都没人发现

因为**没有任何检查比对过"旁路文件记的 total"与"文件实际行数"**。
第四轮补的 `test_rescrub_actually_applied` 只核对指纹时效（"记的规则版本
是不是当前版本"），没核对内容。指纹时效那一关是过的——这恰恰是问题所在：
**检查器验证了它声明要验证的那件事，而那件事只覆盖了一半的输入。**

### 12.3 修法

跳过判据改为"规则指纹 **与** 内容指纹都未变"，旁路文件新增 `content_sha256`
字段（记的是脱敏之后的内容指纹）。规则变或内容变，任一发生就必须重跑。

### 12.4 教训

**只锁一半的输入，等于没锁。** 这与本项目 `provenance.py` 那套内容级血缘
（同时锁代码指纹与输入指纹）是同一个道理——血缘那边一开始就把两半都锁上了，
而 rescrub 这边只锁了"规则"这一半，两处相隔不到一周写成，没有互相参照。

同类形态在本项目已出现多次：mtime 判据（只锁元数据不锁内容，被 touch 绕过）、
`by_difficulty` 硬编码两档（只统计已知档位，漏掉新增的）、
`corpus_size` 写死 95 而召回率动态读（只锁一半，标签与内容脱节）。
**判据涉及多个输入时，把它们逐个列出来，问一遍"这个变了会怎样"。**

## 十三、脱敏器吃掉了审计链自己的标识符（2026-08-14，接第十二节）

修完第十二节那个"只锁规则不锁内容"的盲区、重跑 rescrub 之后，
`generation_raw_log.jsonl` 的 86 条记录**第一次真正过了一遍脱敏**——
然后审计链当场断了：

```
❌ 产物 run_id 均在清单声明的血缘内：
   以下 run_id 未在清单的 run_lineage 中声明：['[REDACTED_LONG_TOKEN]']
```

`run_id` 形如 `gen-20260814T085700Z-0b8e6c2382e5`，37 位连续字母数字加连字符，
**正好命中"长随机串"兜底规则**，86 条全部被打成 `[REDACTED_LONG_TOKEN]`。

**讽刺之处**：`run_id` 是三轮遗留的 R3-13 才刚补上的、审计链存在的**全部意义**
所在——而它被本项目自己的脱敏器抹掉了。`eval_candidates.jsonl` 因为在冻结
豁免名单里没被 rescrub 处理，反而成了唯一幸存的副本。

### 修法

1. 给这个精确形态加豁免（`gen-\d{8}T\d{6}Z-[0-9a-f]{12}`），与 sha256/UUID/
   语义化包名同一类处理——它有明确结构（前缀+UTC时间戳+输入指纹），不是随机凭据。
2. 已被吃掉的 95 条按血缘反推补回：77 条从未受损的 `eval_candidates.jsonl`
   按 `doc_id` 反查得到确切 run_id；剩下 18 条（被跳过的知识单元，不产候选、
   无从反查）按"只可能出自末次续跑"补回，**并逐条打上 `run_id_recovered`
   标注说明来源**，不冒充原始记录。

### 教训

**脱敏规则的作用对象包括本项目自己产生的元数据。** 前十二节讲的都是
"脱敏漏了什么"，这一节是反过来——**脱敏吃了不该吃的，而被吃的恰恰是
用来证明可信度的那个字段**。

通用规则（"长随机串一律打码"）天然会误伤结构化标识符。项目里已经为此
豁免过 sha256（锚定链依赖）、UUID（session_id 关联链依赖），这次是第三类。
**判据应当是"这段字符串有没有可辨识的结构"，而不只是"它有多长多随机"**——
每加一类自有标识符，都要回头问一句：兜底规则会不会把它吃掉。

## 十四、麒麟机上的脚本副本落后于交付版，把真实主机名带回了记录（2026-08-15）

补 R3-31 的领域内负样本时，M-209 要在麒麟机上重跑。取回记录后
`test_detectors` 立刻报红：**`records/M-209.json` 里含身份映射表里的两项
真实值**（主机名相关）。

排查发现麒麟机 `~/rag/repro/measure.py` 里 `_pseudonymize_hostname`
**出现 0 次**——那台机器上的副本停留在假名化机制上线之前的版本。
本地 `records/M-2xx.json` 全都是 `device_d`，唯独新跑的 M-209 是真实主机名。

### 这暴露的不是一次疏忽，是一条结构性风险

L2 记录只能在麒麟机上产生，而麒麟机上的脚本是**手工传上去的副本**。
两边什么时候分叉过、分叉了多少，此前**没有任何机制能发现**——
本地怎么改都不会让麒麟那份跟着变，而记录一旦取回就混进交付物。

这次是防复发检查抓住的（它扫的是**受跟踪文件的内容**，不管文件从哪来），
但那是运气：如果泄漏的是别的东西、或者恰好不在两张表里，就过去了。

### 已做的

1. 把 `identity_map.txt` / `identity_map_loader.py` / 当前版 `measure.py`
   同步到麒麟机，重跑 M-209，确认 hostname 已假名化、两表零残留。
2. 顺带修了 M-209 的另一处同类问题：输入文件不在时它**只 note 一句就
   return**，产出一条 **0 指标的记录并退出 0**——本轮就真踩到了
   （`RAG_EVAL_DIR` 没设），看起来跑完了，实际什么都没测，而记录文件已经
   把上一次的真实结果覆盖掉。改为直接 `SystemExit` 并给出正确命令行。
   这与 R2-11 的三处绕过口、R4-17 的脚本缺失是同一类：
   **证据缺失被当成「跳过检查」而不是「检查失败」**。

### 未做的（如实声明）

**没有建立"麒麟机脚本版本与交付版一致"的自动核对。** 正确做法是每次跑 L2
之前先比对两边关键脚本的 sha256，不一致就拒跑。本轮只是把这一次的分叉补上了，
**没有把实例升级成类**——下一次换一台机器、或隔一段时间再跑，同样的事会再来
一次。记在这里，不假装已经解决。

## 十五、三项跨轮遗留的关闭（2026-08-15）

R3-31 是**四轮一字未改**的遗留项，R4-16/R4-17 是第四轮新提出的。本节记录
它们各自被关闭到什么程度，以及关闭过程中暴露出的新问题。

### 15.1 R4-17：删掉 L1 测量脚本，一键复现全绿

**修复前实测**：删掉 `measure_L1.py` 后重跑，输出是「通过 71、不符 1」——
**与干净基线一模一样**，只多一行黄字"跳过"，重算项从 58 静默降到 22。
读者无从分辨这份结果是不是完整跑出来的。

难点在于不能一刀切判失败：R3-31 认定「只拿到 `可复现性体系/` 一个文件夹」
是合法场景。**区分判据是目录在不在，不是模块在不在**：

| 情形 | 判定 |
|---|---|
| 本目录的脚本被删（目录在） | ✗ 失败 |
| 旁目录的脚本被删（旁目录在） | ✗ 失败 |
| 整个旁目录不在（部分交付） | ⚠ 跳过，合法 |

四条路径（含空变异基线）都写进了变异测试。过程中自己踩到两次：
① 初版用 `--check-only` 跑探针，**那条路径根本不 import 测量模块**，
四种变异全测了个空，而**空变异基线照样 PASS**——一个活的"恒假检查器"标本；
② 诊断措辞把被连累的旁目录脚本误报成"文件不见了"，会让读者去找两个
根本没丢的文件，已分开措辞。

### 15.2 R4-16：主张层只守住 19.4% 的数字

复核员篡改一个**未被任何主张引用**的指标，72/72 全绿。`metric_coverage.py`
把这个落差算出来（**82/423，19.4%**）并印在一键复现输出里。

⚠️ **它不是拿来"提高"的 KPI**。本轮补了 8 条真主张（领域内负样本 4 条 +
MRR/nDCG 4 条），覆盖率反而从 19.7% **降到** 19.4%——因为 M-111/M-209
同时新增了 47 个中间量指标。这个反直觉的结果本身就是"别把它当 KPI 追"
的最好说明，已写进常量旁边的注释。

它带一道闸：删主张会让覆盖数下降并报红，防的是「删掉检查器什么都不会发生」。

### 15.3 R3-31：负样本太容易，把结论撑虚了

四轮里那 20 条负样本全是红烧肉/唐朝/冰岛首都。补 20 条**领域内负样本**
（同一领域、库里确实没做过，每条先核验词根在语料中出现 0 次，本次 0 条判废）
之后：

| 用哪档负样本 | precision | recall | F1 |
|---|---|---|---|
| 域外（原有） | 1.0000 | 1.0000 | **1.0000** |
| **域内（新增）** | 0.7727 | 0.8500 | **0.8095** |

**落差 0.1905**。第八节那个"两分布完全不重叠"的完美结论，是被过于容易的
负样本撑起来的。

另一半是 **MRR / nDCG**（四轮只报 recall@K）。补的过程中挖出一个坑：
`measure_L1.py` 的分档循环**写死 `("close", "hard")`**，v1.4.0 第一次真正
出齐的 paraphrase 档 77 题**一个分档指标都没算到**——与
`review_and_freeze.py` 里写死 `by_difficulty` 是同一个毛病：
**把"当前数据碰巧只有这两类"固化成代码里的常量**。已改为从数据取。

### 15.4 一个必须说清的副作用

R4-17 的用例要在临时副本里把 `reproduce_L1.py` 完整跑四遍，
`test_detectors.py` 总耗时从约 90s 涨到 **约 260s**，超过了
`verify_reports.py` 里写死的 180s 超时，导致一条正确的检查因为**跑得慢**
而变成假红。已把超时调到 900s。

**假红比不检查更糟**——看多了会让人习惯性忽略红字。新增耗时大的用例时，
必须回头检查所有会调用它的地方的超时值。

### 顺带炸出来的第二个问题：麒麟上的 numpy 索引停在 8月5日

⚠️ **注意这个 2.6% 是怎么被发现的**：不是任何检查器报的，是我为了关掉一条
落差登记而顺手重跑，肉眼看见两行数字对不上。如果这轮没重跑，交付物里就会

### 第三个（小但同形态）：L2 记录标题永远是"(版本未知)"

与 R2-28、R3-26 同一类：**修实例没修类，漏掉一个调用点**。

2. **没有任何一道检查负责"记录是不是当前版本"。** 血缘管产物、MANIFEST 管

3. **麒麟机上的一切都是手工副本**——脚本、索引、映射表。第十四节记的是脚本
   分叉，这一节是索引分叉。同一个根因的第二次发作，仍然没有自动核对机制。

## 十七、冲突评测集的"冻结"文件每次重跑都换 sha256（2026-08-27，冻结前发现）

### 事实

《冲突规则冻结-执行方案.md》要在跑 D2 挖掘器之前把冲突判定规则冻结成
09-02 留出集评测的基线。落实 §三（写冻结记录 + 哈希）时发现：

- `review_and_freeze_conflicts.py` 的 `build_eval_set()` 用 `datetime.now()`
  给**每一行** eval 记录盖 `adjudicated_at`。
- 于是 `conflicts_eval.jsonl` 的 sha256 **每跑一次就变一个值**：
  2026-08-16 首冻 `b03056e6…`、08-19 重跑 `8d0c6f26…`、08-27 排查时再跑
  又一个值。`conflicts_eval_frozen.json` 里登记的 `sha256` 也因此和盘上的
  实际文件对不上（08-19 那次重跑写了 eval 文件、但撞上"内容变了版本号没变"
  的防呆断言退出，没更新 frozen 元信息，留下一个半冻结状态）。
- `知识冲突处理说明报告.md` §5.1 引用的是最早的 `b03056e6…`，也是错的。

### 为什么这是缺陷而不是"无所谓"

这个文件的**全部意义**就是"按整份文件 sha256 冻结 + 发 GitHub issue 拿
服务端时间戳锚定"。运行时刻的墙钟时间进了文件字节，等于：任何人重跑一次
`review_and_freeze_conflicts.py` 核对，都会算出不同的 sha256，看起来像
证据被人动过——正是这套可复现体系最该避免的观感。按执行方案 §一 的判据
（"修法能用一句不提这条具体数据的规则说清 = 真 bug"）：**冻结产物不得
内嵌运行时刻的墙钟时间；人工裁决时刻是历史事实，应为固定常量** —— 是 bug，修。

### 修法（v1.0.0 → v1.1.0）

- 新增模块常量 `ADJUDICATED_AT = "2026-08-19T10:16:51.233858+00:00"`（那轮
  裁决实际发生的时刻，也正是当时盘上文件里盖的值）。
- `build_eval_set()` 和复核日志的 `reviewed_at` 都改用这个常量，不再 `now()`。
- `frozen_meta` 的 `frozen_at` **保留** `now()`——它记的就是"这次冻结发生在
  何时"，是应该变的那个字段，且写一次即提交、不参与 ground truth。
- 版本号 1.0.0 → 1.1.0，注释写明"确定性修复，裁决内容零变化"。
- 新增 `M-305`（`measure_conflicts.py`）：登记三个规则文件 + 候选池/评测集的
  sha256、分界行数（149 / 36），并**连调两次 `build_eval_set()` 断言逐字节
  一致**——这条就是本次修复的阴性验证，非确定性一旦复发当场报红。
- `generate_manifest.py` 新增 `_FROZEN_RULES`（evidence 级）：`mine_conflicts.py`
  / `review_and_freeze_conflicts.py` / `measure_conflicts.py` / `conflicts.jsonl`
  / `conflicts_eval.jsonl` / `conflicts_eval_frozen.json` 失配即让 `reproduce_L1`
  报红退出——此前这几个文件要么没进清单、要么是 script 级（只黄字警告）。
- `.gitattributes` 把这几个 `.jsonl`/`.json` 标 `binary`，锁死原始字节。

**实测**：修复后连跑 3 次，`conflicts_eval.jsonl` 恒为 `8d0c6f26f6ded651…`
（= 08-19 那版逐字节相同，18 正 18 负、label/type/reason_kind 一字未改）。
`M-302`(35/36=97.2%) / `M-303`(verdict 18/18、type 8/18、reason 17/18) /
`M-304`(34/34) 全部与修复前逐位一致。

### 教训

1. **"冻结"必须先问一句"这个文件能确定性重建吗"。** `评测集/` 那套冻结机制
   写文件显式 `newline="\n"` 防 CRLF、加了版本防呆断言，唯独没防住自己
   往每行里写 `now()`——防的是别人改文件，没防自己生成时就不稳定。
2. **半冻结状态比没冻结更危险。** 08-19 那次 eval 文件写了、frozen 元信息
   没写，两个文件从此各说各话，`知识冲突处理说明报告.md` 抄的又是第三个
   （最早的）值。三处不一致，靠这次逐个算 sha256 才对出来。
3. 与第七节（`mine_workflows.py` 的 set 遍历顺序非确定性）、
   独立评审 P-4 是**同一类 bug 的第三次**：产物生成环节混进了非确定性来源。
   这次直接把"连调两次必须一致"写成了 M-305 的硬断言。

### 追加（同日）：冻结产物里 4 类标识没脱敏，v1.1.0 → v1.2.0

冻结提交推送后，用户要求"给这些数据脱下敏"。复查 `conflicts.jsonl`
/ `conflicts_eval.jsonl`：`[REDACTED_IP]` / `[REDACTED_SECRET]` / `device_a` 等
该打的都打了，但**主机名、AppID、用户名大小写变体这三类零覆盖**——
`identity_map.txt` 只有 8 条，一个 Ubuntu 虚机主机名不在表里；某个用户名
在表里但匹配是**大小写敏感子串**，它的首字母大写变体（一个 Minecraft OP 名）
漏了；两个 QQ 机器人 AppID 也不在表里。与独立评审记的"主机名/用户名零规则"
同一个缺口，只是这次发作在冲突模块的输出上。
（这 4 个真实值本身见 `identity_map.txt`，那张表 gitignore；本文件是受跟踪
交付物，一律描述性措辞——同 R3-01 记的那次"注释里抄了真实用户名"的教训。）

**为什么能修得干净**：这 4 类标识 `git grep` 全项目只出现在
`conflicts.jsonl` / `conflicts_eval.jsonl`（+ 冻结记录自己的正文，已改成
描述性措辞）——**不在 `cases.jsonl` / `workflows.jsonl` / `preferences.jsonl`
这条被 v1.4.0 召回率哈希锚定的语料链上**。所以只需处理冲突模块，
不牵动别的冻结。

**修法**：`identity_map.txt` 补 4 条（主机名→`device_e`、大写变体→`user_a`、
两个 AppID→`[REDACTED_APPID]`）→ `rescrub_strings.py --force-all` 重扫源数据集
（`memory_source_records.jsonl` 136 条记录变化，`generation_*.jsonl` 0 变化、
只更新指纹旁路文件）→ 重跑 `mine_conflicts.py`（149 行、candidate_id 顺序
不变、实测 4 条记录变化且**全是 token 一致替换**）→
`review_and_freeze_conflicts.py` VERSION 1.1.0 → **1.2.0**。

**实测**：`conflicts_eval.jsonl` 2 行变化——一行是纯 token 替换（主机名出现在
E-029 的 hostname 字段里，假名同样 8 字符、字节对齐），另一行是 K-0042
（`same_sitting` 负例）的 `claim` 预览字段：`[REDACTED_APPID]` 比原 10 位
AppID 长 6 字符，`_claim()` 的 `text[:300]` 截断点前移 6 字符——**纯预览
字段、不参与 `is_conflict()`/`adjudicate()`**，如实记录不特殊处理。
`M-302`(35/36) / `M-303`(18/18、8/18、17/18) / `M-304`(34/34) 逐位不变。
`test_no_real_secret_in_tracked_files` 现在把这 4 个真实值也纳入受跟踪文件
扫描（`identity_map.txt` 是它的输入之一）。

**教训**：脱敏的覆盖面要按"这个 token 是不是真实标识"判，不是按"它像不像
随机串"或"字段名敏不敏感"——主机名、AppID、游戏 ID 都是规规矩矩的可读
字符串，任何基于形态的规则都漏。唯一可靠的是**枚举式的 `identity_map`
+ 让防复发扫描以它为准**，而这张表得有人记得往里加。

### 连带炸出来的：首次冻结提交前没拿 test_detectors 扫暂存集

给 `conflicts.jsonl` 补脱敏时，`test_no_real_secret_in_tracked_files` 顺带
报出：**首次冻结提交（`95356eb`）把 11 个此前 untracked 的内部方案/报告/
脚本文件一起提交了，里面有两个麒麟机用户名（旧 VM 的 + 采集机的，本就在
`identity_map`）与两个内网 IP**。根因是那次 §二 的"提交前安全检查"只跑了
自己写的凭据 grep + 人工核 7 类敏感文件，**没跑 `test_detectors.py`**——
而当时 `git reset` 后暂存区是空的，即便跑了工作区版也扫不到未跟踪文件。
正确做法：`git add` 完再跑 `test_detectors.py`（它按 `git ls-files` 枚举）。

处理：这 11 个文件里的两个用户名 → `device_b` / `device_c`、
`192.168.x.x` → `[REDACTED_IP]`，**定向替换**（不是 `_scrub_string`——
实测它会把 `CASE_SIGNATURE_OVERLAP_THRESHOLD` 常量名、`test_*` 函数名、
shell 的 `$PW` 变量都误判成密钥打码，把文档和脚本搞坏）。
