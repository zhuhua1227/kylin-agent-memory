## 一、要做的事

给 `measure_recall.py` 加一个 `--retrieval` 参数，跑一组消融，把结果接进可复现性体系。

### 1.1 六种配置

| 配置名 | 内容 | 目的 |
|---|---|---|
| `naive` | 朴素向量 top-k（**当前报告口径**） | 基准线，必须与现有 86.3% 逐位复现，否则说明改动引入了偏差 |
| `meta` | + 元数据过滤（按 `doc_type` 限定候选） | 单项贡献 |
| `mmr` | + MMR 去同质（`mmr_lambda=0.7`） | 单项贡献 |
| `bm25` | + BM25 混合（`hybrid_alpha=0.7`） | 单项贡献 |
| `supersede` | + 过滤 `superseded_by != null` 的知识单元 | 单项贡献 |
| `all` | 全开 | 交互效应 |

**每种配置都要报 R@1 / R@3 / R@5 / R@10 + Wilson 95% CI**（`wilson_ci` 复用 `评测集/measure_recall_ci.py`）。

### 1.2 实现路径

⚠️ **`search_knowledge.py:241` 的 `search()` 是 CLI 打印函数，函数体末尾没有 return，不能直接当库调用。**

三条路，**推荐第 2 条**：

1. 改造 `search()` 成返回值版本 —— 会动到已稳定的模块，不推荐
2. **在 `measure_recall.py` 里按同样的调用序列自己组装**：
   `create_store` → `client.encode` → `store.search(fetch_k)` → 按 doc_type 过滤 → `apply_low_value_penalty` → MMR / BM25 → 截断 top_k
3. 抽一个 `retrieve()` 到 `search_knowledge.py`，CLI 与测量共用 —— 最干净但改动面大

**可直接复用的现成件**（都在 `search_knowledge.py`）：

```python
is_low_value_meta(meta) -> bool                    # :148
apply_low_value_penalty(raw_hits, docs)            # :177
class BM25(doc_ids, texts, k1=1.5, b=0.75)         # :70
    .scores(query: str) -> dict[doc_id, float]
```

**注意 `fetch_k`**：`search_knowledge.py:260` 的做法是——任一选项开启时先取 `max(top_k*5, 50)` 个候选，重排后再截断到 `top_k`。**必须照做**，否则 MMR/BM25 没有重排空间，等于没开。

## 二、🔴 三个必须避的坑

### 2.1 `supersede` 那一档必须扣除语料规模效应

过滤掉 `superseded_by != null` 的单元 = **候选池变小**。而你们自己测过（`measure_corpus_size_effect.py`）：
**语料每减 50 条，R@10 自动涨约 1.2pp**——这部分涨幅跟排序质量无关。

**必须同时报三个数**：

```
raw_gain    = supersede 配置的 R@10 − naive 的 R@10
size_effect = 用 measure_corpus_size_effect 的曲线，按"减少了 N 条语料"查出的机械涨幅
net_gain    = raw_gain − size_effect        ← 这才是排序质量的真实贡献
```

**只报 raw_gain 就是 v1.2.0→v1.3.0 那次"把题目变简单当成系统变好"的重演。**

#### ⚠️ 但要分清是哪一种主张——扣除只适用于其中一种

| 主张 | 用哪个数 | 为什么 |
|---|---|---|
| **机制贡献**（"supersede 过滤贡献了 X pp"） | `net_gain`（**扣**） | 要证明的是排序质量，机械涨幅必须剔除 |
| **系统性能**（"R@10 达到 X%，够不够 85%"） | `raw`（**不扣**） | 过滤失效知识是系统真的在做的事，过滤后的候选池就是系统实际面对的池子 |

系统级主张之所以能不扣，**前提是同时报出「有多少 gold 被误过滤」**（见 §2.2）——
那个数证明过滤器是在正确剔除失效知识，而不是在盲目缩池。**两个数缺一，这一档就只能报 net_gain。**

这个区分直接决定 85% 那条硬指标能不能过，**不要混着算**。

### 2.2 必须先检查 gold 文档有没有被 superseded 掉

如果某道题的标准答案本身被标记为 `superseded_by`，过滤后这道题**永远答不对**——那不是检索变差，是评测集与知识库状态不一致。

**跑之前先统计**：227 道题里有多少道的 `doc_id` 落在被过滤的集合里。若 > 0，单独列出来并在报告里说明处理方式（建议：这些题单独归一档报，不混进总数）。

### 2.3 必须验证每个开关**真的改变了输出**

本项目有前科：`meta.low_value` 是死数据、`is_low_value_workflow()` 定义了但零调用（R2-21 / R3-26）。

**每个配置跑完后，与 `naive` 的逐题 rank 做 diff**：

```
若某配置与 naive 的 227 题 rank 完全一致 → 这个开关是 no-op，先查为什么，不要写进报告
```

这条是硬性验收项，见 §五。

### 🔴 冻结守卫在两个阶段的行为**不一样**

`measure_recall.py:147-162` 会逐个校验 `knowledge_base_sha256` 里登记的每个语料文件哈希。

**阶段一（语料没变）**：重建索引不改语料文件本身，守卫应放行。
若报拒跑，说明语料被动过——**先查原因，不要 `--force`**。

**阶段二（语料涨到 ~119 条）**：哈希全变，**守卫必定拒跑。这不是 bug，是设计。**

必须正经走一次**重新冻结 v1.5.0**：

```
题目与 gold 一个不改（eval_set.jsonl 自身 sha256 保持 c0727f48…）
只更新 knowledge_base_sha256 里各语料文件的新哈希
冻结记录里写明理由：「7 天采集使语料从 86 增至 N 条，题目与标注未变，仅扩充语料重新登记」
```

> 🔴 **不要删 `knowledge_base_sha256` 字段、不要 `--force`、不要改题目去迁就。**
> 这些绕过路径在你们自己的评审报告里已经被当作漏洞写进去了（R2-11 一线），
> 评审时被翻出来是减分项，不是省事。重新冻结本身完全正当——**语料扩充是真实发生的事，
> 如实登记即可；掩盖它才是问题。**

## 七、预期

三种可能，都要如实报：

| 情形 | 怎么处理 |
|---|---|
| `all` 让 R@10 CI 下界过 85% | 硬指标达标，同时「关联检索策略」有了量化证据——**两个分一起拿到** |
| 有提升但下界仍不过 85% | 如实报不达标 + 给出提升幅度，按赛题「未达基础指标需明确优化方向」处理 |
| **几乎没提升甚至变差** | **照实报**。这也是有价值的结论——说明在 86 条语料这个规模上，重排的空间本来就小（top-10 已覆盖全库 11.6%）。**不要为了好看去调 `mmr_lambda` / `hybrid_alpha` 反复试到满意为止**，那是在评测集上过拟合 |

最后一栏是这次实验最需要守住的纪律。参数如果要调，**只允许在跑正式消融之前用少量样本定一次，定了就不再动**，并在报告里写明是怎么定的。
