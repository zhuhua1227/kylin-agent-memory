## 预期

| 指标 | 预期 | 理由 |
|---|---|---|
| 定位准确率 | 60%~85% | `forget_tasks.jsonl` 的 20 条指令措辞刻意与评测集对应问题不同（描述"这条记忆是关于什么的"，不抄评测题原文），不该是 100%；低于 50% 说明措辞写偏了——回头改指令措辞，不改判据。 |
| 遗忘生效率 | 100% | 过滤发生在按 k 截断之前（`memory_service.py` 里 `_retrieve_ablation` 先按 `k+f` 取候选、`apply_forget_filter` 再截到 k，见 `精准遗忘-实施方案.md` §2.3），理论上必达；不达 = bug。 |
| 副作用率 | 100% | 过滤只按 `stable_key` 精确匹配滤掉一个单元，不改其余单元的排序输入；不达 = bug。 |

任何一项不达预期的处理：**先查实现，不调判据、不删任务**。

## 一条容易误判的边界（跑分前先知道，避免把正常情况错当 bug）

"副作用率 100%"这条预期，前提是**被遗忘的单元本来就不在其余问题的
top-k 结果里**——它是对语料/embedding 分离度的经验期待，不是过滤器代码
本身能数学保证的性质。如果某个被遗忘的单元恰好也真实排进了某道无关题
的 top-k（哪怕概率很低），遗忘它就会正确地把该题的第 k 名换成下一名候选，
这条"变化"是过滤器工作正常的表现，不是漏洞。

区分方法：查 `score_forget.py` 输出里 `bystander_regressions` 列出的每一条，
看 `hits_before` 里是否真的含有该任务的 `target_doc_id`——
若含有，说明目标单元本来就排在这道无关题的候选里，属于上述正常情况；
若不含有，`hits_after` 却仍然变了，那才是需要排查的实现问题。

（这条边界是写 `记忆服务/遗忘评测/` 下配套的合成语料集成测试时实测碰到
的：6 条文档的极小语料里，几个不相关文档在候选池里排名相邻，遗忘其中
一个会牵连相邻名次——放大到 86 条真实语料 + 真实 embedding 的分离度后，
预期这种情况不会发生，但评测时应先按这条边界检查，而不是直接断言副作用率不是100%就是bug。）

```bash
    --forget-ledger 记忆服务/遗忘评测/forget_ledger_eval.jsonl

# 2. 前台跑评测（netctl 拦 setsid/exec/nohup&，只认前台 ssh + python3）
ssh device_c "cd ~/RAG/记忆服务/遗忘评测 && python3 forget_eval_runner.py"

# 3. 纯 Python 计分（不需要 embedding/device_c，任何机器可复现）
python3 记忆服务/遗忘评测/score_forget.py
```
