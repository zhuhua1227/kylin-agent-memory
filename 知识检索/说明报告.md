## 一、先纠正一个已作废的方向

原计划是「一条工具调用记录 = 一张知识卡片」，14,047 条切成 2~3 万块建索引。

**这个方向已被推翻**（详见《多源数据整合/说明报告.md》第十五点五节，
由用户提问「知识检索不是像 wiki 那样一问一答吗」触发）。原因：

> 单条工具调用是一个**事件**，不是知识。「第 8347 条：执行了 `ls -la`」检索出来
> 毫无用处，约等于 grep 命令历史。**知识产生于事件之间的关系。**

题目要的三类知识——**工作流程知识、历史案例、可复用模板**——都不是 wiki 式的
世界常识，而是「Agent 的操作性知识」，只能从事件的关系里挖：

| 知识类型 | 由什么构成 |
|---------|-----------|
| 历史案例 | 失败 → 修复 |
| 工作流程知识 | 用户意图 → 工具调用序列 → 结果 |
| 可复用模板 | 跨会话反复出现的流程 |

本报告记录的是**挖掘器**的设计与实测结果，而不是切块参数。

## 二、案例挖掘器：两次方法修正（外加一次头部统计的纠偏）

### 2.1 第一版估算（461）被证明基本是噪声

最初的启发式：「`is_error=true` 之后，同会话 5 步内出现同工具的成功调用」，
估算出 461 对。**人工抽查后发现这个数字站不住**：

实测 `[M-107]` 显示，5,174 条"出错"记录中：

| 类型 | 条数 | 占比 |
|------|------|------|
| **权限/审批拒绝** | 4,724 | **91.3%** |
| 真实技术故障 | 126 | 2.4% |
| 无法识别 | 324 | 6.3% |

**91.3% 的"出错"根本不是技术故障**，而是「用户拒绝了工具调用」「auto mode 分类器
拒绝了危险操作」——这类记录没有"怎么解决"这回事，压根不该进历史案例库。原估算
的 461 大量来自把这类记录也当成了"案例"。

真实的技术故障占比只有 **2.4%**。

### 2.2 三步过滤设计

**第一步**：从错误输出的**文本内容**判断是不是真故障，而不是只看 `is_error` 标记。
权限拒绝类文本特征（`user doesn't want to proceed`、`denied by`）与技术故障特征
（`command not found`、`Traceback`）截然不同，用规则区分。

**第二步**：修复判定看"后续调用的输出是否不再含同类错误信号"，而不是简单看
`is_error` 字段是否变成 `false`——标记成功的下一条调用完全可能只是另一次无关探索。

**第三步（人工抽样后新增）**：第一、二步做完，得到 231 个候选，抽样 25 条人工检查，
发现**约 60% 仍是"下一步无关操作"**而非真正的修复——例如「SSH 权限被拒」之后，
下一条同工具调用是「查 Windows 磁盘剩余空间」，这不是修复，是转向做别的事了。

真正的修复有一个共同特征：**修复命令与失败命令共享大量文本**（同一主机、同一
文件路径、同一段脚本），只改了关键的一小处。于是加一道相似度过滤：用**最长公共
子串占比**衡量两条命令的重叠程度，低于阈值（0.4，抽样校准得出）的判定为"无关
操作"，丢弃。

### 2.3 第一轮人工抽样：确认需要相似度过滤

对第一、二步产出的 231 个候选抽样 25 条人工检查，发现**约 60% 仍是"下一步无关
操作"**而非真正的修复——例如「SSH 权限被拒」之后，下一条同工具调用是「查
Windows 磁盘剩余空间」，这不是修复，是转向做别的事了。

真正的修复有一个共同特征：**修复命令与失败命令共享大量文本**（同一主机、同一
文件路径、同一段脚本），只改了关键的一小处。加一道相似度过滤：用**最长公共
子串占比**衡量两条命令的重叠程度，低于阈值（0.4，抽样校准得出）的判定为"无关
操作"，丢弃。加完后第二轮抽样（15条）精度回升到约 75~80%，得到 65 条案例。

### 2.4 头部统计被单日污染：一次通用异常日检测的加入

用户追问数据规模问题时，深挖了"91.3% 权限拒绝"这个统计的构成，发现：

> **5,174 条出错记录中，4,663 条（90.1%）来自 2026-07-27 这一天、仅 2 个会话**，
> 内容是一次批处理任务（日志显示"串行校验开始，待处理14个"），产出约 4,628 条
> 几乎逐字相同的拒绝文本（`The user doesn't want to proceed with this tool use...`）。

这**不是分类规则误判**——这些记录确实是真实的权限拒绝事件，`classify_error()`
判断正确。问题在于：**用包含这一天的聚合统计代表"典型情况"是误导的**。排除
07-27 后重新统计，"正常日子"的真实分布完全不同：

| | 含 07-27（污染的头部数字） | 排除 07-27（正常日子，本次测量时点） |
|---|---|---|
| 权限拒绝 | 91.3% | 18.8% |
| 技术故障 | 2.4% | 20.5%（是污染数字的 8.5 倍） |
| 无法识别 | 6.3% | 60.7%（新暴露的真实缺口） |

> ⚠️ **本表是发现问题那一刻的快照，已被 2.5 节的规则扩充取代**。规则扩充后
> （补 8 类真实信号 + infra 类）重跑，排除异常日的当前口径是
> **权限 21.8% / 技术故障 36.5% / 无法识别 40.8%**（136 / 228 / 255 ÷ 625，
> 对应 `claims.json` C-206）。
>
> 🔴 **第四轮独立复核：这三个数此前写的是「23.1% / 34.4% / 41.5%」，
> 与 `records/M-107.json` 三个都对不上**，而且上一版还在这里加了一句
> "已用 `reproduce_L1.py` 核对通过"——**那句话是假的**：核对器当时只做
> 全文裸子串匹配，`41.5%` 在本文另外两处出现过，随手就能命中，它从来
> 没有验证过这三个数印在**该印的位置**上。这正是 R4-02 要治的病，现已
> 改为按章节锚点定位比对。此处保留旧表不是疏漏，是想保留"发现
> 问题→加规则→数字再变"这条推理链的中间状态；如果只关心当前真实值，
> 认 2.5 节之后与 C-206 的数字，不要用本表。

正常日子里 60.7% 的错误连分类器都认不出类型，这比"权限噪声"更值得处理。
**没有把这次发现只写进文档了事，而是加了一个通用的异常日检测函数**
`detect_outlier_days()`——判据是"单日出错占比超过阈值 + 涉及会话数极少"，
不是硬编码排除某个日期。理由：数据集会持续增长，硬编码只能治一次，通用检测
能长期生效，且判据写在代码里，可自行核对阈值是否合理。现在每次跑 `mine_cases.py`
都会先报告有没有检测到异常日，并同时给出"含异常日"与"排除异常日"两组对比统计。

### 2.5 补规则、修 Bug：正常日子的真实信号

人工抽样 60.7% 的"未知"记录（20+20条两轮），确认了至少 8 类被规则遗漏的真实信号：
中文"找不到命令"变体（`找不到命令` vs 规则里只写了 `未找到命令`）、编码异常
（`UnicodeEncodeError`）、结构化错误（`InputValidationError`/`API Error 4xx`）、
小写/中文的语法错误措辞、`timed out`（区别于 `timeout`）、终端要求（TTY 相关）、
"请求了权限但未授权"（待批准状态）、以及全新的一类——**基础设施故障**
（`claude-sonnet-5[1m] is temporarily unavailable, so auto mode cannot determine
the safety...`，模型服务波动导致安全分类器判断不了操作安全性，既不是权限拒绝
也不是命令本身的技术问题，是平台瞬时故障，单列为第四类 `infra`，同样不产出案例）。

规则扩充后候选案例从 65 涨到 84。**但扩大规则后又暴露两个新问题**，都是人工
抽样（20条）发现的：

1. **第三步相似度过滤挡不住一类具体噪声**：`pscp`/`plink` 这类命令天然带很长的
   连接字符串前缀，传输**不同文件**、执行**不同远程命令**时，这段共享前缀本身
   就能让相似度冲到 0.4~0.6、通过第三步门槛，但实际内容完全不同。

   分析真实修复与这类噪声的最长公共子串**落在哪个位置**，发现清晰规律：
   真实修复（`python`→`python3`、`timeout 30`→`timeout 60`）的公共子串会
   **跨过改动点、延伸到命令结尾**；这类噪声的公共子串**从开头算起、但到不了结尾**
   （只有"模板头"相同）。据此加了**第四步过滤**（`is_shared_template_not_fix()`），
   对 84 条候选实测剔除 28 条，人工抽样确认这 28 条确实是"传输不同文件"类噪声。

2. **一条真实的分类规则缺口**：抽样中发现一条"Claude Code 安全护栏拦截"记录
   （`Blocked: sleep 60 followed by: ...`）被误判成了技术故障混进了案例——
   规则最初只写了 `is blocked`，漏掉了不含 "is" 的裸露写法 `Blocked: xxx`。
   已扩大匹配范围修复（简化为 `\bblocked\b` 词边界匹配，同时利用了已开启的
   `re.IGNORECASE`，不必再重复写大小写变体）。

### 2.7 第五个问题：生成评测集时才发现的挖掘算法漏洞

61 条案例本以为定型了。开始用 `generate_eval_candidates.py` 反向出题时，
人工核对生成的问句发现异常：三个不同 `doc_id`（45/46/47）生成的问题几乎
逐字相同（都是"用plink查qBittorrent.conf报错没有那个文件或目录怎么办"）。

查真实数据发现：这**不是出题环节的问题，是挖掘算法本身的漏洞**。真实情况是
用户连续三次用不同的 `grep` 关键词（`path`/`port`/`webui`）读同一个不存在的
配置文件、连续三次失败，随后**只有一次**真实的重试（换成 `tail -n 20`）。
而挖掘算法的逻辑是"每个失败独立地往后 5 步内找修复"，三次失败各自的向后
搜索都找到了同一个后续调用，于是产出了三条"案例"——实际只发生过一次真实的
解决尝试。

这个漏洞不只影响评测集（会造成"一题多解未标全"，检索到 46 却被判定"没
命中 45"，冤枉本来答对的系统），也污染知识库本身（同一条知识被重复收录
三次，检索结果被同质条目占满）。

实测：61 条案例里有 10 条（16.4%，分 4 组）受影响。**加了第五步**
（`deduplicate_shared_fix()`）：按 `(工具名, 修复动作)` 分组，同组只保留
`steps_between` 最小（离那次真实修复最近）的一条。去重后：**55 条**。

**这是「评测集生成倒逼数据质量修正」的一个实例**——不是先把知识库和评测集
分开做完再对齐，是让下游使用（出题）过程本身充当质量检验，发现问题就回头
修源头，而不是在下游将就。

### 2.8 最终产出

**代价与收获**：数量从最初粗估的 461，到第一轮修正后的 65，四步过滤后的 61，
到发现共享修复动作问题后最终定在 **55 条**。461 是噪声，55 条是经过五轮
（含一次由评测集生成倒逼）质量把关后的结果。**宁可少而真，不可多而假**：
一个建立在假案例或重复案例上的知识库，检索出来的"修复方法"可能压根不成立，
或者让评测出现虚假的歧义，比没有知识库更危险。

**整个过程写成代码而非一次性手工修正**——异常日检测、五步过滤规则都固化在
`mine_cases.py` 里，数据集更新后重跑会自动应用同样的质量把关，不需要每次
都重新人工排查一遍。

## 三、流程切分器：以用户意图为锚点

### 3.1 为什么需要意图锚点

一串工具调用本身只是流水账。只有知道"用户当时想做什么"，这串调用才升格为
"做某件事的方法"。意图锚点来自 `history.jsonl`（《多源数据整合》第二版新补的
数据源）。

### 3.2 关联方式与产出

同一 `session_id` 下，用户输入之后、下一条用户输入之前的那段工具调用，
就是这条意图对应的执行序列。

实测 `[M-108]`：

```
会话交集 18 个，交集内用户输入 69 条
挖出工作流程：54 条（空序列跳过 15，超长截断 1）
```

69 个候选中有 15 条是空序列（纯确认性发言，如"继续"、"好的"，后面没有
关联的工具调用），过滤后剩 54 条。这个过滤是诚实的——没有为了凑数字硬保留
无内容的流程。

> 📌 **2026-08-14 整链重跑后的数字**（上一版 20 / 74 / 59）。会话交集反而
> 略降（20→18），是因为 `history.jsonl` 这一路的时间跨度没跟着长——
> 用户输入仍停在 2026-08-03，而工具调用已到 08-14。**意图锚点的供给
> 成了瓶颈**：工具调用多了 45%，可关联的意图却少了。这条限制此前没被
> 注意到，现记入本节。

> 🔴 **第四轮独立复核 C-210：上面这个代码块此前印的是「会话交集 28 个 /
> 用户输入 120 条 / 工作流程 97 条（跳过 23，截断 4）」——五个数字全是旧的**，
> 与 `records/M-108.json` 的 20 / 74 / 59 / 15 / 1 无一相符。
>
> 它比一处普通的数字过期更糟：**它被排成代码块、前面写着"实测 `[M-108]`"，
> 看起来像是从脚本输出里粘过来的原文**，读者没有理由怀疑它。而实际它是
> 上一版语料（152 条那批）时期的数字，语料重做成 95 条之后没人回来改。
> 现已按记录改正。这类"伪装成实测输出的手抄内容"，正是 §四 那两张表
> 改成脚本生成的原因——**凡是长得像原始输出的，就该真的是原始输出**。

### 3.3 产出样例

```
用户想要：帮我把cemu塞尔达的存档备份，然后讲H盘下的塞尔达存档加载进游戏。
  执行了 11 步，使用工具：Bash, PowerShell（含出错重试）

用户想要：在当前目录下用Python实现一个LRU缓存类LRUCache(capacity)...
  执行了 15 步，使用工具：TaskCreate, TaskUpdate, Write, Bash, PowerShell, TaskList（含出错重试）
```

### 3.4 已知限制

实测 59 条工作流程里，24 条 intent 短于 20 字（如"继续"、"为什么画面这么模糊"
这类占位符），加上只有一步工具调用的情况，按 `is_low_value_workflow()` 的
判据合计 30 条信息量不足——虽然通过了"非空序列"这道过滤，但作为独立知识
单元的检索价值有限。不做删除——评判"意图是否有信息量"涉及主观判断，
且删除会影响评测集覆盖率（这些流程仍是合法的候选池干扰项）。

⚠️ **第二轮独立复核 R2-21 指出并已修复**：`is_low_value_workflow()` 此前
定义了但全项目零调用，判据本身没问题、只是没接进实际流程，是典型的死
代码。现已接线：`build_knowledge_index.py` 建索引时对每条 workflow 调用
该函数，判定结果写进 `DocStore` 的 `meta.low_value` 字段；
`search_knowledge.py` 检索时对标记为 `low_value` 的结果乘以 0.7 的降权
系数再重新排序（不是删除或过滤，仍可被检索到，只是同等相关度下排序
靠后）。0.7 是未精调的合理默认值，如实声明。

🔴 **第三轮独立复核 R3-26 指出：上面这个"已修复"其实一次都没生效过。**
R2-21 的做法是把判定结果**烘焙进建索引时的 meta**，指望下次重建索引时
生效；而重建索引依赖官方 KYSDK、只能在麒麟机上跑，一直没重建。结果是
生产索引的 meta 里压根没有 `low_value` 这个键，`meta.get("low_value")`
恒为 None，整段降权是 no-op——**和 R2-21 修复前的"函数定义了但零调用"
是同一个病，只是从"没人调用"变成了"调用了但输入永远为空"。**

现已改为**检索时实时判定**：建索引时本来就把整个流程单元原样存进了
`meta["raw"]`，检索时直接对它调 `is_low_value_workflow()`，成本可忽略。
这样做的关键好处不是"这次生效了"，而是**判据以后再改也立刻生效，不需要
重建索引，也就不存在"忘了重建"这回事**。存量索引里的 `low_value` 字段
保留但不再作为依据（仅当 meta 里没有 `raw` 时才回退去读）。

教训值得单独记一句：**能实时算的就别烘焙进产物**——烘焙会凭空制造一处
需要人记得去同步的落差，而人记不住。见《可复现性体系/代码产物落差登记
表.md》最后一节。`test_detectors.py` 用例 12 用"meta 里没有 `low_value`
键"的老格式条目做输入，把这条钉成了回归检查。

## 四、模板抽象器：从"决定不做"到独立评审倒逼重做（2026-08-05）

### 4.1 原判断：关键词聚类聚不出类，决定不做

原计划的第三类知识是「可复用模板」——跨会话反复出现的流程。**实测检验**：
对工作流程的意图文本做关键词聚类（存档/备份、部署/环境、网络/代理、
写代码/测试、排查/修复五个主题），结果 72% 未分类，进一步检查"归入同一
主题"的流程也不是真正重复的流程，只是话题相近的不同任务，据此决定本轮
不做模板抽象器。

### 4.2 独立评审指出的问题：结论本身没有可复现材料，且诊断错了病灶

外部审查（详见项目根目录《独立评审报告与整改清单.md》K-3）指出两点：

1. **这个决定本身没有可复现材料**——全项目找不到聚类脚本、没有测量记录、
   没有中间产物，是全项目唯一一处"结论无脚本"的地方，恰好还是一处"放弃
   某项赛题要求"的决定，与其他每一步都有 stats 计数 + `claims.json` 校验
   的做法形成刺眼反差。
2. **更关键的是：模板信号其实存在，只是找错了地方**。关键词聚类作用于
   `intent` 意图文本（自然语言，表述发散，聚不出类完全正常）；但"可复用"
   这个属性体现在**操作序列的重复**上，不在**措辞的重复**上——同一类问题
   被用相同的工具切换/操作序列解决过多次，纵使每次的意图描述完全不同。

### 4.3 重做：按操作序列签名聚合（`mine_templates.py`）

两类信号来源：

- **案例的"失败工具→修复工具"跳转**：按 `(失败工具, 修复工具, 错误类别)`
  签名聚合案例，跨会话出现 ≥2 次即产出模板（如"遇到 Bash 报technical类
  错误时，可以换用 plink"）。
- **流程的工具序列**：按去重后的有序工具名元组聚合工作流程，跨会话出现
  ≥2 次即产出模板。

```
案例池 27 条，流程池 59 条
工具切换类模板：5 条（支持度≥2）
工具序列类模板：4 条（支持度≥2）
模板总计：9 条
```

**确有信号，不是交白卷**——原判断"72%无法归类"的病灶诊断是对的（意图
关键词聚类确实聚不出类），但结论"这个知识类型做不了"是错的，只是换了
聚合维度就产出了 9 条真实模板，已并入索引作为第三类知识单元。

### 4.4 诚实的局限

- 支持度阈值取 2（跨会话出现≥2次），是经验值，未做敏感性分析——阈值
  提高会减少模板数、提高单条模板的可信度，两者的权衡未量化。
- `command_text()` 用"命令首词"近似代表"用了哪个工具"（如 PowerShell 命令
  以 `&` 开头时首词就是 `&`，语义上不是有效的工具标识），产出的部分模板
  质量不高（例："遇到 PowerShell 报unknown类错误时，可以换用 &"）——
  如实记录这个已知瑕疵，未做进一步清洗，留给后续迭代。
- 案例池与流程池规模都不大（27/59），模板的统计显著性有限，标注为
  "轻量级信号"更准确，不宜过度强调其可信度。

8. **冷启动模拟（第一点五节）用的是同一个用户的数据切片**，不是真正意义上的
   "另一个新用户"。若要验证方案在不同用户身上都成立，需要一份真正独立的
   第二用户数据（如队友提供的历史记录）作真实场景应用案例。

## 十、2026-08-05 独立评审后的挖掘算法修正（K-1/K-2）

除第四节记录的 K-3（模板抽象器重做）外，独立评审还在案例挖掘器和流程渲染
里各发现一处真实缺陷，均已修复。

### 10.1 K-1：假案例的两个根因

人工逐条核对 55 条案例（旧版本）时，独立审查发现 **21.8%（12条）是可证伪
的假案例**，两个独立根因：

**根因一（约11%）**：`mine_cases.py` 做了相似度过滤和模板前缀过滤，唯独
没检查"修复命令与失败命令完全相同"这种退化情况——两个字符串完全相同时，
相似度=1.0 远超阈值，最长公共子串就是整串、必然"跨过改动点延伸到结尾"，
两道过滤的设计前提都是"两条命令有差异"，同一条命令是它们共同的盲区。

**根因二（约11%）**：修复判定标准是"下一步输出不含技术故障关键词"，而
正常日子里 41.5% 的错误连分类器都认不出类型（见 2.5 节）——"不是
technical" 这个条件同时包含了"真的修复成功"和"分类器认不出的未知错误"

**修复**（详见 `mine_cases.py` 的 `mine()` 函数）：
1. 新增第3.5步：`failed_cmd.strip() == fixed_cmd.strip()` 时直接剔除

### 10.1.1 K-1 的探查动词过滤被命令包装完全绕过（第二轮独立复核 R2-01）

上面①②两个根因确实堵住了，但复核指出**第③个未被覆盖的根因**：探查动词表
只检查 `fixed_cmd.split()[0]`，而本数据集里绝大多数命令是包装形式——
`plink -ssh host "echo pw | sudo -S ls -la /mnt/seed"` 或
`& D:\putty\plink.exe ...`，首词恒为 `plink`/`&`，永远命中不了表——探查
动词表加了却没剥壳，实测假案例率因此只从 21.8% 动到 22.2%，几乎没有
改善。复核员还额外发现一类未覆盖的假案例：pscp 报非零退出码但输出显示
`| 100%` 传输已完成，"传输失败"这个前提是假的，"修复"实为工作流下一步
（执行刚上传的脚本），按此标准可证伪率达 48.1%（13/27）。

**第一轮修复**（`mine_cases.py`）：
1. 新增 `inner_verb()`：剥离远程执行/提权/引号包装（`WRAPPER_TOKENS` 覆盖
   plink/pscp/ssh/sudo/bash 等），取真正被执行命令的首词，探查动词表改用
   这个剥壳后的结果做判断，同时补齐 `df`/`lsblk` 两个实测新发现的探查
   动词，并新增 `docker port/ps/logs/inspect` 等"动词+子命令"组合判断
   （不能把 `docker` 整体归为探查动词，`docker run` 是真实操作）
2. 新增 `is_spurious_pscp_failure()`：识别 pscp 报错但输出含 100% 传输
   完成标记的情况，在配对"修复"之前就直接排除，不进入候选池

案例数从 27 降到 25。

**第二、三轮修复（给上面这个修复本身写变异测试时，连续两次抓到自己的
bug——这是本轮整改里最值得记住的一段过程）**：

按 `test_detectors.py` 的一贯做法，给 `inner_verb()` 补变异测试，
第一条**当场跑红**——`inner_verb('plink -ssh host "echo pw | sudo -S ls
-la /mnt/data"')` 返回的是 `"pw"`（密码本身），不是 `"ls"`。根因：`echo
<密码> | sudo -S <真命令>` 这个习语里，`echo` 本身被正确跳过了，但它的
参数（密码）没被识别成"需要跳过的值"，落进"取第一个非选项、非包装
token"的判断里被误当成动词返回。**修复**：改用管道最后一段（真命令恒在
`echo 密码 | sudo -S 真命令` 的最后一段）+ 新增 `VALUE_FLAGS`（`echo`/
`-p`/`-pw`/`-i` 等，其后紧跟的 token 一并跳过）。这个 bug 意味着大量
`echo 密码 | sudo -S ls/df/...` 形态的探查案例此前仍未被拦住（密码字符串
显然不在 PROBE_ONLY 表里），而这恰恰是本数据集里探查动词最常出现的
包装形式，直接抵消了第一轮修复的大半效果——案例数从 25 再降到 22。

给 `mine_templates.py`（R2-22，见 10.3 节）写正例测试（"真实的跨会话
工具切换应该仍能被识别，不能矫枉过正到永远不产出"）时，**又跑红一次**：
`inner_verb("mysql -e 'select 1'")` 返回的是 `"select"`，不是
`"mysql"`——引号提取规则本意是抓"整体被包住的远程命令"，但对
`mysql -e 'select 1'` 这种普通命令，引号只是包住了一句 SQL 参数，
被误当成了"整条命令"来处理。**修复**：只有当引号前面的文本里出现过
`WRAPPER_TOKENS` 里的词（plink/ssh/sudo/bash -c 等）时才做引号提取，
否则按原始命令直接处理。修复后案例数从 22 再降到 **20**。

两次都是"先写覆盖修复的变异测试，测试当场发现修复本身有 bug"——不是
凭空发现的，是本项目一贯要求的"每条修复配一条能失败的检测器"这个流程
本身起的作用，过程留档比结论更有说服力。

**独立验证**：对最终产出的 20 条逐一核对复核员点名的所有问题模式（内层
动词为 ls/df/lsblk 探查、`docker port/ps/logs/inspect` 探查子命令、或
pscp 虚假失败），**复核指出的具体反例全部排除**。⚠️ 但验证过程中**另外
发现 1 条本轮之前未被任何清单点名的新案例**：`docker exec CONTAINER cat
...log`（失败）→`docker exec CONTAINER netstat -tulnp`（"修复"）——两者
共享 `docker exec CONTAINER` 前缀，但容器内实际执行的命令完全不同，本质
与 `docker port/ps` 这类探查是同一类问题，只是套了一层 `docker exec`，
现有的 PROBE_SUBCOMMANDS 判断没有覆盖"进容器执行任意命令"这一层包装。
如实记录为已知残留（1/20 = 5%，从整改前的 22.2%/48.1% 已大幅下降但
不是零），留作下一版本的修复项，不藏起来凑"全部清零"的说法。

⚠️ **本次未重新生成 `cases.jsonl` / 重建索引 / 重新冻结评测集**：案例数
20≠27 会连锁改变全部知识单元的 `doc_id` 编号（工作流程与模板紧跟案例
之后编号），进而使已冻结的 v1.3.0 评测集（`eval_set.jsonl`）的 doc_id
全部失效，需要整条链路（B2 建索引 → C 出题冻结 → F 召回率/CI/语料规模
对照实验）重新走一遍，工作量远超一次代码缺陷修复的合理范围。这里做的
是**证明修复本身有效**（已知反例全部排除，另有 1 条新发现的残留如实
记录在上），部署到生产索引留作后续版本（v1.4.0）的工作，不在本轮报告
的召回率/CI 数字里体现，如实声明这个已知的代码-部署落差，而不是不吭声。

### 10.2 K-2：工作流程索引文本丢失操作细节

`render_workflow()` 原实现只保留意图文本 + 去重后的工具名列表，把
`tool_sequence` 里每一步的 `input_summary`（具体做了什么）全部丢弃。
实测渲染文本平均只有 78 字，其中 42.5% 是用户原话——检索命中它，Agent
拿到的信息只是"这事要用 Bash，两步"，没有任何可复用的操作性知识。

这也连带影响了召回率评测的可信度：workflow 类 R@1 此前测出 74.8%、
远高于 case 类的 49.0%，根因正是评测集问句是对 `source_rendered` 的
改写而 rendered 主体就是用户原话——测的是"能否把改写句匹配回原句"，
不是"能否检索到有用流程"，分数虚高恰恰因为任务被简化了。

**修复**：`render_workflow()`（`build_knowledge_index.py` 与
`mine_workflows.py` 的预览函数同步修改）改为逐步展示每一步的工具名与

这种信息量很低的渲染。修复后重新生成的评测集、重新测得的召回率数字见

workflow R@1 74.8% vs case R@1 49.0%（差 25.8pp，且高度可疑，因为差距
根因正是"渲染文本=用户原话"这个测量缺陷本身）；修复后 workflow R@1
71.0% vs case R@1 62.3%（差 8.7pp）。残余差距不再是测量假象，报告分析
认为是 case 类检索文本本身包含大段失败命令与报错文本、技术细节更密集、
语义边界更模糊所致，而不是渲染丢字导致的信息量差异。

### 10.4 模板挖掘的最小信息量门槛（第三轮独立复核 R3-25）

R2-22 的三个 bug 修完后重跑，产出 4 条模板——复核逐条核对后指出：
**这 4 条 100% 是零复用价值的纯工具名对**（`Bash→PowerShell`、`Bash→Read`、
`Write→Bash`、`Bash→Write`），`example_intent` 分别是"好了吗""鱿鱼游戏
有多少集"。R2-22 原本就抱怨过这一类，那一条没处理，**修完 bug 反而只剩
这类**。

根因：序列签名只由**工具名**构成，而 Bash/Write/Read 是通用工具，
"先 Bash 再 Write"这种组合在任何任务里都会出现——它描述的是工具的普遍
用法，不是"可复用的操作套路"。支持度门槛（跨会话≥2）挡不住这种
"到处都成立"的组合，因为它确实到处都成立。

**已加两道最小信息量门槛**（`_has_reusable_signal()`）：
1. **意图必须讲清在解决什么问题**——`example_intent` 少于 12 字直接丢弃。
   一条模板如果连"这套操作是干嘛的"都说不出来，检索到它也没有用。
   顺带把 `example_intent` 从"永远取 items[0]"改为取最长的那条（旧写法
   恰好取到"好了吗"这种占位符）。
2. **序列不能全由通用工具构成**——至少要出现一个有领域含义的工具。

重跑后：工具切换类 1 条、工具序列类 0 条，**合计 1 条**。

⚠️ **如实说明**：这个数字很难看，但它是诚实的——当前 95 条语料规模下，
真正"跨会话重复出现、且讲得清自己在解决什么问题"的操作套路，实测就只有
一条（`Bash 报 technical 类错误 → 换用 curl`）。此前的 9 条/4 条都是把
"通用工具的普遍组合"当成了套路。**宁可产出 1 条真的，也不要 9 条看起来
丰富、检索出来毫无用处的。** 模板类知识需要更大的数据规模才能真正成立，
这一点已写进已知限制。

### 10.3 mine_templates.py 三个 bug（第二轮独立复核 R2-22）

`mine_case_templates()`（工具切换类模板）有三个真实 bug，均已修复：

1. **同一个包装首词盲区又出现了一次**：判断"修复用了哪个命令"此前用
   `fixed_cmd.split()[0]`，与 `mine_cases.py` 在 K-1/R2-01 里踩过的
   完全是同一个坑——本数据集命令多为 plink/pscp 包装形式，首词恒为
   plink/&，取不到真正被执行的命令。改用 R2-01 新增的 `inner_verb()`
   （同一个函数，两处 import，不再各写一份）。
2. **`str == list` 恒假比较**：判断"失败命令和修复命令是不是同一个
   命令"这道守卫写的是 `fixed_word == command_text(...).split()[0:1]`
   ——左边是字符串，右边 `[0:1]` 切片出来的是列表，两者永不相等，这道
   守卫从未生效过。改成两边都用 `inner_verb()` 取字符串再比较。
3. **会话数与出现次数混淆**：文件头声明"跨会话出现 ≥2 次"，但
   `mine_case_templates()`/`mine_workflow_templates()` 两处的支持度
   门槛都写的是 `len(items) < MIN_SUPPORT`（出现次数），不是
   `len(sessions) < MIN_SUPPORT`（会话数）——同一个会话里连续出现两次
   也能通过门槛，与"跨会话重复=可信的可复用经验"这个设计初衷不符。
   两处均改为对会话数判断。

**修复效果**（对已部署的 `cases.jsonl`/`workflows.jsonl` 做隔离验证，
不影响已部署的 `templates.jsonl`，见下方部署说明）：工具切换类模板从

不再依赖"运气"。

### R-7 展开：一次真实的 select() 陷阱

最初实现是"每次 `readline()` 前先 `select()` 探测 OS 层管道是否有数据"。
接入真实的768维向量测试后，**SEARCH 请求必现超时**——但把 `select()` 去掉、
换成纯阻塞 `readline()`，同一份请求序列 0 秒内正常返回。

**根因**：`select()` 只能看见 OS 内核层的管道状态，看不见 Python 自己的
用户态缓冲区。`ve_serverd` 一次 `flush()` 会把"命中条数行 + N条命中行"
一起写出，Python 底层第一次 `read()` 系统调用往往会把这一整块数据都读进
自己的缓冲区（不止一行）；这之后如果再对着同一个 fd 做 `select()`，会
因为"OS 层确实没有新数据了"而误判超时——即使 `readline()` 本可以立刻从
Python 自己的缓冲区里拿到下一行。这是 `select()` 与带缓冲的读取器组合时
的经典陷阱，纸面设计和单元测试都不会暴露，只有接上真实多行响应的请求
才会必现。

**修复**：不用 Python 内置的缓冲 `TextIOWrapper`，改成二进制模式（`bufsize=0`）
+ 自己维护一个字节缓冲区：每次读取前先看缓冲区里有没有现成的整行（不碰
`select`、不触发系统调用），没有才 `select()` 探测+`os.read()`补充数据。
`vector_store.py` 的 `KylinEngineStore` 与 `embedding_client.py` 的
`EmbeddingClient` 都改了。修复后：3条真实向量的基本读写检索、
`count==top_k` 边界（R-15验证）、真实95条知识库端到端检索三项测试全部
通过，`emb_serverd` 的9位精度输出（R-10）也一并验证有效。

**边界说明**：超时后只明确报错（`TimeoutError`/`EmbeddingServerError`），
不做自动重启子进程——自动重启需要重建连接状态（集合是否已建好、数据是否
完整写入），贸然重启可能把"部分写入"伪装成"看起来正常"，风险高于收益，
出错后交给调用方决定。`select()` 只在类POSIX系统上对管道有效，两个
serverd都是Linux-only二进制，这个前提天然成立，不需要跨平台兼容。

**验证方式**：全部改动上传远程麒麟机后原地重新编译（`g++`/`gcc`，均EXIT=0）
并替换二进制，三轮功能测试（玩具规模、真实768维、R-15边界）与一次真实
95条知识库端到端检索全部通过；本地 `reproduce_L1.py` 与 `test_detectors.py`
在改动前后核对结果不变（这批改动不涉及L1的Python逻辑，只是I/O健壮性）。
