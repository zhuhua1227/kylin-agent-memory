# kylin-agent-memory

银河麒麟 V11 上的端侧 OS Agent 记忆系统。它从 Agent 的操作日志里提取用户偏好和可复用知识，处理新旧知识冲突，并支持用自然语言指令遗忘某条记忆。

仓库附带一套评测：145 条数字主张都登记在 `claims.json` 里，其中 115 条在任何装了 Python 和 numpy 的机器上都能重算，不需要麒麟环境。

项目源自 2026 年度中国青年科技创新擂台赛 XA-202612 赛题「OS Agent 记忆优化及高效应用研究」（麒麟软件有限公司命题）。

---

## 要解决的问题

一个 Agent 在同一台电脑上用久了，日志里会积累很多有用的信息：用户习惯用哪个命令、某个报错上次是怎么修好的、某项配置后来改成了什么。要把这些变成能用的记忆，有三个难点：

1. **来源杂。** 信息散在工具调用结果、用户手动改的配置、会话记录里，格式和质量都不统一，没法直接拿去检索。
2. **知识会过期。** 上周的修法这周被推翻了。直接覆盖，会丢掉"什么情况下旧方法还能用"；不覆盖，又会把过期答案检索出来。
3. **效果难证明。** 加了记忆以后到底有没有变好？人工标注成本高，而且标注的人往往就是开发的人。

## 做法

### 知识：从事件之间的关系里挖

单条工具调用不入库。系统找的是跨会话反复出现的模式，归成三类：

| 类型 | 条数 | 例子 |
|---|---|---|
| 历史案例 case | 31 | 某个报错 → 排查过程 → 最终修法 |
| 工作流程 workflow | 54 | 部署某服务的固定步骤序列 |
| 可复用模板 template | 1 | 反复出现、只改参数的命令或配置 |

一共 86 条知识单元。

### 偏好：用之后的真实行为当标准答案

偏好提取用确定性规则，不调用 LLM。某个情境下的某种做法，要同时满足三个条件才算偏好：出现至少 8 次、占比不低于 65%、分布在至少 2 个会话里。

评测时按时间把数据切成两段：用前期数据提取偏好，再去预测留出期里用户实际是怎么做的。标准答案直接取留出期的行为记录，不需要人工标注。切分以整个会话为单位，因为 Claude Code 的会话可以跨天恢复（数据里最长的一个跨了 23 天），按时间戳硬切会让同一个会话的前半段去预测后半段。

### 冲突：旧知识不删，标上适用边界

| 类型 | 定义 | 处理 |
|---|---|---|
| T1 事实过期 | 同一事实槽位，值变了 | 新值生效，旧值标注 `as_of` |
| T2 方法推翻 | 同一问题，后来的解法否定了之前的 | 新方法生效，旧方法保留适用条件 |
| T3 环境变更 | 环境标识变了，一批知识同时失效 | 该环境下的知识批量标记为待重验 |
| T4 局部修订 | 同一文件的某段被改写 | 以段落为粒度，新的生效 |

检索默认返回最新版本，旧版本保留下来，可以按 `stable_key` 回溯。

判定分三层，三层的代码路径彼此隔离：

```
结构层  mine_conflicts.py               确定性规则，产出候选对
语义层  LLM 通读候选池                    只排序、解释，不产出标准答案
裁决层  review_and_freeze_conflicts.py  人工裁决后冻结为 ground truth
```

被测的裁决函数 `adjudicate()` 不参与生成自己的标准答案。冲突规则在留出集数据产生之前就已冻结。

### 检索

- 向量化：麒麟 KYSDK Embedding（768 维）
- 向量存储：`kylin-ai-vector-engine`（Milvus Lite 的麒麟分支）。另实现了一个接口等价的 numpy 后端，用 `create_store("kylin")` / `create_store("numpy")` 切换
- 向量索引和原文分开存：向量库只存 `doc_id → 向量`，原文由 `DocStore` 管理

在朴素向量检索之上消融了四条策略：知识类型质心软先验、MMR 多样性重排、BM25 混合、被推翻知识降权。

### 遗忘

`/forget <描述>` 会先把描述当作查询，回显匹配到的候选记忆，用户确认后才写入遗忘账本；检索时按账本过滤，`/unforget` 可以撤销。整个过程不删向量，也不改已冻结的知识单元。

### 记忆服务

`记忆服务/memory_service.py` 是一个只用标准库写的 HTTP 服务，监听 `127.0.0.1:8077`：

```
POST /retrieve   {"query": "任务描述", "k": 5}
→ {"units": [{"doc_id": 23, "type": "case", "text": "…", "score": 0.83}, …],
   "config": "all", "elapsed_ms": 74.3}
```

`rag-memory.ts` 是给 [pi coding agent](https://github.com/badlogic/pi-mono) 用的钩子，Agent 每次行动前调用这个服务，把相关记忆注入上下文。

## 结果

评测集为 227 道题，冻结后未再改动；语料是上面那 86 条知识单元。比例类指标都附 Wilson 95% 置信区间下界，"门槛"一列是赛题给的要求。

| 指标 | 实测 | 95% CI 下界 | 门槛 |
|---|---|---|---|
| 知识检索 recall@10 | 86.3% | 81.3% | ≥85% |
| 知识检索 recall@1，最难一档 | 32.9%（纯词面基线 2.6%） | | |
| 偏好提取：操作习惯类 | 90.0%（比全局众数基线高 69.5 pp） | 88.3% | ≥85% |
| 偏好提取：输出风格类 | 68.2%（比基线无提升） | 53.4% | ≥85% |
| 冲突判定：全部标注，n=96 | 94.8% | 88.4% | ≥88% |
| 冲突判定：只算留出集，n=60 | 93.3% | 84.1% | ≥88% |
| 检索响应 P95 | 111.70 ms | | ≤500 ms |

遗忘（20 条遗忘指令）：

| 指标 | 实测 |
|---|---|
| 定位准确率（指令直接命中目标知识单元） | 55.0%（11/20） |
| 遗忘生效率（相关题重跑后目标不再出现在 top-10） | 100%（58/58） |
| 误伤（无关题的检索结果出现异常变化） | 0 / 4482 |

### 对照实验一：只换生成模型

检索管线、题目和 prompt 全部固定，只换生成模型。"不调记忆"组是真的不调用记忆服务，并不是删掉一段提示词。共 13 题，用严格子串判分，不用 LLM 当裁判。

| 生成模型 | 不调记忆 | 调记忆 | Δ |
|---|---|---|---|
| Qwen3.5-2B Q4_K_M | 2/13 | 5/13 | +3 |
| Qwen3.5-4B Q4_K_M | 3/13 | 7/13 | +4 |
| Qwen3.5-9B Q4_K_M | 2/13 | 7/13 | +5 |
| Gemini-3.1-Pro（云端参照） | 3/13 | 8/13 | +5 |

换成另外两种判分口径，四档模型的增益同样都为正（+3 到 +7）。"增益随模型变大而增加""9B 追平云端"这两条，换口径或去掉单道题后就不成立了。n=13 太小，不做显著性检验。

### 对照实验二：只换 embedding

语料、题目和检索代码都固定，只把 KYSDK Embedding 换成 BGE-M3（只用 dense 向量），比较朴素向量检索：

| | KYSDK Embedding | BGE-M3 |
|---|---|---|
| R@1 | 52.42% | 50.66% |
| R@3 | 76.21% | 70.04% |
| R@5 | 82.38% | 77.09% |
| R@10 | 86.34% | 87.22% |

R@10 上两者只差 2 题。McNemar 配对统计：只有 KYSDK 命中的 14 题，只有 BGE-M3 命中的 16 题。

### 其他实测结论

- 在 86 条的规模下，官方向量引擎的内存占用是 numpy 后端的 2.4 倍。
- 把 embedding 做成常驻服务，延迟几乎没有降低，真正的瓶颈是文本长度。
- 四条关联检索策略在当前语料规模下，都没有统计上能分辨出来的正收益。
- 对语料做子采样后发现，每多 50 条语料，recall@10 大约降 1.2 pp。按这个趋势外推，单靠扩充语料不能让 CI 下界达到 85%。

## 复现

### L1：任何机器都能跑

```bash
git clone https://github.com/zhuhua1227/kylin-agent-memory.git
cd kylin-agent-memory
pip install numpy
python 可复现性体系/reproduce_L1.py
```

用的是固化在 `可复现性体系/vectors/` 下的向量，不需要麒麟环境和 KYSDK。在 Windows + Python 3.14 上跑一次约 2 分钟。

预期结果：145 条主张中 143 条通过，2 条不符：

- **C-255**：recall@10 的 CI 下界 81.3% 低于 85%
- **C-304**：冲突判定留出集单独口径的 CI 下界 84.1% 低于 88%

除这两条外，任何一条不符都说明代码或数据跟报告对不上。延迟类的主张受机器负载影响。

另外，M-211（模型消融）、M-212（BGE-M3 对照）、M-213（遗忘）三项实验的主张数字会被核对，但 `reproduce_L1.py` 还不会从头重算它们。BGE-M3 对照可以按 `BGE-M3对照/复现.md` 单独重跑。

### L2：需要银河麒麟 V11

共 30 条主张，涉及 KYSDK 现场生成向量和官方向量引擎的实测。环境部署步骤见 `证明向量维度/前置步骤-不可变系统解锁与KYSDK部署命令手册.md`。

## 局限

- 所有数据都来自同一个用户的真实使用记录，知识单元只有 86 条。
- 原始日志含个人信息，不公开。仓库里只有脱敏后的知识单元、评测集和固化向量，所以第三方没法从原始日志重新挖一遍。
- 冲突判定的开发集（36 对）由 AI 助手逐条阅读原始证据后写出裁决；留出集（60 对）由作者一人盲测标注，5 道重复题前后一致（5/5），没有第二位标注者。
- 输出风格类偏好目前只挖到一个触发情境，所以和基线在数学上等价。
- 短、中、长期记忆之间的流转没有单独评测。
- BGE-M3 对照只做了朴素向量检索这一档。
- 评测集「先冻结、后跑模型」的时间顺序靠 GitHub issue 评论的服务端时间戳做外部锚定，但锚定所在的仓库目前是私有的，第三方暂时无法核验，详见 `评测集/说明报告.md`。
