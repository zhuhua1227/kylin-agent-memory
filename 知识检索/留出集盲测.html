## 判断：netctl 授权识别脚本 vs 可执行文件路径（2026-09-01）

- **判定：基于可执行文件路径（实际运行的二进制）识别，非进程祖先链识别脚本。**
- 依据来源：
  1. `netctl.xml` / `kysec_netctl --list applist`：15 个条目全为**原生二进制** path（curl/cups_backend_*/kylin-activation/kaiming-system-dbus/boxadm-daemon），**0 个 .sh/.py 脚本条目**；
  2. 授权记录单一文件路径：`netctl auth: … filepath=/data/…/bin/claude`、`…/kaiming-system-dbus`，auth_result=1 —— 路径即发起连接的可执行文件；且 `claude` 为 **ELF 64-bit 可执行**（file 判定），非脚本；
  3. `t_kid_netctl` 表字段：仅 `ID/KID/PrivilegeType/Path/Reserver_1..3`，以 **Path** 为主键 → 按可执行路径匹配，无 ppid/祖先链字段参与授权判定。
- 含义：网络授权以"发起网络操作的那个二进制可执行文件的 path（+hash）"对照白名单 allow/forbid；脚本本身不按祖先链映射到顶层启动者判定，而是落到实际执行网络调用的二进制。
- 边界（诚实说明）：以上基于磁盘白名单、授权日志、DB 字段判定；ksaf 内核态 `netctl` 处理器的更深逻辑未逆编，不能完全排除低层逐进程校验里含辅助判断。<br/>
  来源：`/etc/kysec/netctl/netctl.xml`、`t_kid_netctl`(whlist.db)、`/var/log/kysec.log` netctl auth 记录。

## 8. Thinking: bind-mount vs overlay investigation (step 231)
- **Common**: both use /proc/mountinfo as the source of truth, decompose a mount into source/root/options → verify backing exists, cross-check with multiple toolsm (findmnt/lsblk/stat/python), and record errors honestly; both address to Panshi/OSTree design.
- **Difference**: overlay = **vertical stacking** on ONE target (which layer is effective; identity by inode/stat; per-layer ro/rw/depth). Bind = **horizontal multi-mounts** of one device; the key is mountinfo **field-4 (root subtree)** to re-map a device's mounts back to `/data/home→/home`, `/data/root→/root`.
- Same under hood (read mountinfo + resolve), different geometry (stacking vs aliasing) — that's the crux.

```
→ cat: /mnt/nonexistent-mount/data/report.txt: 没有那个文件或目录   (No such file or directory, ENOENT), exit 1
```
- The missing component is a directory-level miss (not a "not a directory" `ENOTDIR`): path resolution fails on the nonexistent middle directory → **ENOENT**.
- `/mnt` here is a symlink → `/var/mnt` (empty); there is no custom mount point under it, so the sub-path genuinely doesn't exist.
- General rule recorded: a dangling fstab/mount reference (a mount point or its parent dir that isn't mounted/created) surfaces as **ENOENT**, not a mount-specific error; the robustness: `mount` would also fail on an Nonexistent mountpoint with a "mountpoint does not exist" style message during fstab processing. This is why `/etc/fstab` entries must have a pre-existing mountpoint directory.
