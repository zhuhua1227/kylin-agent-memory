## 〇、v1.0.0 → v1.1.0：为什么整批重新生成，不是修修补补

`mine_workflows.py` 有一个 `set()` 遍历顺序非确定性 bug（同一份输入数据，
两次运行本脚本产出的 `workflows.jsonl` 行序可能不同——Python 的 set 遍历
受进程级哈希随机化影响）。这个 bug 是**实测召回率时才暴露的**：workflow
类召回率测出来接近 0%，人工核对发现评测集记的 `doc_id=55` 对应"备份塞尔达
存档"，但当时建索引用的 `workflows.jsonl` 里 `doc_id=55` 是完全不相关的
另一条流程——两次独立运行（生成评测集时一次、建索引时另一次）的行序不一样，
doc_id 编号全部错位。完整定位过程见《可复现性体系/勘误与修正记录.md》第七节。

修复后（改用确定性的 list 遍历，`workflows.jsonl` 内容不变，只是行序固定），
`workflows.jsonl` 的 doc_id 55~151 整体重新分配。`cases.jsonl` 的 doc_id
0~54 不受影响（`mine_cases.py` 从未有过这个 bug，用的是 dict 插入序，本身
就是确定性的）。

评测集据此**整批重新生成**（不是挑几条改）：Gemini 出题本身也不是确定性的
（同一批知识单元重新调用一次，具体问法会变），所以不能"旧 doc_id 换个号
但配对关系照抄"，必须从近似重复扫描到人工核查全部重新走一遍。方法论没变，
具体决定不能照搬——详见 `review_and_freeze.py` 顶部说明与下面第三节。

### 〇.5 v1.1.0 → v1.2.0：冻结机制本身还有一个缺口

v1.1.0 冻结时只对 `eval_set.jsonl`（题目文件）算了 SHA256，**没有对
`cases.jsonl`/`workflows.jsonl`（语料文件）算哈希**。而 `doc_id` 是语料的
**行号**，是相对编号——独立审查 E-3 指出：这意味着语料只要再重新生成一次、
行序再变一次，全部 doc_id 会**静默失效**，而 `eval_set.jsonl` 自身的哈希
校验照样通过（因为它没变），**测量前完全没有机制能发现这一点**。这正是
v1.0.0 整批作废的根本原因（`mine_workflows.py` 的 doc_id 非确定性错位），
返工后却没有把这个教训真正闭环——只是手动确认了一次语料没变，没有做成
可自动核对的机制。

**修复**：`review_and_freeze.py` 冻结时新增 `knowledge_base_sha256` /
`knowledge_base_lines` 字段（对 `cases.jsonl`/`workflows.jsonl` 分别算
哈希与行数）；`measure_recall.py` 与 `可复现性体系/measure_L2.py` 的
M-207 在测量前都会先核对当前语料哈希与冻结时记录的是否一致，**不一致
直接拒测**而不是跑出一份看似正常、实则全盘失真的结果。已用变异测试验证：
故意改动 `workflows.jsonl` 一个字节后重跑，脚本正确拒绝并报出期望/实际
哈希前16位；恢复原文件后正常通过。

**第二轮独立复核 R2-11 指出并已修复：这道守卫本身有三处绕过口**——
主路径（改语料）确实拒跑，但复核员另外做的三个绕过实验全部成功：
①直接篡改 `eval_set.jsonl`（题目文件）本身——不拒跑，因为原实现只
校验知识库语料哈希，从未校验题目文件自己的哈希；②删掉冻结元信息的
`knowledge_base_sha256` 字段——原实现只打印一行警告后继续跑，是降级
放行不是拒绝；③整个删掉 `eval_set_frozen.json`——原实现
`if not os.path.exists(...): return`，静默放行。三处的共同问题都是
"证据缺失/不完整"被当成了"跳过检查"而不是"检查失败"，与第一轮
reproduce_L1.py 已经改过的"证据消失必须等价于核对失败"这条原则正好
相反。**已修复**：三处全部改为直接 `SystemExit` 拒测，并新增了此前
完全没做过的第四类校验（eval_set.jsonl 自身相对冻结记录的 sha256）。
另：`可复现性体系/records/M-207.json` 的 `inputs` 此前只登记了
`eval_set.jsonl`，语料哈希从未进入可复现性记录本身——E-3 的修复落在
`eval_set_frozen.json` 和两个校验脚本里，唯独没有落进记录。
⚠️ **第三轮独立复核 §三·二指出这句话的措辞有问题，已改正**：上一版写的是
"现已补上 cases/workflows/templates 三项"，但**改的只是 `measure_L2.py`
的代码，`records/M-207.json` 这个产物本身仍然只有 1 项 inputs**——M-207
只能在真麒麟机上重跑，本地改完代码无法刷新记录。同一份报告里两处完全
相同的情形（代码已改、产物未重生成），一处如实声明（§2.3 的评测集）、
另一处却写成已完成，**标准不一致**。现在统一口径：**代码已改，产物待
麒麟机重跑 M-207 后才会生效**，落差登记在 `可复现性体系/代码产物落差
登记表.md`。

已用变异测试逐一验证**五种**绕过场景（正常路径不误报 + 绕过①②③ +
第三轮新发现的绕过④⑥），见 `test_detectors.py` 用例 6.5。

题目内容与 v1.1.0 完全一致（`eval_set.jsonl` 的 SHA256 不变，仍是
`e0a7f825f3...0b9e`），版本号按惯例递增到 **v1.2.0** 只为区分冻结元信息
的 schema 变化，不代表评测集内容有任何改动。

### 〇.6 v1.2.0 → v1.3.0：语料整体重做，评测集内容级重新生成

这一次不是元信息级的递增，是**真实内容变化**——外部独立评审（《独立评审报告
与整改清单.md》）系统性审计了数据层与知识挖掘层，逼出连锁重做：

1. **数据层重做（D-3/D-4/D-5）**：`merge_and_validate.py` 补上内容级去重
   （`(session_id, tool_name, tool_input, tool_output)` 四元组签名）与三态
   执行结果分类，14,588 条原始记录去重后剩 6,927 条（去重率51%，远高于
   评审自己估的33.1%，部分归因于本项目本身是一次很长的连续会话，产生了
   大量相邻近乎重复的工具调用）。
2. **挖掘层重做（K-1/K-2/K-3）**：`mine_cases.py` 新增两道过滤（命令完全
   相同剔除、探查动词剔除，见 C-213/C-214）；`build_knowledge_index.py`
   的 `render_workflow()` 从"只列去重后的工具名"改成"逐步展示每步做了
   什么"；**新增模板挖掘器**（`mine_templates.py`，K-3）——此前评估过
   "模板抽象器"后决定不做，独立评审指出"可复用模板"是题目原文明确要求
   的第三类知识，且现有案例/流程数据已经够抽象出模板，理由不成立，
   本轮补上。

三者叠加后，知识单元语料从 **152 条（55案例+97流程）** 变为
**95 条（27案例+59流程+9模板）**——数量下降主要来自数据层更严格的去重
（含大量本次开发会话自身产生的重复调用）与挖掘层更严格的过滤，不是内容
质量下降；模板类是全新增加的知识类型。完整数字变化见
《知识检索/说明报告.md》第五、十节。

语料变了，`doc_id` 编号必然整体重排（道理与〇节的 v1.0.0→v1.1.0 完全一样：
`doc_id` 是语料行号，是相对编号），旧评测集的 `doc_id` 全部失效，必须
从生成候选到人工复核整批重新走一遍，**不是修修补补**。

**候选题重新生成**：`generate_eval_candidates.py` 对 95 条知识单元反向出题，
产出 **178 条候选**（close/hard 各半），比 v1.1.0 的 248 条少，符合语料
从152条降到95条的比例。

**近似重复扫描 + 人工复核**：阈值 0.75 命中 3 对，阈值 0.60 命中 12 对
（含新出现的一类模式，见下方）。逐对核查后确认 **9 条问题**（对应
`review_and_freeze.py` 的 `REMOVALS`）需要剔除，3 对确认是误判予以保留
（`CONFIRMED_KEPT_PAIRS`）。

**本轮新发现的碰撞模式：模板与源头撞车**——`REMOVALS` 里 9 条中有 **5 条**
（doc_id 92/87/89/91/86）是模板类知识单元与其抽象来源（案例或流程）撞车：
模板的出题材料（`example_intent`/`example_error`）**必然复用**源头知识单元
的原文，出题时两者天然高度相似。这不是挖掘算法的缺陷，是模板抽象器（K-3）
的设计本身决定的——只要模板存在，这类碰撞就会持续出现，属于已知限制
（见第八节），本轮暂不改造 `generate_eval_candidates.py` 的出题 prompt
去主动规避（样本量小，且需要与出题模型反复调试才能确认改进有效）。

其余 4 条剔除延续前两版已确认的模式：doc_id 62（与61同为2.5分钟内两个
会话问了近乎一样的"claudecode免登录"）、doc_id 21（与19同为qbit-pt日志
排查、close档丢失tail/cat区分信息）、doc_id 58close+hard（与60同为同一天
两个会话重复问邯郸天气，58执行失败60成功，保留60）——三类都与前两版
（doc_id 126/128、77/78、45/47/48 等）性质相同，方法论没变。

**冻结**：178 条候选 − 9 条剔除 = **169 条**，`eval_set.jsonl` 版本号
递增到 **v1.3.0**，SHA256=`2e198716fa14b587e5832c0eb94a4dca259ec78a8f6d9f2c44e352d5087a21f0`
（C-220/C-221）。`by_difficulty`={close:82, hard:87}，
`by_knowledge_type`={case:53, workflow:107, template:9}——template类样本
量小（9条），其召回率数字统计意义有限，第五节与《召回率实测报告.md》
会单独标注。

**召回率结果**（预告，完整数字见第五节与《召回率实测报告.md》）：本版
recall@10=**91.7%**、recall@5=**87.0%**、recall@1=64.5%，均达标或接近
v1.2.0 的历史值（90.0%/84.5%/63.6%）。

⚠️ **这组数字与 v1.2.0 不可直接比较，不只是"行号/doc_id 对不上"这种表面
问题**：语料从 152 条砍到 95 条（砍掉 37%），候选池变小本身就会机械性地
推高召回率，不需要检索质量有任何变化。独立复核的子采样对照实验
（`评测集/measure_corpus_size_effect.py`，记录 M-114）测出：候选池每减少
50 条，R@10 自动涨约 3~4pp、R@1 自动涨约 10pp——把这条曲线套到 152→95
这次真实迁移上，语料效应本身预期贡献的涨幅**已经超过实测涨幅**（R@10
实测只涨 1.7pp、R@1 只涨 0.9pp），扣除语料效应后，三项指标没有一项指向
"检索质量有明显提升"。**recall@5 达标不应被称为"新达标"**——这个说法
暗示的是系统改进带来的结果，而候选池变小的机械效应至少是主要贡献者，
真实检索质量是否也有贡献，无法用这条曲线确证。完整分析见
《召回率实测报告.md》"语料规模效应"一节。
`知识检索/search_knowledge.py` 同期新增混合检索（BM25+向量+MMR，见
《知识检索/说明报告.md》第十一节），但本次召回率测量口径仍是纯向量
检索（与历史数字可比），混合检索的效果是独立结论，不掺进这次对比。

### 〇.7 v1.3.0 → v1.4.0：整链重跑，且第一次真正出齐三档

**触发原因不是评测集本身有问题，是上游语料被发现有损坏。** 第四轮独立
复核之后，排查出脱敏器存在"吃掉自己产生的标记"的缺陷，已交付语料有
**12,332 处内容被销毁**（详见《可复现性体系/勘误与修正记录.md》第十节）。
修复只能防止再发生，**挽回已丢内容的唯一途径是从原始来源重新抽取**——
于是整条链路在 2026-08-14 完整重跑一次：

```
重新抽取(9,807条，原6,927) → 合并 → 三个挖掘器(语料 86 条，原 95)
  → 重建索引(KYSDK 实时向量化) → 重新出题 → 人工复核 → 冻结 v1.4.0
  → 重新导出固化向量 → 重测召回率
```

**三处实质变化**：

1. **paraphrase 档第一次真正出齐**：227 题 = close 74 + **paraphrase 77**
   + hard 76。三档 prompt 早在 R2-03 就写好了，但 v1.3.0 的产物里
   paraphrase 档是 **0 条**——第四轮独立复核 E1 判 FAIL 的正是这一点。
   本轮重跑才落地。它填上了 close 与 hard 之间的空档。
2. **hard 档变硬了**：纯词面 baseline 在 hard 档从 19.5% 塌到 **2.6%**，
   说明新出的 hard 题目真正做到了不含原文词面。
3. **出题审计链首次完整**：`run_id` / system prompt 全文落盘 / 逐题源指纹
   全部到位，`verify_generation_audit.py` 退出码 0，**227/227 题可追溯**
   （v1.3.0 时为 0/169，是三轮遗留的 R3-13）。

⚠️ **代价必须一并说清**：召回率**全面下降**，且 **v1.4.0 没有任何一档在
统计意义上达标**（recall@10 点估计 86.3% 过线，但 95% 置信区间下界 81.3%
不过线；v1.3.0 时下界为 88.0%）。下降来自题目变难而非检索退化——语料
从 95 降到 86 本应让召回率**略升**。完整分析见《召回率实测报告.md》。

⚠️ **冻结文件的行尾在锚定前归一为 LF**：`review_and_freeze.py` 此前三处写盘
都没指定 `newline`，在 Windows 上写出的是 CRLF——**那意味着被锚定的 sha256 是
一个平台相关的哈希**：任何人在 Linux 上用完全相同的内容重新生成，得到的值都不同，
锚定就失去了可核验性（v1.3.0 锚的正是 CRLF 版）。本轮在锚定 v1.4.0 之前改为显式
LF 并重新冻结，**题目内容一字未改**，仅换行字节变化，sha256 从
`a0ff76b5…6349` 变为 `c0727f48…0d96`。

⚠️ **外部锚定的代价**：v1.3.0 的 sha256 曾发到 GitHub issue 做过服务端
时间戳锚定，v1.4.0 重新冻结后那条锚定**对当前评测集不再适用**。重新锚定
只能证明"v1.4.0 在某时刻之前已存在"，**证明不了 v1.3.0 当初那次的顺序**
——这部分证据不可挽回，如实记录。

## 一、为什么这一步不能靠自动化阈值搞定

用 Gemini 3.1 Pro（经 `192.168.100.3:8082` 的 litellm 代理，实际路由到
`openai/gemini-3.1-pro-preview`）从知识单元反向生成问句。v1.1.0/v1.2.0
这一轮（152 条知识单元=55案例+97流程）产出 248 条候选；v1.3.0 这一轮
（语料重做后 95 条知识单元=27案例+59流程+9模板，见〇.6节）产出
**178 条候选**（close/hard 各半），数量下降比例与语料条数下降比例一致，
说明"跳过信息量不足的知识单元"这条生成规则（同下）在两轮语料上表现一致，
不是语料变小之后规则变松了。

**语料覆盖率（独立评审E-7要求量化披露）**：v1.4.0 的 231 条候选覆盖 **77/86=89.5%** 的知识单元（v1.3.0 时为 178 条候选覆盖 89/95=93.7%）
的知识单元，被跳过的 6 条为：workflow×4（intent 分别是"继续"×2、"完成了吗"、
"没让你搞u盘不用了"，均为无实质信息的占位符式表述）、template×2
（example_intent 为"这里面的鱿鱼游戏有多少集"、"好了吗"，抽象模板的示例
意图本身信息量不足以支撑清晰提问）。这 6 条**仍留在索引里作为检索干扰项**，
未从检索空间移除，只是不出现在评测集里——这一点做对了，主动说明。

先跑自动化近似重复检测（`scan_duplicates.py`）：同一 difficulty 档内、
跨 `doc_id` 的问句相似度超过阈值就标记为疑似歧义。**这一步本身不能替代
人工判断**，v1.1.0/v1.2.0 那一轮（152条语料，248候选）实测证明：

- **阈值 0.75** 只扫出 5 对；
- 放宽到 **0.60** 扫出 16 对，但逐一核查源头后发现**多数是误判**——比如
  doc_id 6/15 都是"XXX报错没有那个文件或目录怎么办"，相似度 0.62，
  但两条分别问的是不同文件名（`ebbinghaus.py` / `check_ebbinghaus_sqlite.py`），

## 二、生成设计

### 2.1 边界（已与用户确认，全程遵守）

> Gemini 生成的是「问题」，不是「事实」。

- **合法**：知识单元是真实的（B2 挖掘出的 27 案例 + 59 流程 + 9 模板，
  v1.3.0 语料，见〇.6节），Gemini 只负责换着法子问。
- **不合法**：不让 Gemini 凭空编知识单元本身——那是自己给自己递答案。

本脚本的输入是**已经挖掘好、已经建进检索索引的知识单元**，输出是
`query → 期望命中的 doc_id`，`doc_id` 编号规则与 `build_knowledge_index.py`
建索引时完全一致（案例在前按文件顺序编 0..26，流程紧接着编 27..85，
模板最后编 86..94），确保评测集能直接用于已建好的索引，不需要重新编号。

### 2.2 双档难度设计

每条知识单元生成两档问题：

- **close**：保留知识单元里的关键词（工具名、命令名、报错关键字），
  近似复述或同义改写，字面重合度较高；
- **hard**：只描述场景或目的，**不出现**具体工具名/命令名/专有名词，
  检索必须靠语义理解才能命中。

Gemini 被要求模仿真实用户的口语化短句风格（参考"pytest命令找不到"这类真实
查询样例），且**如果知识单元本身信息量不足以支撑清晰提问，允许如实跳过、
不硬造问题**——这条规则在两轮语料上都生效：v1.1.0/v1.2.0（152条语料）
跳过 28 条，v1.3.0（95条语料）按比例跳过相应数量，跳过原因多是"意图仅为
'继续'这种占位符，缺乏具体信息"，与 B2 报告"部分流程意图信息量偏低"的
已知限制吻合，是一次交叉验证。

### 2.3 R2-03 修复：close 档"承认了但没修"、paraphrase 档从未建过

第二轮独立复核指出：上面 2.2 节的说法一直没变过（"close档字面重合度较高"
是承认，不是修复），出题 prompt 本身对字面重合度没有任何可执行约束，
全项目搜索 `paraphrase` 零命中——第一轮就该建的第三档从未真正建过。
复核员独立实现的纯词面 baseline（字符bigram+ASCII词元双通道TF-IDF，不含
任何模型）在 close 档 R@1 反超 embedding（89.0% vs 85.4%），实测证明
"close档只需要抠关键词"这个问题依然存在。

**已修复（代码层）**：
1. `generate_eval_candidates.py` 的 `DIFFICULTY_SPECS` 把三档要求量化成
   具体的字符bigram覆盖率目标区间（close ≤0.45、paraphrase 0.10~0.30、
   hard ≤0.10），不再是一句"尽量别抄关键词"的口头要求；
2. 新增 `coverage()`/`check_coverage()`，出题后用代码实际核对每一档是否
   落在目标区间，不达标自动打回重出（最多3次），重试后仍超标的**不剔除
   但如实标注**（`bigram_coverage`字段落盘、汇总写进
   `generation_coverage_violations.jsonl`）——這是"根治"而不是"祈祷模型
   照做"：约束是代码核出来的，不是靠信任 prompt。

⚠️ **本次未重新调用 Gemini 生成 v1.4.0 评测集**：三档设计+覆盖率核对逻辑
已在隔离环境用模拟调用验证正确（重合度超标能触发重试、达标后正确停止、
`check_coverage()`对已知的高/低重合度样例判断准确），但**未实际烧一轮
API配额去生成新问题**。原因与R2-01/R2-02同类：v1.3.0（169题）是已冻结、
已锚定哈希、且全部召回率/置信区间/语料规模对照实验都建立在其上的版本，
真正重新出题会连锁需要重新冻结→重新锚定→重新测召回率+CI+语料规模效应，
工作量远超本轮单项修复的合理范围。close/paraphrase/hard三档的真实效果
（是否真的把close档的字面baseline优势打下去了）留待v1.4.0验证，本报告
不虚报"已修复并验证效果"，只如实说明"代码已修复、逻辑已验证、尚未产出
新一版评测集"。

### 3.1 doc_id 45/47/48：三方近似重复（本轮新发现的一种模式）

三条案例都是"qbit-pt容器里的qbittorrent.log报No such file"，close档问句

自动化/批处理性质的排查动作）。三条各自独立地在后续 5 步内匹配到了**不同的

`deduplicate_shared_fix()` 的去重条件——该函数按"共享同一个 `fixed_input`"

相同**，是一个不同的漏洞模式。

予以保留；close 档三条高度撞车，只保留问法与自身修复动作语义最贴合的

本身不像 `deduplicate_shared_fix()` 那样有清晰、可复用的判据。作为已知限制
记录（见第八节），不是漏判。

能够证明"评测集在那些模型写出来之前就已经定稿"。v1.3.0 补锚定时同样适用
这个边界——锚定证明的是"此刻之后"，不是"此刻之前"。

## 四A、出题审计链：现状、局限与补登（R3-13）

本项目对评委的核心叙事之一是「评测集可信度设计：记录生成 prompt、复核
规则、冻结时间与哈希，使评委可复核，不是**自己出题自己考**」。第四轮独立
复核指出这句话在**出题**这一段是落空的。本节如实说明落空到什么程度、
补了什么、还差什么。

### 4A.1 一句话现状

```bash
cd 评测集 && python verify_generation_audit.py
```

```
🟠 审计清单：清单存在但标记为**事后补登**
🟠 三产物 run_id 一致性：三个产物都没有 run_id 字段（已登记缺口）
🟠 system prompt 落盘：清单里没有 prompt 全文（补登按设计留空）
✅ 语料与冻结登记一致：3 个语料文件的原始字节 sha256 与冻结登记逐一相符
🟠 逐题可追溯（L0 严格）：169 题中 0 题可追溯到 run_id、0 题可追溯到源知识单元（0.0%）
ℹ️ 事后重建（L1 弱证据）：169/169 题的 source_rendered 与当前知识库同 doc_id 逐字一致
结论：169 题中 0 题可追溯到 run_id、0 题可追溯到源知识单元。
退出码 2：清单为事后补登，审计链不成立，缺口已登记。
```

**0 就是 0**。拿到这份评测集，现在没有任何办法回答「某一道题是哪次运行、
用哪版 prompt、从哪条知识单元出的」。这个数字不做粉饰，它是本节存在的
理由。

### 4A.2 缺的到底是什么

| 想问的问题 | 当时记了吗 | 后果 |
|---|---|---|
| 这道题是哪次运行出的？ | ❌ 无 `run_id` | 三个产物（候选集/原始日志/跳过日志）无从核对是否同一次运行 |
| 发给模型的 prompt 是哪一版？ | ❌ `SYSTEM_PROMPT` 从不落盘 | 源码改过之后，当时那版全文已不可考 |
| 来自哪条知识单元？ | ⚠️ 只有 `doc_id` | `doc_id` 是**位置编号**，重新挖掘就整体重排（152 条 → 95 条那次就是） |
| 用哪个模型、什么参数？ | ⚠️ 只有冻结元信息里一句人写的自述 | 是声明，不是调用时机器捕获的记录 |

`generation_raw_log.jsonl` 本该覆盖第二、四两行，但它产自 v1.2.0 那一轮
（doc_id 0~151，当前语料合法区间只到 94），且它的 `prompt` 字段只存
`user_content`——**system prompt 从不进日志，而争议的核心恰恰是 system
prompt 里的档位定义与覆盖率目标**。审计日志系统性地漏掉了唯一需要被审计
的那部分。交付物表里对该文件的旧版标注见第六节。

### 4A.3 补上的审计三件套（代码已就位，尚未跑过一次真出题）

| 件 | 落在哪 | 做法 |
|---|---|---|
| **`run_id`** | `generation_audit.py::derive_run_id()`，由 `generate_eval_candidates.py` 在运行开始时派生 | 格式 `gen-<UTC时间戳>-<输入指纹前12位>`。指纹囊括知识库三文件、system prompt、脚本自身、`render_units.py`、模型名与 `max_tokens`、覆盖率验收区间。**不用 `uuid4()`**：随机 id 无法复现，评委拿同样输入重跑对不上任何东西；纯哈希又区分不了「同样输入跑两次」。**三个产物的每条记录写同一个 `run_id`**，审计第一步就是核对三者的 `run_id` 集合是否相同 |
| **prompt 落盘** | `评测集/generation_audit.json`（`prompt.system_prompt_text` + `sha256` + 版本号 + 档位定义 + 覆盖率区间） | 全文只在清单里存一份，原始日志逐行存 `prompt_version` + `system_prompt_sha256`，两边对不上即判定日志与清单不是同一次运行。同时在源码里建立 `PROMPT_VERSION` 沿革表（v1 两档无覆盖率闸门 / v2 三档+闸门） |
| **逐题溯源** | 候选集/原始日志/跳过日志每条记录新增 `run_id`、`source_unit_sha256`、`source_rendered_sha256` | `source_unit_sha256` 是该知识单元**当时的内容指纹**（sort_keys 紧凑 JSON），不是 `doc_id`——以后重新挖掘、编号全乱，仍能凭指纹判断源头还在不在、变没变 |

配套：`verify_generation_audit.py`（审计校验脚本）、
`generation_audit.py --backfill`（补登入口）。
另外，`generate_eval_candidates.py` 现在**拒绝**在已有冻结评测集时覆写
上游候选集（要 `--force`）——重新出题必须连带重新复核、重新冻结、重新
外部锚定，不能是跑一下脚本就顺手把上游冲掉。

### 4A.4 补登清单如何标注「不可证明」

对已交付的这 169 题，三件套一件都没有，只能**事后补登**。补登照抄
`可复现性体系/provenance.py` 的 `backfilled=True` 标准：

> 关键字段一律写 `null`，绝不拿**当前源码**里的 prompt 冒充「当时的
> prompt」——那是把一句谎话变成结构化数据，比没有审计链更糟，下一轮复核
> 会直接采信。

`generation_audit.json` 因此长这样（节选）：

```json
{
  "backfilled": true,
  "run_id": null,
  "prompt": null,
  "model": {"requested": null, "params": null,
            "note": "冻结元信息里那句 generation_model 是手填的声明，
                     不是调用时机器捕获的记录，证据等级不同，不搬到这里"},
  "known_gaps": [
    {"field": "prompt.system_prompt_text / sha256",
     "state": "不可知，且**已知不是当前源码这一版**",
     "why": "当前源码是三档+覆盖率闸门的 v2，而已交付候选只有 close/hard
             两档、无 bigram_coverage 字段，因此当时用的是更早的一版,
             但那一版的全文没有任何留存"}
  ],
  "frozen_reason": "重新出题会产出不同的题……v1.3.0 的 sha256 已做过外部
                    时间戳锚定，锚定链条一旦作废补不回来"
}
```

注意 `prompt` 那条缺口的措辞是「**已知不是**当前这版」而不是「不知道」：
两者证据等级不同，清单里分开写。支撑它的是可独立证伪的重算证据
（`evidence` 字段，5 条），任何人都能自己跑一遍推翻：

| 证据 | 实测 | 说明什么 |
|---|---|---|
| 已交付候选的档位取值集合 | 只有 `close` / `hard`，各 89 条 | 当前源码出三档（含 `paraphrase`），**已知不是同一版 prompt** |
| 候选里带 `bigram_coverage` 的条数 | 0 / 178 | 出题时覆盖率闸门尚不存在，与上一条互证 |
| 冻结题在同 `doc_id` 原始响应里逐字命中 | 0 / 169 | `generation_raw_log.jsonl` 不是这批题的日志 |
| 该日志的 `doc_id` 区间 | 0~151（当前语料合法区间 0~94） | 它属于 v1.2.0 那轮的 152 条语料 |
| 三产物 `run_id` 取值分布 | 全部 `<缺失>` | 当年即使有日志混进别的运行，也没有机制能发现 |

### 4A.5 现在能追溯什么：L0 与 L1 必须分开数

- **L0 严格链（生成时捕获）**：`run_id` + prompt 指纹 + 源单元内容指纹。
  当前 **0 / 169**。
- **L1 事后重建（现在重算）**：拿每道题存下的 `source_rendered` 与当前
  知识库同 `doc_id` 的渲染结果逐字比对，**169 / 169 全部对上**——其中
  141 题用当前渲染规则，另 28 题（全部是案例类）须用 K-2 之前的
  `render_case`（`error_text` 截 150 字而非 300 字）。
  53 条案例题在 150 字规则下 **53/53** 一致、在当前 300 字规则下只有 25 条
  一致，是数据把这版历史渲染规则指认出来的，不是猜测。

  L1 说明的是：`doc_id → 知识单元` 的映射自出题以来没有错位，语料也没被
  换过（`语料与冻结登记一致` 那一项是拿**原始字节** sha256 与
  `eval_set_frozen.json` 的 `knowledge_base_sha256` 逐个比对得到的，不是
  嘴上说说）。

  ⚠️ **L1 不能替代 L0**。它说不清用哪版 prompt、哪次运行、哪个模型出的。
  把 169/169 写成「169 题全部可追溯」就是拿弱证据冒充强证据——那正是
  R3-13 要修的那类问题，不能在修它的过程中再犯一次。报告与脚本输出里
  两个数字始终分行显示。

### 4A.6 为什么不现在重跑，以及重跑后会变成什么样

不重跑的理由（已写进 `frozen_reason`，不是口头说明）：重新出题会产出
不同的题（模型输出不确定），必须连带重新人工复核、重新冻结、**重新做
外部时间戳锚定**；而 v1.3.0 的 sha256 已经做过 GitHub issue 锚定，锚定
链条作废后补不回来（第四节已说明锚定只能证明「此刻之后」）。

下一次整链重跑后，`python verify_generation_audit.py` 的输出会变成：

```
✅ 审计清单：generation_audit.json 存在，run_id=gen-…
✅ 三产物 run_id 一致性：三者集合相同，且与清单一致
✅ system prompt 落盘：全文已落盘（v2，…字，sha256=…），日志逐行指纹与之一致
✅ 语料与冻结登记一致
✅ 逐题可追溯（L0 严格）：N 题中 N 题可追溯到 run_id、N 题可追溯到源知识单元（100.0%）
退出码 0：L0 严格审计链完整。
```

这不是设想——`python verify_generation_audit.py --self-test` 会在一份
合成的、审计链完整的干净副本上真跑一遍并断言全绿（**空变异基线**），
然后逐个注入 5 类缺陷（删清单 / 篡改一条 `run_id` / 篡改清单里的 prompt
全文 / 改动源知识单元 / 拿「补登」当借口掩盖部分记录缺 `run_id`），断言
每一类都红在**指定的那几项**上。基线不绿，说明判据里混了无关变量，
那它对本目录报出的 0 就没有意义；能绿也能红，这个 0 才是结论。

### 4A.7 仍然不可弥补的部分

即使下次整链重跑，有一件事**永远补不回来**：v1.3.0 这 169 题当时用的
system prompt 全文。它没有留存，任何事后写出来的版本都只是当前源码的
副本，不是当时那份。因此本报告不声称「v1.3.0 的出题过程可审计」，只
声称：**v1.3.0 的题目内容与源语料的对应关系可核验（L1），出题过程本身
不可审计（L0 = 0），且这一事实已被机器可读地登记在案**。

另需说清一个容易被误读的地方：大模型出题**天然不可复现**，记了 `run_id`
也不等于重跑能得到同一批题。审计链的目标不是「重跑得到同样的题」，
而是「说清这批题是在什么条件下产生的」。

   全文落盘、逐题源指纹到位，`verify_generation_audit.py` 退出码 0，

   **不是第三方标注**。
2. **Gemini 3.1 Pro 出题的知识边界**：Gemini 只看到脱敏后的知识单元文本，

3. **相似度扫描的召回上限**：本次只对相似度 >0.60 的候选对做了逐一核查，

   报告曾把这条列为"留给召回率实测去补充发现"——历史上确实发生过**（见
   `勘误与修正记录.md` 第七节 doc_id 非确定性错位、`render_case()` 截断
   150字丢关键词两个真实案例，均已修复），这条限制本身长期有效，不因
   语料换成 v1.3.0 而消失。
4. **模板类知识单元与出题天然冲突（K-3/〇.6节新发现）**：本轮9条剔除里
   5条是模板与其抽象来源撞车，根因是模板出题材料必然复用源头原文——只要
   模板类知识单元存在，这类碰撞会在每一轮语料更新后持续出现，不是一次性
   问题，已知限制，暂不改造出题prompt去主动规避（详见〇.6节）。
5. 🔴 **知识检索召回率：v1.4.0 没有任何一档在统计意义上达标**。
   recall@10 点估计 **86.3%** 虽过线，但 **95% 置信区间下界只有 81.3%**；
   recall@5 点估计 82.4% 已经不过线（v1.3.0 时 R@10 下界 88.0%，是当时唯一
   站得住的达标结论）。**下降来自评测集变难而非检索退化**：v1.4.0 新增整档
   paraphrase 77 题（v1.3.0 该档为 0），而语料从 95 降到 86 本应让召回率略升。

   判定，都是让检查器迁就结论。
   hard 档明显弱于 close 档（R@1: 32.9% vs 70.3%），但**这个落差本身不能当作
   "系统确有语义理解"的证据**——纯词面 baseline 在两档之间的落差通常更大，
   close 档的高召回本质是"生成规则要求保留关键词"造成的字面命中。真正站得住

## 附：本报告的数据如何验证

**任何机器（无需银河麒麟环境）**：`review_and_freeze.py` 的复核逻辑与决定
理由是纯 Python，可直接重跑核对（依赖已生成的 `eval_candidates.jsonl`）；
**recall@k 本身也可以**——`可复现性体系/measure_L1.py` 的 M-111 用 P-6
固化好的向量（`可复现性体系/vectors/docs.tsv` + `eval_queries.tsv`）纯
Python复算，无需 KYSDK，数字与下面的 L2 路径逐位一致（见 claims.json 的
C-233）。

**需要麒麟环境**：`generate_eval_candidates.py`（读取知识单元需要与麒麟机上
一致的目录结构）、`measure_recall.py` 与 `可复现性体系/measure_L2.py` 的
M-207（需官方 embedding SDK 现场编码）——这条路径额外验证的是"固化向量
确实出自官方 SDK"，M-111 的纯 Python 路径验证不了这一点，两条路径合起来
才是完整链条。

⚠️ **Gemini 生成结果不是确定性的**——同样的知识单元重新调用一次 Gemini，
生成的具体问句措辞可能不同（模型采样存在随机性），但生成规则（两档难度、
不编造事实）与复核逻辑是确定性的、可复现的。**冻结文件本身（`eval_set.jsonl`
及其 SHA256）才是最终交付物**，不依赖"重新生成能得到完全相同的文本"。

被推翻的判断与修正过的数字，完整记录在 `可复现性体系/勘误与修正记录.md`。
