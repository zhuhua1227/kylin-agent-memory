## 一、整体架构：用图书馆打比方

把整条管线想象成一座**智能图书馆**：

| 管线环节 | 图书馆里的动作 | 本项目对应实现 |
|---------|---------------|---------------|
| 文本（输入） | 一批新书送到馆里 | 一段中文文本（字符串） |
| 向量化 | 管理员"读懂"书的内容，算出一串数字坐标；内容相近的书坐标也相近 | `emb_vec.c`：调用官方 KYSDK embedding SDK |
| 存储 | 把书连同坐标一起放进书架（按坐标而非书名组织） | `pipeline.py` 里一个 Python list，每项是 `{text, vector}` |
| 检索 | 把你的问题也换算成坐标，找书架上坐标"最近"的几本书 | `pipeline.py` 里暴力遍历 + 余弦相似度排序 |
| 返回 | 把找到的书（摘录）递给你 | 打印排序后的前 K 条结果 |

**两个组件、两种语言的分工**：

```
文本 ──> [emb_vec.c，C程序，调官方SDK] ──> 768维向量 ──> [pipeline.py，Python] ──> 存储/检索/返回
         ↑ 比赛硬性要求："调用银河麒麟embedding SDK"        ↑ 存储方案不限定，自主设计
```

- **`emb_vec.c`**：唯一职责是"文本进、向量出"，直接调用官方 C 接口，满足比赛"必须使用官方 embedding SDK"的硬性要求；
- **`pipeline.py`**：负责编排整条管线（建库、检索、排序、输出），用 Python 是因为列表操作、排序、字符串处理比 C 写起来快得多，而且这部分比赛并未限定必须用官方组件实现，可自由设计。

两者通过 **`subprocess`**（Python 调用一个外部命令行程序）胶合：Python 每次要向量化一段文本时，就启动一次 `emb_vec` 这个可执行文件，把文本作为命令行参数传进去，从它的标准输出里读回 768 个数字。

## 二、组件详解

### 2.1 `emb_vec.c` —— 向量化工具

在已验证成功的 `emb_test.c`（证明 768 维用）基础上改造而来，核心区别：

| | `emb_test.c`（证明用） | `emb_vec.c`（管线内部调用用） |
|---|---|---|
| 输入 | 写死在代码里的固定文本 | 命令行参数 `argv[1]`，可传任意文本 |
| 输出 | 人类可读的说明文字（模型名、维度、前5个值等） | 只输出 768 个浮点数，空格分隔，单行，无任何多余文字 |
| 用途 | 一次性证明官方 SDK 输出 768 维 | 被 Python 反复调用，做管线的"向量化引擎" |

之所以要单独做一个"纯净输出"版本，是因为 Python 那边要用程序自动解析这行输出（按空格切开、转成浮点数列表），如果混入"模型名："之类的文字会导致解析失败——这是"给机器读的输出"和"给人读的输出"两种不同的设计目标，写脚本调用别的程序时要注意区分。

调用接口：
```c
int text_embedding_create_session()   // ①建会话
int text_embedding_init_session()     // ②初始化
int text_embedding_init_model()       // ③加载 GTE-base 模型
bool text_embedding(session, text, &result)  // ④向量化
embedding_result_get_vector_length()  // ⑤取维度（768）
embedding_result_get_vector_data()    // ⑥取向量数据
```

编译：
```bash
gcc emb_vec.c -o emb_vec -I/usr/include/kylin-ai/coreai/embedding -lkysdk-coreai-embedding
```

用法：
```bash
./emb_vec "一段要向量化的文本"
# 输出：0.012345 -0.067890 ... （共768个数，空格分隔，一行）
```

### 2.2 `pipeline.py` —— 存储 + 检索编排

四个核心函数，职责单一：

- **`get_vector(text)`**：调 `emb_vec`，把它的输出行解析成 Python 的 `list[float]`；
- **`normalize(vec)` / `dot_product(a, b)` / `cosine_similarity(a, b)`**：数学工具函数，按团队已理解的公式实现——先对两个向量做 L2 归一化（除以自身模长），归一化后的向量做点积，结果就直接是余弦相似度（省去了除以模长的重复计算）；
- **`add_to_store(store, text)`**：向量化一段文本，连同原文一起存进列表；
- **`search(store, query_text, top_k)`**：向量化查询文本，遍历库里每一条算相似度，按分数从高到低排序，取前 K 条。

"向量库"就是普通的 Python `list`，没有用任何数据库软件——数据只存在内存里，程序退出即消失。这是刻意的简化：阶段01的目标只是"跑通"，不是"能用于生产"。

## 三、为什么这样设计（关键决策记录）

1. **为什么不在 Python 里直接调用 KYSDK？**
   KYSDK 官方接口是 C 语言的，没有提供 Python 绑定。与其费力气写 C-Python 的绑定（ctypes/cffi），不如直接把"调用官方 SDK"这件事封装成一个独立的命令行小工具，Python 通过 `subprocess` 调用它——接口简单（一个字符串进，一行数字出），出问题也容易单独调试（直接在命令行跑 `./emb_vec "xxx"` 看结果），不用在 Python 和 C 混合调试。

2. **为什么先用暴力搜索，不用真正的向量数据库？**
   核心原因：符合 roadmap"骨架先跑通"的定位，且比赛只要求 embedding 用官方 SDK，存储方案自主设计，没有必要在验证流程阶段引入额外的学习成本。后续在《知识检索/向量引擎接入报告.md》与《存储后端选型对比报告.md》里正式对比了暴力搜索、官方向量引擎、numpy 三条路径的性能与资源占用，此处不再单独出一份决策记录。

3. **为什么向量化要额外做一个 `emb_vec.c`，不直接复用 `emb_test.c`？**
   `emb_test.c` 是"证明768维"的固定证据文件，属于比赛交付材料的一部分，不应该被后续开发覆盖或依赖；管线开发单独拉一个副本改造，两者用途分离，互不影响，`emb_test.c` 保持原样作为证明材料。

## 四、已知限制（阶段01"骨架"阶段，暂不处理，后续阶段解决）

- **性能**：每次调用 `emb_vec` 都要重新走一遍"建会话→初始化→加载模型"的完整流程，单次调用有固定开销；检索是暴力遍历，数据量大了会变慢。这两点在阶段02做"知识检索"优化时处理（切块策略、检索加速、必要时引入专业向量库）。
- **持久化**：向量库存在内存里，程序退出即丢失，尚无落盘/数据库能力。
- **仅支持单条查询**：没有做批量处理、并发调用。
- **文本编码注意事项**：命令行传中文参数，如果调用环境本身编码设置不对（比如非 UTF-8 终端），可能导致 `emb_vec` 收到乱码字节而崩溃（`invalid UTF-8 byte` 错误）。本管线设计上是 Python 脚本在**同一台 Linux 机器上**直接调用同机的可执行文件，不经过跨系统的编码转换，因此不受影响；但若未来有其他程序通过网络/跨系统方式调用 `emb_vec`，需确保传入的文本是合法 UTF-8 编码。

输出恰好 1 行、768 个数字，首个数值与《证明向量维度》报告中记录的官方 SDK 输出完全一致，证明该工具正确复用了官方接口。


**⚠️ 三点诚实说明：**

1. **测量记录本身不构成证明** —— 那些 JSON 我们能写，别人也能写。
   真正让数字站得住的是"你可以自己跑一遍"。
   可信度不来自「无法伪造」，而来自「容易被验证」。
2. **延迟类数字随硬件变化，不应期待跨机器一致** —— 实测同一段代码在麒麟虚机（2 vCPU）
   与开发机（24 核）上差约 2 倍。核对脚本对延迟只验证结论（是否达标、比值是否合理），
   不比对绝对毫秒数。每个数字产自什么环境，写在 `records/*.json` 的 `environment` 字段里。
3. **方法可复现 ≠ 数据可复现** —— 提取脚本任何人都能跑，但本项目这份数据集
   来自项目成员机器上的真实使用历史，**没有人能重新采集到同一份**。
   第三方验证方式是用随交付物提供的数据集重跑，而非重新采集。

被推翻的判断与修正过的数字，完整记录在 `可复现性体系/勘误与修正记录.md`。
