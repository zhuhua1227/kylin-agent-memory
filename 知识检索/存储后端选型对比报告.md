## 一、为什么做成两个后端，而不是二选一

比赛方案原文对存储这一环的措辞值得注意：

> （4）适配端侧部署需求，**调用**银河麒麟国产桌面操作系统 embedding SDK，**设计轻量化存储方案**，确保检索响应延迟≤500ms

embedding SDK 是**必须调用**的（已在《证明向量维度》《向量化常驻服务》中完成）；但存储方案是让参赛者**"设计"**，关键词是**"轻量化"**——**原文并未规定必须使用官方向量库**。

而评分标准明确要求「适配端侧部署的轻量化程度，**需提供量化论证数据**」。

因此本项目不做拍脑袋的二选一，而是**两个后端都实现、接口完全一致、用实测数据论证选型**：

1. 直接产出评分点名要的「轻量化程度量化论证数据」；
2. 让「**设计**轻量化存储方案」这个动作落到实处——是对比论证后选的，不是随手抓一个；
3. 两组数字都能报，既有官方栈适配、又有性能，不必在两者间取舍。

## 二、架构：一个关键的设计决定

**向量索引与原文存储分离。** 向量后端只负责 `doc_id → 向量`，原文由独立的 `DocStore` 管理。

```
                   ┌─────────────────────────────┐
   查询文本 ──────► │ EmbeddingClient（官方SDK）   │──► 768维向量
                   └─────────────────────────────┘         │
                                                           ▼
                      ┌────────────────────────────────────────────┐
                      │  VectorStore（抽象接口）                     │
                      │    create / add / search / count / close    │
                      └────────────────────────────────────────────┘
                             │                          │
                 ┌───────────┴──────────┐   ┌───────────┴──────────┐
                 │ KylinEngineStore     │   │ NumpyStore           │
                 │ 官方向量引擎          │   │ 归一化矩阵 + BLAS     │
                 │ （经 ve_serverd 桥接）│   │                      │
                 └──────────────────────┘   └──────────────────────┘
                             │                          │
                             └──────────┬───────────────┘
                                        ▼  [(doc_id, score), ...]
                              ┌──────────────────────┐
                              │ DocStore：doc_id→原文 │
                              └──────────────────────┘
```

**为什么这么切**：如果让向量库同时存原文，官方引擎可以塞进动态字段 `$meta`，但 numpy 后端就得为了对齐而硬造一个平行结构，两个后端的职责就不对称了，「可切换」会沦为表面功夫。把原文统一交给 `DocStore` 之后，两个后端做的事情完全相同，**换后端只需要改一个字符串**：

```python
store = create_store("kylin")   # 或 "numpy"
```

### 官方 SDK 只有 C++ 接口的处理

官方向量引擎没有 Python 绑定，因此写了常驻桥接进程 `ve_serverd`，Python 通过管道驱动它——沿用《向量化常驻服务》中 `emb_serverd` 已验证有效的同一套模式。协议只传数字（`doc_id` + 浮点数），因此不需要任何转义。

## 四、★量化对比数据★（20000 条 × 768 维，top-10）

> ⚠️ 以下各项均只取决于数据规模与向量维度，与向量数值无关，故用随机向量测量有效。
> 随机向量**不能**用于评估召回质量——那需要真实向量与标注评测集（属评测系统的工作）。

**下表为 2026-08-04 重跑值** `[M-205]`（L2，麒麟虚机 2 vCPU / 3.9GB）：

| 指标 | 官方麒麟向量引擎 | 轻量 numpy | 倍数关系 | 首测值（08-03） |
|------|----------------|-----------|---------|---------------|
| 冷启动 | 58.5 ms | **0.2 ms** | numpy 快 279× | 65.7 / 0.5 ms |
| 建索引（2万条） | 14.58 秒 | **1.66 秒** | numpy 快 8.8× | 15.30 / 0.89 秒 |
| 检索 P50 | 14.48 ms | **2.89 ms** | numpy 快 5.0× | 14.02 / 2.92 ms |
| 检索 P95 | 15.84 ms | **6.60 ms** | — 见下注 | 15.04 / 3.13 ms |
| **常驻内存** | 141.6 MB | **59.3 MB** | numpy 省 2.39× | 157.1 / 62.6 MB |
| 磁盘占用 | 见下方说明 | 58.7 MB | 大致相当 | 同左 |

**内存构成**（这一项最值得细看）：

- 官方引擎 141.6MB = 引擎守护进程增量 **114.5MB** + 桥接进程 **27.1MB**
- numpy 59.3MB = 本进程内存增量（归一化后的向量矩阵常驻）

原始向量数据本身是 `20000 × 768 × 4 字节 = 58.6MB`。**numpy 的 59.3MB 几乎就是数据本身，
没有额外开销；官方引擎则要多付约 2.4 倍**——这部分是索引结构、gRPC 缓冲与服务进程自身的开销。

⚠️ **两处需要如实说明的地方**：

1. **两次测量的差异**：内存与建索引耗时的重跑值比首测低 5~10%，属正常波动，
   **核心结论（numpy 内存约为官方引擎的 40%）不变**。
2. **numpy 的检索 P95（6.60ms）不能直接与官方引擎比**：numpy 首次调用要预热
   BLAS 线程池，n=20 的样本里 P95 恰好落在预热那一次上——它的 **p50 只有 2.89ms，
   与首测的 2.92ms 几乎一致**。比较倍数关系时应当用 p50，否则会严重低估 numpy 的优势。
   这个方法问题的完整记录见《可复现性体系/勘误与修正记录.md》2.2 节。

**磁盘占用的诚实说明**：本次测量中官方引擎侧读数为 0.0MB，这是**测量假象**而非真实优势——`default.db` 在此前的基准测试后已膨胀到 97MB 且删除集合后空间未回收（SQLite 不自动 vacuum），本次写入直接复用了这些空闲页，所以文件没有增长。两个后端存的是同样的 58.6MB 向量数据，真实磁盘成本大致相当。

### 对照硬指标

⚠️ **独立评审R-5指出**：本项目里"查询向量化P95"这个数字先后测出过 68.4 / 84.9 /
118~124 / 28.4ms 四个值（不同批次、不同硬件负载下的独立测量），此前多处代码
与报告硬编码了最早、最乐观的 68.4ms，而《向量化常驻服务/说明报告.md》自己
早已把结论区更新为 84.9ms（首测偏乐观，重跑后系统性偏慢，详见该报告5.3节）。
以下改用 84.9ms 这个**已被重跑确认、最新的**数值，并注明：向量化与检索是
两个独立基准（不同批次、不同规模）各自测得的P95，直接相加是保守的上界估计，
不是同一批数据逐题求和后再取分位数（后者才是`measure_recall.py`E-10修复后
的做法，此处两个基准脚本本身不共享逐题原始数据，无法那样算）：

```
kylin   端到端 P95 上界估计 = 查询向量化 84.9ms + 检索 15.84ms ≈ 100.7ms（占预算 20.1%）  ✅ 达标
numpy   端到端 P95 上界估计 = 查询向量化 84.9ms + 检索  6.60ms ≈  91.5ms（占预算 18.3%）  ✅ 达标
```

**两者都达标，余量都在 79% 以上。** 注意端到端延迟的大头（84.9ms，占 84%~93%）来自**官方 embedding SDK**，而它是题目硬性要求必须调用的——也就是说，**检索后端的选择对最终延迟的影响只有个位数至十几毫秒，相对 500ms 预算不构成实质差异**。

（另见《评测集/召回率实测报告.md》第三节：在真实95条知识单元语料+真实查询上实测的端到端P95为kylin 111.70ms / numpy 118.32ms，逐题求和后取分位数，口径更严谨，与本节的上界估计量级一致，互相印证。）

## 五、结论与选型建议

### 5.1 一个必须如实记录的发现

立项时曾推测「官方引擎作为专业向量库，在轻量化上可能优于自建方案」。**实测推翻了这个推测：numpy 后端在冷启动、建索引、检索延迟、常驻内存四个维度上全面占优，内存只占官方引擎的 40%。**

这个结果符合工程直觉：2 万条 × 768 维只有 6100 万次乘加，BLAS 一次矩阵乘法即可算完；而官方引擎要走 gRPC 序列化、跨进程通信、索引结构维护，这些固定开销在这个数据量级下反而成了主要成本。**专业向量库的优势在千万级数据量上才会显现，本项目的数据规模远未触及那个拐点。**

### 5.2 那还用不用官方引擎

用，但理由要说对：

| 官方引擎的真实优势 | 说明 |
|------------------|------|
| **麒麟端侧适配的完整性** | 全栈使用官方组件（embedding SDK + 向量引擎），这是本项目相对其他队伍的差异化，也直接对应「实用性（10分）：成果与 OS Agent 及同类产品的适配性」 |
| **持久化开箱即用** | 数据落在 `/home` 分区随引擎守护进程管理，重启不丢；numpy 方案的落盘与加载需自己实现（本项目已实现，但那是额外代码与额外的出错面） |
| **可扩展上限** | 引擎配置 `max_count: 400000`；numpy 方案内存随数据量线性增长，本项目 2 万条占 62MB，若涨到 40 万条将占约 1.2GB，在 3.9GB 的端侧设备上会很紧张 |

| 官方引擎的真实代价 | 数据 |
|------------------|------|
| 常驻内存多 2.4× | 141.6MB vs 59.3MB（第四节08-04重跑值） |
| 建索引慢 8.8× | 14.58 秒 vs 1.66 秒（一次性成本，可接受） |
| 检索慢 5.0×（p50口径） | 14.48ms vs 2.89ms（相对 500ms 预算可忽略） |

⚠️ **独立评审R-4指出并已修正**：此前这里用的是08-03首测的P95值（15.04ms
vs 3.13ms=4.8×），既是已被第四节08-04重跑值取代的旧数字，又用了P95而非
第四节自己交代过的"倍数关系应当用p50"这条口径（numpy的P95会被BLAS线程池
预热样本拉高，严重低估numpy优势——第四节脚注已详细说明）。现改用与第四节
表格逐位一致的08-04重跑p50值。

**建议**：**默认使用官方麒麟向量引擎**，理由是端侧适配完整性与可扩展上限；同时**保留 numpy 后端作为轻量化选项**，在内存受限的部署场景下可一键切换。两组数据都写进技术方案。

### 5.3 答辩时的表述要点（重要）

**不要说「官方引擎性能更好」——那不是事实，容易被问穿。**

应当说的是：

> 我们实现了两套存储后端并做了量化对比。轻量 numpy 后端在本项目数据规模下各项指标全面占优（内存仅为官方引擎的 40%），我们如实记录了这一点。最终默认选用官方麒麟向量引擎，是基于端侧适配完整性与可扩展上限的工程权衡，代价是 2.5 倍内存与 12ms 延迟；而 12ms 相对 500ms 的指标要求不构成实质影响。两套后端可一键切换，内存受限场景可退回轻量方案。

这个表述同时展示了：做过对比实验、数据诚实、选型有依据、方案有弹性。**比单方面吹某一个后端更有说服力。**

## 八、已知限制

1. **numpy 后端的内存随数据量线性增长**，40 万条约需 1.2GB。当前 2 万条规模无压力，但作为长期方案需要注意。
2. **官方引擎的 `default.db` 是全系统共用的**，且删除集合后磁盘空间不自动回收。测试用集合应及时清理（`ve_cleanup`）。
3. **两个后端目前都是全量扫描**（官方引擎在此数据量下是否启用了近似索引未做深究）。真到百万级需要重新评估。
4. **未测多并发**。当前建索引与检索都是单线程，端侧单用户场景够用。

3. **方法可复现 ≠ 数据可复现** —— 提取脚本任何人都能跑，但本项目这份数据集
   来自项目成员机器上的真实使用历史，**没有人能重新采集到同一份**。
   第三方验证方式是用随交付物提供的数据集重跑，而非重新采集。
