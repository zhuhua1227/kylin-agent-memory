# 偏好提取模块 —— 说明报告

> 对应赛题：题目内容 (2)「构建偏好记忆动态捕捉模块，基于多源融合数据，实现用户**操作习惯、输出风格、安全策略**等偏好的自动提取与**版本化管理**，实现**跨场景偏好适配与回溯**」
> 对应评分：技术创新性 30 分的三个点名子项之一 + 性能指标「偏好提取准确率 ≥85%」
> 设计依据：`偏好提取-设计方案.md`
> 代码位置：`知识检索/mine_preferences.py`（提取+切分+评测+版本化）、`可复现性体系/measure_preferences.py`（M-401~M-404）

---

## 〇、一句话结论

**用前期数据提取"这个用户在什么情境下倾向怎么做"，去预测留出期的真实行为，命中率就是准确率——标准答案是留出期的真实行为记录，零人工标注、零循环论证。**

三类偏好里，**操作习惯**类实测留出期预测准确率 90.0%（Wilson 95% 置信区间下界 88.3%，稳稳超过赛题 85% 门槛），相对"不看具体情境、只猜类别内全局众数"这条基线提升 **+69.5 个百分点**（置信区间下界 65.6% > 0，可确信）。**输出风格**类提升幅度为 0（该类别目前只有单一触发情境，如实报告结构性局限）。**安全策略**类实测为**空结果**——不是没做，是深挖后发现设计方案原本判断"证据强度最高"的依据本身站不住（详见 §二），如实报告，不强行凑数。

## 一、口径：不区分动作的选择主体（设计方案 §一，2026-08-15 已定）

**"用户偏好"的操作性定义**：该用户在其 Agent 交互轨迹中**稳定表现出**的操作模式与约束表达，**不区分**具体动作由用户直接指定还是由 Agent 在用户授权下选择。三条依据：

1. 赛题背景原文把"工具调用执行结果"列为记忆数据源之一
2. 记忆系统服务的是"用户+Agent"交互整体，拆分对系统能力无影响
3. 下游价值在于"下次遇到同类情境能否复用既有模式"，与动作主体无关

---

## 二、一次真实的假设推翻：安全策略并非"证据强度最高"

### 2.1 设计方案原始判断与实测数字对不上

设计方案 §2.1 原本判断安全策略是三类里"证据强度最高"的一类，依据是"老数据集有 4,664 条 `user_rejected` 记录（占 tool_execution 的 33.2%）"。**实测这个数字对不上**：真实 `execution_status=="user_rejected"` 记录是 **865 条，占 9.34%**，不是 4664/33.2%。推测是设计时把 B2 案例挖掘阶段被识别、后来判定为单日污染的旧统计（"5174 条出错记录 4663 条来自 07-27"）错记成了这里的数字——两个数字接近但指的不是同一件事。

### 2.2 深挖发现：这 865 条本身也是同一枚地雷

进一步核查发现，865 条 `user_rejected` 记录里 **798 条（92.3%）来自同一天同一会话**（2026-07-27，`session_id=bada921e`），用 `mine_cases.detect_outlier_days()` 一验就中——与 `mine_cases.py` 文档字符串里记录的"90.1%来自单日两个会话的批处理任务"是**同一枚地雷**，只是这次是在 `execution_status` 字段上重新踩了一次。

排除该异常日后，正常日子的拒绝率只有 **0.8%（66/8230）**，且**没有任何命令类型的拒绝率有统计支持**——`rm` 这类真正有风险的操作拒绝率反而只有 3.6%，`ip`/`df` 这类只读命令拒绝率虚高到 60~85% 全部是异常日的产物。

### 2.3 提取阶段的第二个坑：把"多数是允许"误当成"策略"

修复异常日之后，第一版实现仍产出了 **52 条**"安全策略偏好"——逐条核查发现全部是"对 X 这类操作的默认处置是 allowed，ratio≈0.97~1.0"，是在复读全局 0.8% 的低拒绝率基线，不是任何有信息量的策略（因为几乎所有操作类型都是"大多被允许"）。

修法：**只统计"拒绝"是多数的组，"允许是多数"的组一律不产出偏好**——不是它们支持度不够，是它们本来就不该被当成"策略"报出来（见 `mine_preferences.py` 的 `required_choice="rejected"` 参数）。修复后，**安全策略类实测 0 条**，与门槛无关，是这批数据里真实不存在统计意义上"倾向拒绝"的操作类型。

**这是本模块最有说服力的部分之一**：一条被设计方案寄予厚望的信号，追到底发现是同一个数据集特性（单日批处理污染）第二次露头，加上提取逻辑本身的一个真实设计缺陷（把"默认值"误当"策略"）。如实报告空结果，比硬凑出几条弱偏好更有价值。

## 三、提取机制（L1 确定性，不调 LLM）

### 3.1 剥壳复用，不重新发明

- **`inner_verb()`**（命令首动词提取）—— 复用 `mine_cases.py`，第三/四轮复核已验证到类级通用
- **`detect_outlier_days()`**（单日污染检测）—— 复用 `mine_cases.py`，§二用到
- **`adjudicate()`**（版本变更裁决）—— 复用知识冲突模块，§五用到

### 3.2 操作习惯：情境=intent 类别，选择=命令首动词

`VERB_INTENT_MAP` 从真实数据里 995 个不同的 `inner_verb()` 输出手工归类得出（不是拍脑袋列的）：`grep`→content_search、`cat`→file_view、`ls`→file_list、`systemctl`→service_control 等约 60 组映射。

### 3.3 输出风格：一次"范围定义错了、不是门槛该调松"的真实示范

最初把 `.md`/`.txt`/`.json`/`.html`/`.yaml`/`.csv` 六种扩展名都算作"文档类产出"，六选一分母变大，`.md` 占比从 73.4%（58/79）被稀释到 55.8%（58/104），卡在 `min_ratio=0.65` 门槛之下、产出量为 0。深查发现 `.yaml`/`.html` 大多是配置文件/网页 demo，不是"整理结果"的候选形态。收窄回设计方案 §2.2 原定的三种格式后，真实占比回到 73.4%，产出 1 条偏好。**产出为 0 时先查范围定义，不是先调松门槛**——设计方案 §八自己就写了这条原则，这里是一次真实践行。

### 3.4 三道门槛（缺一不可）

```
min_trigger=8    情境出现太少，比例没有意义（4/4=100% 说明不了什么）
min_ratio=0.65   低于此值说明这个情境下并无稳定倾向，是随机的
min_sessions=2   只在一个会话里出现的是一次性做法，不是习惯
                 （同 mine_templates.py R2-22 bug③ 的判据：用
                  set(session_id) 而不是 len(items) 计数）
```

### 3.5 提取产出（`知识检索/preferences.jsonl`）

```
tool_exec_total: 9266
  rejected_by_min_trigger:     685
  rejected_by_min_ratio:         5
  rejected_by_min_sessions:      0
  rejected_by_required_choice:  57  （只发生在 safety_policy：allowed 是多数的组）

extracted_operation_habit: 19
extracted_output_style:     1
extracted_safety_policy:    0
```

19 条操作习惯偏好全部有真实、可复现的对比对象（如 `content_search` 情境下 `grep`(170) vs `Select-String`(2)，比例 0.988；`file_view` 情境下 `cat`(422) vs `Get-Content`(10)，比例 0.976），部分情境（`journalctl`/`mv`/`dmesg`/`cp`/`git`）目前只观测到唯一候选（`n_alternatives=0`，ratio 恒为 1.0）——这类偏好仍可被留出期验证（预测"下次还是用这个"是否成立），但证据强度弱于"有真实竞争后胜出"的情形，schema 里如实标注，不混为一谈。

## 四、评测：留出期行为预测

### 4.1 切分：会话完整性优先于时间戳

知识冲突模块挖掘时已经发现：本数据集里 Claude Code 会话可以跨天恢复，最长一个会话 `session_id=1cd1ff9f` 横跨 **23 天**（2026-07-13→08-13）。纯按时间戳切分会把这个会话拦腰切断——前半段预测自己的后半段，情境几乎相同、任务连续，是切分泄漏，会把准确率虚抬。

`split_by_time_keeping_sessions()` 按会话起始时间排序、整个会话归入同一侧。实测：训练期 142 会话 / 留出期 95 会话，交集为 0；已知的 23 天长会话被完整保留在训练期一侧。**朴素按时间戳切分确实会腰斩会话**——本数据集上实测会切断 3 个会话，证明这道防线在防真实存在的风险，不是防假想敌。

### 4.2 多数基线的口径：类别级，不是情境级

若把"多数基线"理解成"同一具体情境（trigger）下 T1 里最常见的选择"，这个值与提取器的 `choice.observed` 定义完全相同（两者都是同一情境下的 T1 众数），在提取器覆盖到的情境上两者会永远预测一致、提升幅度恒为 0——这个数字就测不出任何东西。

**本模块的解读：基线的"情境"取 category 这一级颗粒度，不看具体 trigger**——"不管当前是哪个具体意图，只看这一大类里 T1 整体最常见的选择是什么"，这是标准机器学习评测里"忽略特征、只猜全局众数"的基线，与情境条件化的提取器预测天然不同。两者在同一批留出期出现次数上比较，保证公平。

### 4.3 实测结果（三个数分开报，不合成一个）

| 类别 | n（留出期出现次数） | 提取器准确率 | 多数基线 | 提升幅度 | 提升区间（保守） |
|---|---|---|---|---|---|
| **操作习惯** | 1352 | **90.0%**（CI [88.3%, 91.5%]） | 20.5%（CI [18.4%, 22.7%]） | **+69.5pp** | [65.6%, 73.1%] |
| 输出风格 | 44 | 68.2%（CI [53.4%, 80.0%]） | 68.2%（同上，恒等） | 0.0pp | [−26.6%, 26.6%]（跨0） |
| 安全策略 | 0 | — | — | — | — |

⚠️ 提升区间用两个独立 Wilson 区间直接相减，是**保守估计**（两者其实算在同一批试验上，天然相关，真实区间只会更窄）——方向安全：不会把不显著的提升幅度包装成显著。

- **操作习惯**：提升区间下界 65.6% > 0，可以确信提取器优于多数基线；准确率区间下界 88.3% > 赛题 85% 门槛，**这是本模块唯一一个统计上确信达标的类别**。
- **输出风格**：提升幅度=0——不是提取器无效，是这一类目前只挖到 `doc_format` 单一触发情境，类别级基线与该唯一情境的多数在数学上恒等。区间跨 0，**如实写"不能证明提取器优于多数基线"**，按赛题"未达基础指标需明确优化方向"处理：优化方向是拓宽输出风格的情境切分（如按目录/项目上下文区分），不是这个数字本身算错了。
- **安全策略**：提取阶段已是空集，评测阶段自然无可评测对象。

**不把三个数合成一个"总体准确率"**——三类证据强度、样本量、结构完全不同，合成会互相掩盖（前四轮"总体 vs 分档"的教训，本模块照此办理）。若一定要引用单一数字回应赛题"偏好提取准确率≥85%"，应引用**操作习惯类的 90.0%（CI 下界 88.3%）**并明确注明这是三类中唯一确认达标的一类，不代表模块整体。

### 4.4 阴性验证：一条设计假设被实测推翻、随即改写

设计方案 §七原始草稿的第⑤条阴性验证设想"打乱时间顺序后准确率必须掉到基线水平，否则说明提取器没在用时间信息"。**实测这个假设不成立**：随机打乱训练/留出切分后，操作习惯准确率是 94.6%，比按时间切分的 90.0% **更高**，不是更低。

这符合"习惯"这个概念的本意——真正的习惯就应该跨时间稳定；如果打乱后准确率暴跌，反而说明提取到的是短期上下文效应而不是真习惯。照抄原设计的断言会测出一个不成立的假设，不是测出真 bug。

**改为验证设计方案 §6.2 真正要防的风险本身**：不做会话完整性切分，确实会让会话跨训练/测试两侧泄漏（本数据集实测 3 个会话在朴素按时间戳切分下被腰斩），而 `split_by_time_keeping_sessions()` 必须把这个泄漏降到零。这是"防的风险是真实存在的"与"防线本身真的挡住了"两件事一起测，比一个不成立的准确率假设更贴近本模块真正的风险点。5 条阴性验证全部写进 `test_detectors.py` 的 `test_preference_extractor_negatives()`，`mutate.py` 新增 2 条变异。

### 4.5 变异测试自己发现的一个覆盖漏洞

`mutate.py --all` 首次跑"切分保持会话完整"这条变异（把排序键从时间戳换成 `session_id` 本身）时，**确实被检出，但检出的机制不对**：唯一新增的红用例是血缘（provenance）检查（改了代码、`preferences.jsonl` 的血缘随之判 stale），不是任何一条直接验证切分行为的用例——④"跨天会话不被切断"这条断言测的只是"会话没被腰斩"，而按 `session_id` 字母序排序**同样不会腰斩任何会话**，只是分错了哪些会话在训练期、哪些在留出期，语法上仍然"合法"，测不出来。

这正是本项目反复强调的"检出了，但检出的是错误的原因"——如果哪天血缘检查被弱化或去掉，这条变异会真的悄悄溜过去。补了一条专门检验时间序（不是 session_id 字母序）的用例：构造两个会话，一个时间上最早但 `session_id` 字母序最后（`zzz-earliest`），一个时间上晚但字母序最先（`aaa-later*`），断言前者必须落在训练期——按字母序排序会把它错分进留出期，直接测穿。补上后重跑 `mutate.py --all`，这条变异改由该用例直接检出。

## 五、版本化：偏好变更即知识冲突

设计方案 §5.1：**用户中途改了规则（"以后不用每次都问了"）→ 旧偏好被新偏好推翻 → 这就是 T2 方法推翻。** 版本化/裁决/回溯不重新发明机制，直接复用知识冲突模块已建成、已用 18 条真实冲突测过准确率的 `adjudicate()`。

`detect_preference_conflicts()`：把同一 `stable_key` 在训练期与留出期两个时间窗口下的 `choice.observed` 做对比，不同即触发裁决。实测发现 **1 条真实的偏好版本变更**：

```
pref:operation_habit:disk_usage:  du → df
  旧窗口：n=20, ratio=0.80, 3会话（07-11~08-01）
  新窗口：n=34, ratio=0.68, 6会话（07-26~08-13）
  裁决：T2，new_supersedes_old
```

⚠️ 诚实的解读：`du`（目录占用）与 `df`（文件系统剩余空间）问的是不同的问题，这条"变更"未必是纯粹的偏好反转，也可能是"disk_usage"这个 intent 类别本身粒度偏粗，把两种不同用途的磁盘查询合并到了一起——本身也是本模块归一化表还能继续细化的一个真实例子，如实记录，不拔高成一条教科书案例。

## 六、跨场景适配

`scenario.n_by_scenario` 已在 schema 里，场景标识从会话内最早一条 `user_input.project` 字段推断（Windows 路径→`windows`，`/`开头路径→`kylin`）。实测：**windows 场景 474 次 / kylin 场景 0 次**（另有 1468 次 `unknown`，因为许多会话本身没有 `user_input` 记录可回填 project）。

本项目老数据集几乎全部来自 Windows 笔记本真实开发记录，kylin 场景样本量不足以做有统计意义的跨场景对比——与知识冲突模块 §一.2 记录的**同一条环境边界**（"新的 Kylin 目标机数据冲突尚未长出"）。`detect_scenario()`/`scenario.n_by_scenario` 机制已就绪、可直接用，卡的是数据积累时间，不是机制未实现。

## 七、冻结

`知识检索/preferences_eval_frozen.json` 记录：切分点（训练/留出会话列表的 sha256）、`preferences.jsonl` 的 sha256、语料哈希（`memory_source_records.jsonl`）、完整评测结果快照。安全策略等偏好提取不需要人工裁决（标准答案是留出期真实行为，不是人的判断），所以没有 `review_and_freeze_conflicts.py` 那种手写裁决的环节——"冻结"要证明的是另一件事：**切分点不是看着结果反向挑的**，任何人都能核对这就是那次评测用的切分。
