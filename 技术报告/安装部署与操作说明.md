## 七、安装部署指南

本章覆盖两套不同的环境，答题要求 (5)（安装部署指南、操作说明）对应的是前者：

- **端侧运行环境**（本章）：银河麒麟机器，记忆服务实际运行的地方，需要官方 KYSDK Embedding、官方向量引擎等系统级组件，安装过程涉及不可变系统的解锁。
- **评测复现环境**（第八章 3 节）：任意 Windows / macOS / Linux 机器，只需 Python 与 numpy，用于核对本报告的数字主张，不涉及本章的系统级安装。

两者不要混淆：复现评测数字不需要一台麒麟机；但要让记忆服务真正跑起来、能被 OS Agent 调用，必须完成本章的全部步骤。

### 1. 环境要求

**表7.1 端侧运行环境要求**

| 项目 | 要求 |
|---|---|
| 目标机 | 银河麒麟桌面操作系统 V11（磐石 OSTree 不可变系统），2 vCPU / 3.9 GB 起 |
| 系统级依赖 | KYSDK Embedding SDK、`kylin-ai-runtime`、`kytensor`、官方向量引擎 `kylin-ai-vector-engine`——均通过麒麟软件源以 apt 安装，不在 `requirements.txt` 管理范围内 |
| Python | 3.9 及以上（`list[float]` 这类内建泛型标注，3.8 跑不了） |
| Python 第三方依赖 | 仅 `numpy>=1.24`（`requirements.txt` 唯一一项），执行 `pip install -r requirements.txt` |

### 2. 系统解锁与 KYSDK 部署

磐石不可变系统对写入 `/usr` 设了两道防护：安装守卫拦截未经许可的 dpkg 操作，`/usr` 本身以只读方式挂载。首次在一台全新的麒麟机上部署，需按以下顺序完成：

1. 查看当前部署状态：`sudo ostree admin status`，确认是干净的单一部署槽。
2. 解锁 `/usr` 为可写：`sudo ostree admin unlock --hotfix`，随后用 `grep ' /usr ' /proc/mounts | tail -1` 验证结尾为 `rw`——`/usr` 常出现多行 overlay 记录，第一行恒为只读的中间层，必须取最后一行判断，只看第一行会误判为未解锁成功。
3. 安装 embedding 开发包，走 `unshare -m` 通道以绕过安装守卫：`sudo apt update` 之后 `sudo unshare -m sh -c 'apt install -y libkylin-coreai-embedding-dev'`。
4. 麒麟出厂镜像的后端版本通常落后于 SDK 要求的协议版本，需要安装 AI 子系统元包并协同升级。由于 dpkg 会把元包依赖判定为"已满足"而只重装元包自身、不碰其 71 个真实依赖，须显式取出完整依赖清单并逐一强制重装：先用 `apt-cache depends --recurse` 导出清单，再对清单中的每个包执行 `apt install -y --reinstall`。这一步同时会修复模型包 `model_description.yaml` 缺失 `others_info` 字段导致的 `errorCode 10`（模型未找到）问题。
5. 重启后端服务使新协议生效：`sudo systemctl restart kytensor`；`kylin-ai-runtime` 由图形会话拉起、无 systemd 单元，需要在图形界面注销重新登录，或按第 5 小节所述方式手动拉起。
6. 放行 kysec 执行控制以运行自编译的验证程序：`sudo setstatus -f exectl off`，编译并运行验证程序确认输出向量维度为 768，随后执行 `sudo setstatus -f exectl warning` 恢复安全策略。

完整命令、每一步的验证方法与已知报错的对照表，见《证明向量维度/前置步骤-不可变系统解锁与KYSDK部署命令手册.md》。

### 3. 一个必须先知道的限制：这套部署不会持久

以上安装写入的全部内容——`sshd`、embedding SDK 全套、`kytensor`、`kylin-ai-runtime`——在磐石不可变系统上属于临时覆盖层，**整机重启后必定退回出厂状态**，这一点已经过正常重启与异常断电两种场景反复实证，虚拟机快照备份同样无法挽回，因为这些改动从未落到磁盘。这不是操作失误，是不可变系统"保护系统分区不被持久修改"这一设计目标的必然结果。

因此本项目把恢复流程固化为一键脚本，**每次整机重启后运行一次即可**：

```bash
bash ~/restore_env.sh
```

脚本自动完成上一节第 2 至 6 步的全部工作（解锁、修复依赖、重装 SDK 与模型包、重启后端服务、验证），约 5~10 分钟。若需要免人工干预，可进一步配置为开机自动执行——因为解锁与安装可以在无人登录的开机阶段完成，而 `kylin-ai-runtime` 必须挂在图形会话下才能启动，这部分被拆成两个脚本、由两种机制分别触发：`restore_env_boot.sh` 由 root 的 `@reboot` crontab 触发，负责系统层恢复；`start_runtime_session.sh` 由桌面自启动条目触发，负责在用户登录后拉起 `kylin-ai-runtime`。完整配置方法见前述手册第 7.4 节。

### 4. 构建知识索引

确认官方向量引擎已在运行（它由 systemd 用户级服务管理，需带 `--user` 查询）：

```bash
systemctl --user is-active kylin-ai-vector-engine   # 期望 active
```

随后构建生产索引：

```bash
python3 知识检索/build_knowledge_index.py --backend kylin --collection rag_knowledge --exclude-conflicts
```

`--exclude-conflicts` 是复现本报告全部检索指标所必需的：不加此参数会把知识冲突记录也当作第四类知识单元一并入库，索引膨胀且不再与冻结评测集口径一致（历史上确实因遗漏此参数导致过一次索引膨胀 21% 的事故，详见《基准重建-执行方案.md》）。默认后端为 `numpy`，生产部署需显式指定 `--backend kylin`。构建成功后会打印知识单元的分类计数，应为案例、流程、模板三类合计 86 条。

### 5. 启动记忆服务

```bash
bash 记忆服务/start_memory_service.sh
```

默认以 `config=all backend=kylin` 启动，监听 `127.0.0.1:8077`。启动脚本会先自检 embedding 客户端能否返回 768 维向量，失败则提示先运行 `restore_env.sh`；随后以 `nohup` 常驻（磐石不可变系统没有可持久的 systemd 单元），并轮询 `/health` 接口直至服务就绪或超时。切换检索配置用环境变量：`CONFIG=naive bash 记忆服务/start_memory_service.sh`。

### 6. 验证安装

```bash
python3 记忆服务/smoke_service.py --config all
```

冒烟测试发出 5 条手工查询，全部应在 500 毫秒内返回、结构合法、`config` 字段与启动参数一致。看到全部通过，即完成从系统解锁到服务可用的全部安装部署。

## 八、操作说明

### 1. 知识检索接口

记忆服务运行后暴露两个 HTTP 接口：

**表8.1 知识检索接口契约**

| 接口 | 请求 | 响应 |
|---|---|---|
| `POST /retrieve` | `{"query": "任务描述文本", "k": 5}`，`k` 取值 1~50，默认 5 | `{"units": [{"doc_id", "type", "text", "score"}, ...], "config": "all", "elapsed_ms": 74.3}` |
| `GET /health` | 无 | `{"ok": true, "index_size": 86, "config": "all", "backend": "kylin"}` |

`config` 字段在每次响应中回显，用于证明服务当前用的是哪一套检索配置；服务启动时若指定 `--config meta_oracle` 会直接拒绝启动，因为该档使用了题目标准答案自身的类型标签做过滤，属于标签泄漏、只是上界不是可部署的能力（3.6 节已说明）。`score` 字段仅供参考：对朴素检索它是排序依据本身，对带重排的配置它只是向量层相似度，不是最终排序依据，调用方不应把它当排名字段使用。

不需要先起服务、只想调试单条查询时，可直接用命令行工具：

```bash
python3 知识检索/search_knowledge.py "查询文本" --backend kylin --top-k 5
```

常用参数：`--type` 限定返回类型（`case` / `workflow` / `template` / `conflict`）；`--mmr` 启用多样性重排（`--mmr-lambda` 调节强度）；`--hybrid` 启用 BM25 混合检索（`--hybrid-alpha` 调节权重）；`--include-superseded` 关闭知识取代过滤、连同已被取代的旧版本一并返回。

### 2. 偏好查询与冲突回溯

图 3.1 架构图中"偏好查询""冲突回溯"两项能力，目前的实现方式与知识检索不同，如实说明：

- **偏好查询**是离线产物，不是运行时接口。偏好提取的结果落在 `知识检索/preferences.jsonl`，每条记录以 `stable_key` 标识某一情境下的稳定操作模式，按需直接读取该文件即可查询；运行时不重新计算。
- **冲突回溯**是一个 Python 库函数，不是 HTTP 接口：`mine_conflicts.retrieve_old(stable_key)`。传入某条知识的 `stable_key`，返回其旧版本记录；若查不到会直接抛出 `KeyError`，不会静默返回空值——这是有意的设计，避免"这条知识从未存在过"与"这次恰好没查到"在调用方看来无法区分。

这两条能力目前均未封装成独立的 HTTP 端点。若后续需要通过网络调用，可复用 `记忆服务/memory_service.py` 现成的路由骨架各自新增一个 handler，当前版本尚未实现，如实标注为边界而非默认已具备。

### 3. 精准遗忘

三个接口（`POST /forget` 两步确认、`POST /unforget`、`GET /forgotten`）的完整契约见 3.7 节表3.4。调用示例：

```bash
# 第一步：定位候选
curl -s -X POST http://127.0.0.1:8077/forget \
     -d '{"instruction": "忘掉那条 sqlite3 找不到命令的处理记录", "k": 5}'

# 第二步：确认遗忘（doc_id 取自上一步候选列表）
curl -s -X POST http://127.0.0.1:8077/forget \
     -d '{"instruction": "忘掉那条 sqlite3 找不到命令的处理记录", "confirm_doc_id": 12}'
```

### 4. 接入 OS Agent：pi 记忆钩子

`记忆服务/rag-memory.ts` 是 pi coding agent 的行动前记忆注入钩子，用 `--memory on` / `--memory off` 控制是否调用记忆服务：开启时，钩子在智能体开始行动前调用 `POST /retrieve`，把返回的知识单元拼装成注入块，插入到最后一条用户消息之前（系统提示之后、任务之前）；关闭时完全不调用该接口，其余提示词一字不变——两种条件下的系统提示逐字相同，这一点由钩子的实现方式保证，不是配置约定。这正是 4.9 节模型消融实验里"调 / 不调记忆"这一变量的实际实现。服务不可用时钩子会记录一条错误并降级为无记忆继续运行，不阻塞智能体。

### 5. 评测复现流程

对应答题要求中的"量化评测实施方案"：本报告全部量化结论按以下固定顺序产出与核对，任何人可按此顺序重新走一遍。

1. `pip install -r requirements.txt`——唯一第三方依赖 numpy。
2. `cd 可复现性体系 && python reproduce_L1.py`——纯 Python 重跑，任何机器可执行，无需麒麟环境，2~3 分钟内输出「合计 N 条主张：通过 M、不符 2、跳过 0」，与《当前数字看板.md》逐条核对。
3. 需要麒麟真机的部分：确认 `~/restore_env.sh` 已跑通、`sudo setstatus -f exectl off` 放行执行控制后，运行 `python3 measure_L2.py`，测量完毕执行 `sudo setstatus -f exectl warning` 恢复安全策略。
4. 每次指标发生变化后，重跑 `python 可复现性体系/生成数字看板.py` 更新权威计数，再跑 `python 可复现性体系/check_report_numbers.py` 核对本报告正文里的数字与看板是否一致——退出码非零即表示有数字未同步。
5. 变异测试自检（可选，验证"检测器本身有效"而非验证结论）：`python mutate.py --all`。

完整的操作细节、每步预期耗时与常见问题，见《准备复现.md》与《可复现性体系/可复现性说明.md》第四节；本节只给出固定顺序。
