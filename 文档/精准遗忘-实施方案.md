## 〇、为什么不是"删除"

看过现有代码后，三个事实决定了设计：

```
① vector_store.drop() 是整集合删除，没有按条删的接口
② memory_service.py 注释明写：「只读场景：绝不调用 store.create()」，索引归 build_knowledge_index.py 管
③ supersede 根本不删向量 —— apply_supersede_filter() 读一张边表，查询时把被取代的单元滤掉
```

所以「遗忘」的正确形态是 **supersede 的兄弟**：一张**遗忘账本** + 一个**查询时过滤器**。

```
优点
  · 冻结的 17 个文件、语料、索引一字节不动
  · 可逆（撤销遗忘 = 账本追加一条反向记录）
  · 可审计（谁、何时、凭什么指令、忘了哪条）
  · 与现有架构一致，diff 小
```

**「精准」体现在两处**：定位到具体单元（`stable_key`，重挖不变），以及**两步确认**——
自然语言天然有歧义，先回显候选再确认，才不会忘错。

## 二、实现

### 2.1 遗忘账本 `记忆服务/forget_ledger.jsonl`

追加写，永不改写既有行：

```json
{"ts":"2026-09-12T10:00:00","op":"forget","stable_key":"case:...","doc_id":12,
 "instruction":"忘掉那条 sqlite3 找不到命令的记录","text_sha256":"...","confirmed":true}
{"ts":"...","op":"unforget","stable_key":"case:...","reason":"误操作"}
```

生效状态 = 按 `stable_key` 取**最后一条**的 `op`。

**账本路径由启动参数指定**（`--forget-ledger`），评测用独立账本，不污染生产账本。

### 2.2 两步接口

```
POST /forget   {"instruction": "忘掉那条 sqlite3 找不到命令的记录", "k": 5}
   → 第一步（定位）：把 instruction 当 query 走【现有】检索链，返回候选
     {"candidates":[{"doc_id":12,"stable_key":"case:...","type":"case","text":"...前 200 字"}, ...],
      "note":"未执行遗忘，请用 confirm_doc_id 确认"}

POST /forget   {"instruction": "...", "confirm_doc_id": 12}
   → 第二步（确认）：校验 doc_id 在第一步候选内 → 追加账本 → 返回
     {"forgotten":{"doc_id":12,"stable_key":"case:..."},"ledger_size":N}

POST /unforget {"stable_key": "case:..."}            撤销
GET  /forgotten                                      列出当前生效的遗忘
```

**定位复用 `_retrieve_ablation()` 原样**——遗忘指令的"理解"就是检索本身，不另写解析器。
这正是「自然语言指令驱动」最诚实的实现：指令怎么描述记忆，检索就怎么找到它。

### 2.3 过滤器

`memory_service.retrieve()` 里，`_retrieve_ablation()` 返回 `hit_ids` 之后、截 `[:k]` 之前：

```python
hit_ids = apply_forget_filter(hit_ids, self.docs, self.forget_ledger)
```

与 `apply_supersede_filter` 同形：按 `stable_key` 查账本生效状态，滤掉已遗忘的。

🔴 **过滤在截断之前**，否则忘掉 top-1 后返回 k-1 条，行为不一致。

### 2.4 `stable_key` 怎么拿

`docs.meta` 里若已有 `stable_key` 直接用；没有则按 `mine_conflicts.stable_key(unit_raw, kind)` 现算。
**不要自己发明第二种 key**——重挖后 `doc_id` 会变，`stable_key` 不会，这是它存在的意义。

## 三、评测（零 LLM 裁判，复用冻结评测集）

### 3.1 思路

`评测集/eval_set.jsonl` 227 题覆盖 77 个 gold doc。**它本身就是"某条记忆还能不能被检索到"的探针**：

```
遗忘 doc D 之前   gold=D 的题，D 在 top-k 里（按原始命中率）
遗忘 doc D 之后   gold=D 的题，D 必须不在 top-k       → 遗忘生效
                  gold≠D 的题，命中集合必须不变         → 精准（无副作用）
```

两个指标都是**集合比较**，纯机械，不需要任何人或模型判断"忘得对不对"。

### 3.2 任务集 `记忆服务/遗忘评测/forget_tasks.jsonl`（20 条）

```json
{"task_id":"F-01","instruction":"忘掉那条 sqlite3 找不到命令的处理记录","gold_doc_id":0,"gold_stable_key":"case:..."}
```

**人工写 20 条**，覆盖 20 个不同的 gold doc（case / workflow 都要有）。

🔴 **措辞必须与评测集里对应的问题不同**——否则定位准确率是靠字面重合刷出来的。
写法：描述那条记忆"是关于什么的"，不抄评测题。

### 3.3 三个指标

| 指标 | 算法 | 意义 |
|---|---|---|
| **定位准确率** | 第一步返回的 top-1 `doc_id == gold_doc_id` 的比例 | 自然语言指令能不能找对那条 |
| **遗忘生效率** | 确认后，gold=D 的所有评测题重跑，D 不在 top-10 的比例 | 忘了就真找不到 |
| **副作用率** | 确认后，gold≠D 的 226 题重跑，top-10 集合与遗忘前**逐题相同**的比例 | 只忘该忘的 |

**副作用率是「精准」二字的证据**，三个里最重要。目标：100%，且这是**可达**的——
过滤只动一个 `stable_key`，理论上不该碰别的题；若不是 100%，说明实现有 bug，不是指标"没达标"。

### 3.4 流程（每条任务独立，账本每次清空）

```
① 清空评测账本
② 跑 227 题基线 → hits_before[q] = top-10 集合        （只跑一次，所有任务共用）
③ 对每条 F-xx：
   a. POST /forget {instruction}          → 记 top-1，算定位准确率
   b. POST /forget {confirm_doc_id: gold} → 强制按 gold 确认（评测的是遗忘，不是定位错了以后怎么办）
   c. 跑 227 题 → hits_after[q]
   d. 遗忘生效：gold=D 的题，D ∉ hits_after[q]
      副作用：  gold≠D 的题，hits_after[q] == hits_before[q]
   e. POST /unforget，复位
④ 汇总三个指标，落 runs_forget.jsonl（每题每任务一行，含 before/after 集合）
```

**b 步用 gold 强制确认**：定位和遗忘是两个独立能力，分开测。定位错了走确认流程本来就会被人拦下。

### 3.5 计分 L1，生成 L2

```
runs_forget.jsonl 已落盘 → score_forget.py 纯 Python 重算三个指标   → L1，评委任何机器可复现
跑检索需要 embedding 服务                                          → L2
```

与模型消融、BGE 对照同一套分层。
