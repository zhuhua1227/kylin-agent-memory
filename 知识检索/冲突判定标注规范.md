## 一、功能性定义（一切从这一句推导）

> **知识冲突 = 若检索系统今天把「旧的那条」返回给使用者，会造成误导；
> 而「新的那条」正是取代它的。**

这个定义直接来自模块要解决的问题：OS Agent 的长期记忆**不能把已经作废的事实当成有效知识服务出去**。

判断任何一对时，把自己放在使用者位置上问：**今天系统返回旧的这条，我会不会被坑？**

---

## 二、三个必要条件（缺一不可）

```
① 同一知识对象   —— 两条讲的是同一件事
② 取代关系       —— 新的让旧的不再成立，而不是在旧的之外补充
③ 旧的曾经是有效知识 —— 它曾经处于"可被检索到"的稳定状态
```

第 ③ 条是这份规范里最容易被忽略、也是这次分歧的根源，见 §四。

## 三、判否清单（满足任一即**不是**冲突）

| 情形 | 说明 | 真实判例 |
|---|---|---|
| **纯追加** | 新内容加在旧内容之外，旧的仍然成立 | `append_only` 那 91 条 |
| **润色** | 换个说法，信息量没变 | **K-0067**：music-sweep 删掉"organize+lyrics"几个字，语义未变 |
| **细化** | 旧的是概括，新的是展开，两者并存无矛盾 | — |
| **无关** | 根本不是同一件事 | 设计方案 §六.2 的"两条无关知识"负例 |
| **部分推翻但核心用途未变** | 旧的某个次要细节被否定，但它的主要用途不受影响 | 见 §五 第 2b 步 |
| **撰写过程中的自我修正** | 见 §四 | K-0002 / K-0042 / K-0098 |

## 四、🔴 撰写过程中的自我修正 —— 不计为冲突

### 裁定

> **同一会话 且 同一天**内发生的修改，视为撰写过程的自我修正，**不计为知识冲突**。

### 理由（从 §一 的功能定义推出，不是为了方便）

被修改掉的那个中间状态，**从来没有成为过"可被检索到的知识"**——
它没有跨过任何一次会话边界，检索系统永远不可能把它返回给任何人。

按 §一 的判据："今天系统返回旧的这条会不会坑我"——**系统根本不会返回它**，
因为它从未作为稳定状态存在过。**故不构成冲突。**

### ⚠️ 必须声明的两件事

**① 这条排除是原设计就有的，不是这次为了数字新加的。**
`mine_conflicts.py` 的 `same_sitting` 结构过滤在本次分歧之前就存在，
其存在理由正是本节所述。本规范是把它**写成文字**，不是新增规则。

**② 它对准确率的影响必须如实披露。**
采用本条 → 34/36；不采用（纯语义口径）→ 31/36。
**两个数都要报**，本条作主口径并附本节理由，纯语义口径作敏感性分析。
**三个口径（含现状 35/36）在 n=36 下都够不着 88%**，所以这个选择不存在"挑对自己有利的"空间。

### 为什么不是"同一会话"而是"同一会话 **且** 同一天"

实测有会话横跨 **23 天**（`session_id=1cd1ff9f`，2026-07-13→08-13）。
只按 session 排除会误杀真实的跨天知识变化。**两个条件必须同时满足才排除。**

## 五、判定流程（按顺序走，第一个命中即定案）

```
1. 两条讲的是同一件事吗？
   否 → 不是冲突（无关）

2. 新的只是在旧的之外补充内容，旧的仍然成立吗？
   是 → 不是冲突（纯追加）

2b. 【部分推翻】旧的一半成立、一半被否时：
   被否掉的那部分，足以让使用者据此做出错误决定吗？
   否 → 不是冲突（次要细节变动）
   是 → 继续往下走
   （判例 K-0052 · server-pve-network：旧条断言"不经过软路由/代理"，其中"不经过软路由"仍成立、
     "不经过代理"被否；而后者正是驱动"只能靠 DNS 优化"这个实用结论的那一半 → 算冲突）

3. 换了说法但信息量没变吗？
   是 → 不是冲突（润色）

4. 同一会话 且 同一天吗？
   是 → 不是冲突（撰写过程自我修正，见 §四）

5. 到这里 = 冲突。继续判 reason_kind：
   · 旧结论【当时就是错的】      → reason_kind = 旧结论当时为假
   · 旧结论【当时对，后来前提变了】 → reason_kind = 前提消失
```

**第 4 步的位置很重要**：它排在语义判断**之后**。
先判语义上有没有取代关系，再看是不是同一次写作——
**顺序反了，就会重演"看到结构标签就不读内容"那个错误**。

### 🔴 2026-09-07 新增：史注格式引发的两类规则失效

> **补充时点声明**：本节四条判例在**留出集裁决完成之后**补入。
> **`mine_conflicts.py` 未随之修改**（冻结生效中）——这里记录的是
> **已诊断、待修的局限**，不是对判定结果的追认，也未用于重算任何指标。

根因是**一个交互缺陷**，不是任何一边单独的错：

```
提示词 B 组⑤ 要求笔记写成    「读数：<值>（原为 <旧值>，已不再是）」
挖掘器 append_only 判据用的是  「旧文本 ⊂ 新文本」子串匹配
两者一交互 → 两个方向都会失效
```

| conflict_id | 形态 | 规则判 | 正确判 | 说明 |
|---|---|---|---|---|
| **HO-K-0053** | 当前值未变（两段都是 3），只有「原为 2 / 原为 3」这句史注不同 | conflict | **不是冲突** | 文本有差异所以进了候选池，但**当前状态未变、无信息量变化**。是 K-0067（润色）的变体，称**史注漂移** |
| **HO-K-0036** | 同上（两段都是 0） | conflict | **不是冲突** | 同上 |
| **HO-K-0204** | 运行态读数被下一次复测整体取代（PID 35559 → 35562） | not_conflict | **是冲突** | 旧值被写进史注 → 旧文本成了新文本子串 → 误判为纯追加 |
| **HO-K-0247** | 旧条整条即 PID 断言，被新读数取代，旧值仅存于史注内 | not_conflict | **是冲突** | 同上，称**假追加**——是 K-0067 型局限的**反向**情形 |

**对 §三「纯追加」那条的补充**：判否条件写的是「新内容加在旧内容之外，**旧的仍然成立**」。
史注格式下**旧的并不成立**（它已被取代），只是文本上仍作为子串存在。
**判「纯追加」时要看语义上旧断言还成不成立，不能只看文本包含关系。**

**已知代价**：这四条即留出集 60 条里的全部 4 处误判（准确率 56/60 = 93.3%）。
两个方向都修好后留出集应为 60/60——**该缺陷当前是在压低成绩，不是抬高**。

## 七、使用规则

1. **任何一次裁决都必须在记录里写明所依据的规范版本号**（本文件 v1.0）
2. 裁决时**先看内容、后看结构标签**——结构标签只用于 §五 第 4 步，不得用于第 1~3 步
3. 遇到本规范未覆盖的情形：**先补进 §六 判例表，再裁**，不要临时发挥
3b. 🔴 **引用任何一对时一律用 `conflict_id`（K-xxxx），永远不要用 `eval_id`**——
    后者是行位置产物，重挖即失效（v1.0.1 修的就是这个）
4. 本规范一旦冻结，**不得为了让某个数字好看而修改**；确需修订时必须
   记录修订理由、修订前后的数字，并保留旧版本
