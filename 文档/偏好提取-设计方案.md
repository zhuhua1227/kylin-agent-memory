# 偏好提取 · 设计方案

> **对应赛题**：题目内容 (2)「构建偏好记忆动态捕捉模块，基于多源融合数据，实现用户**操作习惯、输出风格、安全策略**等偏好的自动提取与**版本化管理**，实现**跨场景偏好适配与回溯**」
> **对应评分**：技术创新性 30 分的三个点名子项之一 + 性能指标「偏好提取准确率 ≥85%」（约 6.25 分）
> **当前状态**：零实现。与知识冲突处理并列为最大的未开垦分值。
> **接口依据**：字段名与调用方式已按真实代码校对（见 §8 注册点清单）

---

## 〇、一句话

**用前期数据提取"这个用户在什么情境下倾向怎么做"，去预测留出期的真实行为，命中率就是准确率。**

标准答案是**留出期的真实行为记录**，不是人的判断——**零人工标注、零循环论证、n 可以做到几百**。这是它相对知识冲突模块（n=18、需人工裁决）的最大结构优势。

---

## 一、口径：不区分动作的选择主体（2026-08-15 已定）

**本方案中"用户偏好"的操作性定义**：该用户在其 Agent 交互轨迹中**稳定表现出**的操作模式与约束表达，**不区分**具体动作由用户直接指定还是由 Agent 在用户授权下选择。

三条依据，**必须写进报告**（主动定义比等评委问出来强）：

1. 赛题背景原文明确把「**工具调用执行结果**」列为两类记忆的核心数据源之一
2. 记忆系统服务的对象是"用户 + Agent"这一交互整体，拆分对系统能力无影响
3. 下游价值在于"下次遇到同类情境能否复用既有模式"，该价值与动作的选择主体无关

> **可选加固**（性价比高、不需新数据）：同一个 Agent 在两个环境（Windows 老数据 / 麒麟新数据）下提取出的偏好如果明显不同，就证明**偏好是情境条件化的，不是模型烧死的默认行为**。这直接堵死"那只是 Claude Code 的默认行为"这句质疑。

## 二、三类偏好各自的信号来源

| 赛题类别 | 主信号 | 数据位置 | 主体归属 |
|---|---|---|---|
| **操作习惯** | 同一情境下的工具/参数/顺序选择 | `tool_execution` | 交互整体（按 §1 口径） |
| **输出风格** | 用户对产出形式的要求 + 实际产出物形态 | `user_input.text` + `tool_input.file_path` 后缀 | 用户为主 |
| **安全策略** | **`execution_status == "user_rejected"`** + 用户显式约束表达 | `tool_execution` + `user_input` | **纯用户，无归属争议** |

### 2.1 安全策略这一类没有主体归属问题

老数据集有 **4,664 条 `user_rejected` 记录（占 tool_execution 的 33.2%）**。

四轮复核里我一直把它当**污染**（对案例挖掘确实是——它们不是技术故障），但**对偏好提取它是金矿**：

> **用户拒绝了什么，比 Agent 做了什么更能说明偏好，而且这是用户的真实决定，不存在"这是谁选的"的争议。**

同一批数据，对一个模块是噪声、对另一个模块是信号。这一点值得写进报告。

配合 `user_input` 里的显式约束表达（"不要直接结束进程""先不要删除""暂时不要修改""只列出来""不要覆盖"），安全策略这一类的证据强度是三类里最高的。

### 2.2 输出风格的双通道

- **要求侧**：`user_input.text` 里的格式要求（"整理成 markdown 报告""把关键结果整理出来""列成表格"）
- **产出侧**：实际写出的文件类型分布（`.md` vs `.txt` vs `.json`）、报告内是否用表格、结论是否前置

两侧一致 → 强偏好；只有要求侧 → 说明 Agent 没照做（这本身是"对齐度"信息，见 §5.3）。

```json
{
  "pref_id": "P-0007",
  "category": "operation_habit",
  "statement": "内容搜索任务倾向用 rg 而非 grep",
  "trigger": {"kind": "tool_intent", "match": "content_search"},
  "choice": {"observed": "rg", "alternatives": ["grep", "findstr", "Select-String"]},
  "support": {
    "n_trigger": 47, "n_choice": 41, "ratio": 0.872,
    "n_sessions": 9, "first_seen": "2026-07-05T...", "last_seen": "2026-08-13T..."
  },
  "scenario": {"project_hint": "windows", "n_by_scenario": {"windows": 44, "kylin": 3}},
  "version": 1,
  "supersedes": null,
  "superseded_by": null,
  "stable_key": "pref:operation_habit:content_search"

```

**四个设计点**：

1. **`stable_key` 用语义键不用序号** —— 直接沿用冲突模块 §0.1 的教训（`doc_id` 是 `enumerate` 下标，重挖即重排）
2. **`support` 必须完整落盘** —— `n_trigger` / `n_choice` / `ratio` / `n_sessions` 缺一不可。只报 ratio 不报 n，等于没报（4/4=100% 和 41/47=87% 不是一回事）
3. **`scenario` 是跨场景适配的落地** —— 同一偏好在不同环境下的支持度分开记，这是赛题要求 (2) 里"跨场景偏好适配"的直接实现
4. **`supersedes` / `superseded_by` 直接复用冲突模块** —— 见 §5

## 四、提取机制（L1 确定性，不调 LLM）

```python
# 知识检索/mine_preferences.py

def extract(records, min_trigger=8, min_ratio=0.65, min_sessions=2):
    """从多源记录里提取稳定的情境-选择偏好。

    ⚠️ 三道门槛缺一不可，理由分别是：
      min_trigger  情境出现太少，比例没有意义（4/4=100% 说明不了什么）
      min_ratio    低于此值说明这个情境下并无稳定倾向，是随机的
      min_sessions 只在一个会话里出现的是一次性做法，不是习惯
                   （同 mine_templates.py 的跨会话判据，那边踩过
                    "用出现次数冒充会话数"的坑，R2-22 bug③）

    确定性、不调 LLM——这是它能进 L1、能被 mutate.py 保护、
    能公开测"提取准确率"的前提。
    """
```

**情境（trigger）的定义是本模块成败的关键**，与冲突模块的"签名粒度"同理：

| 情境类型 | 判据 | 反例（粒度太粗，会把不相关的聚在一起） |
|---|---|---|
| 工具意图 | 命令首动词归一化后的语义类（搜索/查看/编辑/网络…） | ❌ 直接用 `tool_name`（Bash 占 70%，等于没分） |
| 失败后续 | `is_error=True` 之后一步的动作类别 | ❌ 用 `exit code N`（冲突模块实测：6 个不相关问题聚成一组） |
| 破坏性操作前 | `rm`/`mv`/覆盖写 之前一步是什么 | |
| 产出形式 | 写文件时的扩展名与结构 | |

**剥壳复用**：命令首动词要用 `mine_cases.py` 已有的 `inner_verb()`——它已做到类级通用（第四轮实测未点名新形态 15/15 通过），**不要另写一个**。

## 五、版本化 / 跨场景 / 回溯：直接复用冲突模块

赛题要求 (2) 的后半段（版本化管理、跨场景适配、回溯）**不需要另造机制**：

### 5.1 偏好的版本变更就是一种知识冲突

> 用户中途改了规则（"以后不用每次都问了"）→ 旧偏好被新偏好推翻 → **这就是 T2 方法推翻**。

复用 `mine_conflicts.py` 已建成的：`adjudicate()` 裁决 + `build_supersede_edges()` 建链 + `retrieve_old()` 回溯。

**唯一要新增的是触发检测**：同一 `stable_key` 的偏好，在不同时间窗口下 `choice.observed` 变了 → 生成一条偏好冲突。

### 5.2 跨场景适配

`scenario.n_by_scenario` 已在 schema 里。场景标识从 `user_input.project` 字段推断（老数据是 Windows 路径如 `I:\SillyTavern-release`、`C:\Users\...`；新数据是 `/home/device_b/...`）。

检索/应用偏好时按当前场景过滤或加权——这就是"适配"。

### 5.3 对齐度（附加产出，不是硬指标）

`my_rules.md`（若你写了）与提取结果的一致性 = **Agent 行为是否符合用户声明的偏好**。
这是**对齐度**，不是提取准确率，**分开报**。它不承重（主指标是 §6 的行为预测），是加分旁证。

## 六、★ 评测：时间切分行为预测

### 6.1 核心流程

```
按时间切分 → 训练期 T1（前 60%）/ 留出期 T2（后 40%）
T1 提取偏好集合 P
T2 找出所有触发情境
对每个触发情境：用 P 预测会做什么选择
与 T2 里的真实选择比对
准确率 = 命中数 / 触发情境总数
```

**标准答案是留出期的真实行为记录，不需要任何人工标注。**

### 6.2 🔴 切分泄漏：会话可以跨 23 天

冲突模块挖掘时发现的事实：**本数据集里 Claude Code 会话可以跨天恢复**，最长一个会话 `session_id=1cd1ff9f` **横跨 23 天**（2026-07-13 → 2026-08-13）。

**纯按时间戳切分会把同一个会话拦腰切断**——同一会话的前半段预测自己的后半段，情境几乎相同、任务连续，这是泄漏，会把准确率虚抬。

**必须按会话完整性切分**：

```python
def split_by_time_keeping_sessions(records, train_ratio=0.6):
    """按会话起始时间排序，整个会话归入同一侧，不切断会话。

    ⚠️ 不能纯按 record 的 timestamp 切——本数据集里会话可跨天恢复
    （实测最长一个会话横跨 23 天）。拦腰切断会让同一会话的前半段
    预测自己的后半段，情境几乎相同，属泄漏，准确率会虚高。

    时间戳格式是 normalize_time.py 产出的 ISO8601 UTC
    （2026-07-31T09:31:13.404000+00:00），字典序即时间序，可直接排序。
    """
    starts = {}
    for r in records:
        s = r.get("session_id")
        t = r.get("timestamp", "")
        if s and (s not in starts or t < starts[s]):
            starts[s] = t
    ordered = sorted(starts, key=lambda s: starts[s])
    cut = int(len(ordered) * train_ratio)
    train_sess, test_sess = set(ordered[:cut]), set(ordered[cut:])
    return ([r for r in records if r.get("session_id") in train_sess],
            [r for r in records if r.get("session_id") in test_sess])
```

### 6.3 🔴 必须有多数基线（E-1 教训的直接迁移）

**如果"总是选该情境下最常见的那个选项"就能拿到 85%，那偏好提取本身没有价值。**

这与评测集那个词面 shortcut 是同一类问题：第一轮实测过，一个 40 行的字符串脚本在 close 档上比整套 SDK 还准。**同样的陷阱在这里的形态是：某个选择本来就占 85%，提取器只是复读了这个分布。**

必须实现并同报三个数：

| 口径 | 说明 |
|---|---|
| **提取器准确率** | 用 T1 提取的偏好预测 T2 |
| **多数基线** | 总是选 T1 里该情境下最高频的选项 |
| **提升幅度** | 两者之差 —— **这才是模块的真实贡献** |

**报告的主指标应该是提升幅度，不是裸准确率。** 参照评测层把主指标从总体切到 hard 档的做法。

### 6.4 冻结

虽然不需要人工标注，仍要冻结（否则"切分点是不是挑出来的"没法自证）：

- 切分点（会话列表哈希）
- T1 提取出的偏好集合 `preferences.jsonl` 的 sha256
- 语料哈希（`memory_source_records.jsonl`）

照 `review_and_freeze_conflicts.py` / `review_and_freeze.py` 的模式，写文件时 `newline="\n"`（CRLF 会让跨平台哈希不一致，破坏外部锚定）。

## 七、阴性验证（进 `test_detectors.py` + `mutate.py`）

写法照 `test_detectors.py:308` 的 `test_mine_cases_k1()`：**import 真实模块 + 手造最小反例 + 调真实函数 + `check()` 双重断言**（"不该产出的没产出" **且** "对应 stats 计数器动了"）。

```python
def test_preference_extractor_negatives():
    print("\nN. 偏好提取（必须拦住这五类假偏好）")
    import mine_preferences

    # ① 支持度不足：情境只出现 3 次，不得产出偏好
    check("偏好-低支持度不产出", ... and stats["rejected_by_min_trigger"] >= 1)

    # ② 单会话：只在一个会话出现的做法不是习惯
    #    （mine_templates R2-22 bug③ 踩过"用出现次数冒充会话数"的坑）
    check("偏好-单会话不产出", ... and stats["rejected_by_min_sessions"] >= 1)

    # ③ 比例不足：情境下选择五五开，不构成倾向
    check("偏好-无稳定倾向不产出", ... and stats["rejected_by_min_ratio"] >= 1)

    # ④ 🔴 切分不得切断会话
    tr, te = mine_preferences.split_by_time_keeping_sessions(cross_day_session_recs())
    check("偏好-跨天会话不被切断",
          not (set(r["session_id"] for r in tr) & set(r["session_id"] for r in te)))

    # ⑤ 🔴 打乱时间顺序后，准确率必须掉到基线水平
    #    否则说明提取器根本没在用时间信息，"行为预测"是假的
    acc_real = mine_preferences.evaluate(records)["accuracy"]
    acc_shuf = mine_preferences.evaluate(shuffle_time(records))["accuracy"]
    check("偏好-时间打乱后准确率显著下降", acc_real - acc_shuf > 0.05,
          f"real={acc_real:.3f} shuffled={acc_shuf:.3f}")
```

## 九、报告里必须写的四段

1. **口径定义**（§1 那三条依据）——主动定义，别等评委问
2. **多数基线与提升幅度**——裸准确率不能单独出现，参照评测层"主指标切 hard 档"的做法
3. **切分泄漏的处理**——说明为什么按会话切而不是按时间戳切，并给出会话跨 23 天这个实测依据
4. **样本量与 Wilson 区间**——n 与区间同时给。若提升幅度的区间跨 0，明确写"不能证明提取器优于多数基线"，按赛题「未达基础指标需明确优化方向」处理

**这四段不是免责声明，是这个模块可信度的一部分。** 冲突模块主动说破"verdict 18/18 是问题结构决定的、不是规则聪明"，那一段是它最有说服力的地方——偏好模块照这个标准来。
