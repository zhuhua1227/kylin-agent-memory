# 记忆服务 · 说明报告

> 依据《记忆服务与pi对照实验-设计方案.md》批次一。**麒麟机上常驻的 HTTP 查询接口**，
> 把本项目的知识检索能力封装成 OS Agent 可调用的接口（roadmap 阶段 04 的
> 「将记忆能力封装为 OS Agent 可调用的接口」）。

---

## 一、这是什么

| | |
|---|---|
| 服务端 | `memory_service.py` —— 纯标准库 `http.server`，只监听 `127.0.0.1:8077`，不引框架、不装包 |
| 客户端钩子 | `rag-memory.ts` —— pi coding agent 的行动前记忆注入钩子（`--memory on/off`） |
| 启动 | `start_memory_service.sh`（nohup 常驻；磐石不可变系统无持久 systemd 单元） |
| 冒烟验收 | `smoke_service.py`（5 条手工查询，全部 < 500ms + 结构合法 + config 回声一致） |
| 对照验收 | `verify_diff.py`（两组 payload 逐字比对：system prompt 相同、off 组不调接口） |

检索管线**复用**现成件（`向量化常驻服务/embedding_client.py`、`知识检索/vector_store.py`、
`评测集/measure_recall.py:retrieve_ablation`），不重新发明；原文由 `DocStore` 取回。

## 二、接口契约

### `POST /retrieve`

```
请求  {"query": "任务描述文本", "k": 5}          k ∈ [1,50]，默认 5
响应  {
  "units": [
    {"doc_id": 23, "type": "case", "text": "【历史案例】…", "score": 0.83},
    …
  ],
  "config": "all",          ← 必回显，证明用的是哪一套检索配置
  "elapsed_ms": 74.3
}
错误  400 入参非法 / 500 检索异常（回包含 error 字符串与 config，不掐连接）
```

- `score` 只作参考：对 `naive` 是排序依据本身；对带重排的档是"向量层"相似度，
  **不是最终排序依据**，调用方勿当排名字段。

### `GET /health`

```
{"ok": true, "index_size": 86, "config": "all", "backend": "kylin"}
```

### 自然语言指令驱动的精准遗忘（《精准遗忘-实施方案.md》）

不删向量、只加账本 + 查询时过滤，与 supersede 同形（`forget_ledger.py`）：

```
POST /forget   {"instruction": "...", "k": 5}
  → 第一步·定位（instruction 当 query 走现有检索链，只查不写）
  {"candidates": [{"doc_id","stable_key","type","text"}...],
   "note": "未执行遗忘，请用 confirm_doc_id 确认"}

POST /forget   {"instruction": "...", "confirm_doc_id": 12}
  → 第二步·确认（doc_id 须落在按同一 instruction 重新算出的候选内才写账本，
    无状态设计，不需要服务端记住"第一步返回过什么"）
  {"forgotten": {"doc_id": 12, "stable_key": "case:..."}, "ledger_size": N}

POST /unforget {"stable_key": "..."}      撤销
GET  /forgotten                          列出当前生效的遗忘
```

`--forget-ledger` 指定账本路径（默认与本脚本同目录 `forget_ledger.jsonl`），
评测跑独立账本、不污染生产账本。评测流程与三个指标（定位准确率/遗忘生效率/
副作用率）见 `遗忘评测/预登记.md`；本地单测（零依赖，不需要 device_c/embedding）
见 `test_forget_ledger.py`。

## 三、两条硬约束（设计方案 §1.3）落实

1. **`config` 禁止 `meta_oracle`**：`main()` 启动时若 `--config meta_oracle` 直接
   `SystemExit` 拒绝启动。理由：那一档用标准答案自身的 `knowledge_type` 做过滤，
   是标签泄漏、是上界不是能力。
2. **`config` 走启动参数、不写死**：`--config`（默认 `all`）/ `--backend`（默认 `kylin`）/
   `--collection` / `--docs` / `--port`。报告声明系统用哪档，服务就跑哪档。

其他：单线程 `HTTPServer` 是**刻意**的——`emb_serverd`/`ve_serverd` 的管道协议不是并发安全的，
并发请求会错位；检索 P95 ≈ 112ms，单线程完全覆盖演示与实验流量。
启动时预热**完整跑一次检索链**（不只 encode），把 KYSDK 首调开销消化在启动期。

## 四、它在模型消融 4×2 里的角色

`rag-memory.ts` 的 `--memory` 开关就是消融的「调 / 不调记忆」变量：

```
--memory on   before_agent_start 事件里 POST /retrieve → 把 units 拼成注入块
              → context 事件里 splice 到最后一条 user 消息前（系统提示之后、任务之前）
--memory off  完全不调接口，其余一字不变（不是删提示词）
```

- **两组 system prompt 逐字相同由构造保证**：本扩展从不改写系统提示。
- 每次注入记 `injected_doc_ids` → `runs.jsonl`（可回溯注入了什么）。
- 服务挂了不阻塞 agent：落一条 error 记录后按无记忆继续（降级路径也可演示）。

⚠️ 消融实验最终没走 pi 的 agent loop（回答型任务、零 LLM 裁判，见
`评测集/模型消融/模型消融4x2-报告-v2.md` §一），`run_ablation.py` / `run_krow.py`
直接调 `:8077/retrieve` + llama-server / 云端 API。`rag-memory.ts` 是批次一的
「记忆能力可被真实 agent 框架消费」的证据，本身已冒烟验收。

## 五、启动与验收

```bash
# 麒麟机（重启后先 ~/restore_env.sh 恢复 KYSDK）
bash 记忆服务/start_memory_service.sh              # config=all backend=kylin，默认
python3 记忆服务/smoke_service.py --config all     # 冒烟：5 条查询全 < 500ms

# 换检索档
CONFIG=naive bash 记忆服务/start_memory_service.sh
```

- `verify_diff.py` 读 `~/RAG/memory_service/payload_log/*.json`（批次一冒烟时落的
  两组 payload，运行态产物，不在本仓）；它记录的是**当初怎么验的**，复跑需重新
  产 payload。

## 六、部署位置

```
麒麟机（device_c）  ~/RAG/memory_service/    ← 运行目录（服务端 + runs.jsonl + payload_log）
              知识目录、向量集合由 build_knowledge_index.py 管，本服务只读、绝不 store.create()
本仓          记忆服务/                  ← 源码提交物（本目录）
```

服务端只读向量集合；重启服务是「重建索引后刷新」的手段，不碰索引本身。
