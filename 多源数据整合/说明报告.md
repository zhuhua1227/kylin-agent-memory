## 一、为什么做这件事

比赛 roadmap 阶段02 第一个模块要求"支持工具执行结果、用户行为数据、手动配置信息等数据的统一接入"。此前团队担心找不到真实数据，只能用几句手造的示例文本（见"端到端最小管线"任务）。

调查发现：**团队自己日常使用的两套系统，天然积累了大量真实的"agent 工具调用 + 执行结果"数据**——这正是路线图要的数据源，而且是真实数据，比人工编造更有说服力，还免费。

### 范围决策记录（重要，答辩可能被问到，如实记录过程）

调查之初曾假设 OpenClaw 里某些 agent（如 mako）是"纯技术用途、不涉及第三方隐私"，据此向用户提议方案。**后经查 OpenClaw 主配置文件 `openclaw.json` 的 `bindings` 字段，发现这个假设是错的**：

```
lucy   → 绑定飞书 bot_main（用户私人使用）
maya   → 绑定飞书 bot_qg（另一飞书账号）
mako   → 绑定QQ机器人 "main" 账号（对接真实QQ用户，并非纯技术用途）
butler → 绑定QQ机器人 "family" 账号（对接家人群）
```

修正后确认：**当前活跃的4个 agent 中，只有 lucy 是用户私人使用、不直接对接第三方群聊的**，因此最终范围收窄为**仅使用 lucy 一个 agent 的数据**，其余三个（涉及真实第三方隐私）明确排除；另有3个已停用、不在当前配置中的历史 agent 目录（main/assistant_v2/flarum_bot）来源不明，本次也不纳入。

**教训**：调查真实数据源时，"名字听起来像技术用途"不能作为隐私判断依据，必须去查实际的配置/绑定关系。

## 三、统一数据格式

```json
{
  "source": "claude_code | openclaw_lucy",
  "session_id": "该条记录所属会话的唯一标识",
  "timestamp": "记录发生时间（两个来源格式不同，见第六节已知限制）",

  "tool_input": {"...": "调用参数，结构因工具而异"},

```

两个来源虽然原始格式不同（见第四节），但提取后统一转换成上面这个结构，实现了 roadmap 要求的"格式标准化"。

## 四、提取方法（两个来源格式不同，踩过的坑）

### 4.1 Claude Code（`extract_claude_code.py`）

一次工具调用在原始记录里分两部分体现：
- 一条 assistant 消息的 `content` 数组里有一个 `type="tool_use"` 的块（带 `id`/`name`/`input`）；
- 随后一条消息里有一个 `type="tool_result"` 块（带 `tool_use_id`，与上面的 `id` 对应，带 `content` 即执行结果）。

脚本先扫一遍收集所有 `tool_use`，再扫一遍收集所有 `tool_result`，按 id 配对，两边都有的才输出。

**防御性设计**：Claude Code 官方文档明确说明这个 JSONL 内部格式会随版本变化、不保证兼容，所以脚本对每一行都做 try/except，解析失败直接跳过，不让个别"看不懂"的记录中断整体提取。

### 4.2 OpenClaw lucy（`extract_openclaw_lucy.py`）

**最初直接套用 Claude Code 的解析逻辑，结果提取到 0 条记录**——原以为两边格式一样，实测发现完全不同：

| | Claude Code | OpenClaw |
|---|---|---|
| 调用块类型名 | `tool_use` | `toolCall` |
| 调用块字段 | `id` / `name` / `input` | `id` / `name` / `arguments` |
| 执行结果的位置 | 嵌套在某个 content 块里（`type="tool_result"`） | **独立的一整条消息**（`role="toolResult"`） |
| 配对键 | 块内的 `tool_use_id` | 消息级别的 `toolCallId` |

发现问题后重新写了针对 OpenClaw 真实格式的解析逻辑，才提取出 188 条记录。**这也是本报告想强调的一点：不要假设"看起来差不多的系统内部格式也差不多"，务必先用真实样本核实数据结构，再写解析代码。**

本次只处理了 lucy 目录下的"普通" `.jsonl` 消息记录文件，`.trajectory.jsonl`（OpenTelemetry 风格的全量上下文快照格式）暂未处理，原因和后续计划见第六节。

## 五、脱敏处理（重点，多次踩坑迭代出来的）

`anonymize.py` 是两个提取脚本共用的脱敏模块，**递归**遍历任意深度的 JSON 结构（不止查顶层字段）。这个设计要求本身就来自一次真实事故：

> 调查 OpenClaw 配置时，曾用"只查顶层字段名是否含 key/token/secret"的方式做脱敏，结果漏检了嵌套两层的 `memorySearch.remote.apiKey` 字段里的一个真实 API key。这直接决定了脱敏模块必须支持任意深度递归，不能只处理顶层。

除此之外，实际对真实数据跑通后，又连续发现并修复了两次密码泄漏：

1. **第一次**：本项目今天部署麒麟环境的过程被 Claude Code 完整记录了下来，其中大量出现明文 SSH/sudo 密码（写在命令里，比如 `echo '密码' | sudo -S ...`）。这类密码**只有11位、不是乱码**，完全不符合"看起来随机的长字符串"这类通用规则，首版脱敏完全没检测到，导致密码在提取结果里明文出现了近6000次。加了针对"密码传递惯用写法"的结构化规则（`-pw`、`echo ... | sudo -S`、中文"密码"后跟值等）后修复。
2. **第二次**：人工抽查 lucy 数据样例时，发现同一个密码还有另一种变体写法（大小写不同、没有数字后缀）出现在 `sshpass -p "..."` 里，第一版的"精确字符串匹配"抓不到变体。改成正则"词根+任意后缀，不分大小写"后修复。

**最终采用的脱敏层次**（详见 `anonymize.py` 源码注释）：
1. 字段名本身敏感（含 key/token/secret/密码等关键词，任意嵌套层级）→ 整个值打码；
2. 正则匹配常见敏感模式：API key 前缀、长随机字符串、手机号、邮箱、IPv4；
3. 命令行里"结构上看就是密码"的写法（`-pw`、`sudo -S` 管道等）；
4. 已知具体敏感字符串的兜底匹配（本项目实测泄漏过的密码，词根+正则，覆盖大小写/后缀变体）。

**诚实说明局限性**：自然语言里提及密码/隐私的方式千变万化，规则永远不可能穷举完。姓名等自由文本实体（比如聊天记录里提到的人名）目前**没有**自动化处理能力，正则做不到可靠的中文人名识别。已对最终数据集做了人工抽样检查（30条随机样本，见第七节），未发现明显的人名残留，但这不等于100%保证——**如果这份数据集要用于对外提交的材料，建议在最终定稿前再做一轮更大范围的人工抽查**。

## 六、已知限制

1. **`.trajectory.jsonl` 未处理**：OpenClaw 的 OTel 风格链路追踪格式信息更丰富，但结构是"全量上下文快照"，同一条消息会在多条 trace 记录里重复出现，直接解析容易重复计数，需要额外的去重逻辑。当前"普通 .jsonl"格式已经能满足"工具调用+结果"这一数据源的核心需求，`.trajectory.jsonl` 留作后续按需扩展。
2. ~~两个来源的 `timestamp` 格式不一致，`merge_and_validate.py` 目前没有做统一转换~~
   ——**已修复**：Claude Code 原用 ISO8601 字符串（如 `"2026-07-31T09:31:13.404Z"`），
   OpenClaw 原用纪元毫秒数字（如 `1783332242578`），现已在后续补做的时间戳归一化
   模块中统一转成 ISO8601 UTC 字符串（见第十二节、`normalize_time.py`），"偏好提取"
   等下游模块可以直接按时间排序/分析，不需要再补这一步。
3. **姓名类隐私信息无法自动脱敏**（见第五节说明），需人工抽查兜底。
4. **数据分布不均衡**：claude_code 占 97.3%（6,216 条），openclaw_lucy 占 2.7%
   （170 条）——如果后续模块要分别评估"不同来源"的效果，需要注意这个不均衡
   可能带来的偏差。

# 第二版新增内容（2026-08-03）

## 十一、为什么要补另外两类数据源

首版交付后复核题目原文，发现一处关键差距。题目内容(1)要求：

> 支持**工具执行结果、用户行为数据、手动配置信息**等数据的统一接入

首版只有工具执行结果。而后两类恰恰是**偏好提取**最需要的——题目要求偏好覆盖
「操作习惯、**输出风格**、**安全策略**」三类，它们各自的数据依据并不相同：

| 偏好类别 | 主要数据依据 | 首版是否有 |
|---------|------------|-----------|
| 操作习惯 | 工具执行结果（用户实际调用了什么工具、什么参数） | ✅ |
| **输出风格** | **用户输入历史**（用户怎么提要求：要中文、要简洁、要不要讲原理……） | ❌ |
| **安全策略** | **手动配置**（权限放行清单、是否跳过确认……） | ❌ |

也就是说：**缺了后两类，三类偏好里有两类没有数据支撑，只能硬编。**

### 11.1 新增数据源一：用户行为数据

- 来源：`~/.claude/history.jsonl`（Claude Code 记录的用户输入历史）
- 字段：`display`（输入原文）/ `timestamp` / `project` / `sessionId`
- 产出：**534 条**，时间跨度 2026-05-26 → 2026-08-03
- 分布：斜杠命令 18 条、自然语言输入 516 条
- 提取脚本：`extract_user_history.py`，沿用同一套四层递归脱敏

### 11.2 新增数据源二：手动配置信息

- 来源：`~/.claude/settings.json`（全局）、`~/.claude/settings.local.json`（本地）
- 产出：**7 条**配置项，按偏好类别归类为「输出风格 3 条 / 安全策略 4 条」
- 提取脚本：`extract_manual_config.py`

实际内容：

```
[输出风格] model = opus
[输出风格] theme = dark
[输出风格] effortLevel = high
[安全策略] skipAutoPermissionPrompt = True
[安全策略] permissions.allow[0] = PowerShell(Get-NetIPConfiguration *)
[安全策略] permissions.allow[1] = PowerShell(Get-NetIPInterface *)
[安全策略] permissions.allow[2] = PowerShell(Test-Connection *)
```

### 11.3 ★手动配置的第二重身份：偏好提取的交叉验证答案键★

这是本次最有价值的一点设计。

配置文件是用户**亲手写下的、且早于本项目存在**的显式偏好声明。这给了偏好提取一个
**零循环论证**的验证手段：

> 让偏好提取器**只吃行为数据**（工具执行结果 + 用户输入历史），
> 看它能否独立推导出与配置文件一致的偏好。

两边完全独立产生——配置是用户自己写的，偏好是从行为里挖出来的——所以一致性就是
真实的正确性证据，**不需要任何人做主观判断**。

**为什么这一点重要**：偏好提取准确率若靠"数据主人自己看着模型输出说对不对"，
会被质疑**看数据下菜碟**（先看结果再决定什么算对）。用用户独立编写的配置当答案键，
从机制上排除了这种可能。

⚠️ **因此这些记录带 `is_answer_key: true` 标记**。做偏好提取实验时**必须把
config_item 类记录排除出训练输入**，否则等于拿答案当输入，实验作废。

### 11.4 为什么不把 `memory/` 目录也算作配置源

`~/.claude/projects/*/memory/*.md` 里确实记录了用户偏好（有 `type: feedback` 的条目），
看起来很适合当答案键。但**明确排除**，原因是：

那些文件是**模型从对话里自动总结生成的**，不是用户手写。拿它当答案键会变成
「模型给模型打分」，评委一问「你的标准答案是谁写的」就穿了。

只用真正的手写配置文件，虽然只有 7 条，但每一条都站得住。

## 十二、修复首版已知限制：时间戳格式统一

首版"已知限制"第 2 条记录：Claude Code 用 ISO8601 字符串、OpenClaw 用纪元毫秒，
未做统一转换，判断为"后续若需按时间分析再补"的可选项。

**第二版把它升级成硬前置并已修复**（`normalize_time.py`）。升级的原因有两条：

1. **偏好的「版本化管理」**：题目要求偏好能版本化更新与回溯，必须能按时间排序；
2. **★评测方法的可信度设计★**：偏好提取的主力评测方式是
   「按时间切分 → 用早期数据提取偏好 → 验证它能否预测留出窗口的真实行为」。
   时间戳不统一，这个切分根本做不出来。

第 2 条尤其关键——它是整个偏好评测**不依赖主观判断**的基础。

**处理方式**：一律转成 ISO8601 UTC 字符串。选它而不是纪元毫秒的原因是
**字符串字典序即时间序**，jsonl 文本可以直接排序，且人眼可读便于抽查。
原始值保留在 `timestamp_raw`，格式来源记在 `timestamp_source`——
数据加工不应丢弃原始信息，出问题时要能追溯是转换错了还是源数据本身有问题。

归一化覆盖情况（实测）：

```
iso8601: 13866
epoch_ms:  722
（无 unknown，全部识别成功）

时间跨度：2026-05-26T05:47:12.519000+00:00 → 2026-08-03T09:20:53.555899+00:00
```

约 10 周跨度，足够支撑按时间切分的留出验证。

> ⚠️ **2026-08-04 纠正**：上面这个"约10周"是把**全部四类记录混在一起**算的时间跨度，
> 由 `user_input`（从05-26开始）拉长的。**分记录类型看，实际情况并不一样**：
>
> | 记录类型 | 真实起点 | 真实跨度 |
> |---------|---------|---------|
> | `user_input`（含时间戳的最早来源） | 2026-05-26 | 约 10 周 |
> | `tool_execution`（B2 案例/流程挖掘的数据源） | **2026-07-03** | **约 4.1 周（29天，止于08-01）** |
>
> 这是在 B2 知识挖掘做冷启动模拟时发现的：按"10周"的最早时间切子集，切出来的
> `tool_execution` 记录数是 **0**——因为工具调用记录压根还没开始。**任何后续
> 模块要用 `tool_execution` 做按时间切分（不只是 B2，也包括任务E的"操作习惯"
> 类偏好，如果要用工具调用频率/序列做时间维度分析），应该按 `tool_execution`
> 自己的真实跨度（07-03~08-01）设计，不能直接照抄这里的"10周"。**
> `user_input` 相关的分析（如"输出风格"类偏好的时间切分）仍可放心用 10 周口径。
> 详见《知识检索/说明报告.md》第一点五节。

## 十三、★新踩的坑★：展平操作会拆掉脱敏保护

这是第二版实际踩到并修复的一个安全问题，值得单独记录。

### 现象一：假阳性——配置项的名字被误打码

`extract_manual_config.py` 初版把字段命名为 `config_key`，产出全是：

```
[输出风格] [REDACTED_FIELD] = opus
```

**原因**：`anonymize.py` 的第一层规则是「**字段名**含 key/token/secret 等关键词 →
整个值打码」。字段名 `config_key` 里含 "key"，于是配置项的**名字本身**被当成密钥打掉了。

这与首版第六节记录的 `session_id` 被"长随机串"规则误伤是同一类**假阳性**问题。

**修复**：字段改名为 `config_path`。

### 现象二：假阴性——真密钥反而漏掉（更危险）

上一个只是难看，这一个是真漏洞：

本脚本把嵌套配置**展平**成 `{"config_path": "apiKey", "config_value": "sk-xxx"}`。
原来的字段名 `apiKey` 降级成了**普通字符串值**，而真正承载密钥的字段现在叫
`config_value`——不含任何敏感关键词。**递归脱敏的保护就这样被展平操作拆掉了。**

首版报告第五节特意强调"脱敏必须支持任意深度递归"，正是因为曾漏检嵌套两层的
`memorySearch.remote.apiKey`。而展平操作把这个来之不易的保护给绕过去了。

**修复**：新增 `redact_if_sensitive()`，在展平的同时拿**原始路径**逐段过一遍同样的
敏感判定，把保护补回来。验证结果：

```
model                        -> opus
apiKey                       -> [REDACTED_CONFIG_VALUE]
memorySearch.remote.apiKey   -> [REDACTED_CONFIG_VALUE]     ← 首版那次真实泄漏的路径
permissions.allow[0]         -> PowerShell(...)
auth.token                   -> [REDACTED_CONFIG_VALUE]
```

### 现象三：过度脱敏切断了数据之间的关联（同一个坑，第二次踩）

比前两个更值得记，因为**首版报告已经明确警告过，而第二版还是踩了**。

首版第六节教训⑤原文：

> `session_id` 等 UUID 字段容易被"32位以上乱码"规则误伤脱敏，
> **脱敏应只作用于 `tool_input`/`tool_output` 具体内容字段，不要整条记录一起脱敏**

首版的两个提取脚本遵守了这条。但 `extract_user_history.py` 初版图省事，直接对
**整条记录**调了 `anonymize(rec)`，结果 `session_id` 全被打成 `[REDACTED_LONG_TOKEN]`。

**后果远比"字段难看"严重**：用户输入与工具调用的 `session_id` 交集从 **28 掉到 0**，
「用户意图 ↔ 工具调用序列」的关联链路被彻底切断。

而这条链路正是把「工具调用日志」升格为「**工作流程知识**」的关键——
没有意图锚点，一串命令只是流水账；有了它，才是"做某件事的方法"。
题目内容(3)要求的三类知识里，「工作流程知识」这一整类会因此挖不出来。

**修复**：只对自由文本字段 `text` 脱敏，`session_id` / `project` / `timestamp` 保持原样。
修复后实测：

```
工具侧会话 108，输入侧会话 114，交集 28
可关联的用户意图 120 条，覆盖工具调用 9094 条（占全部工具调用的 64.7%）
```

### 教训

两条，第二条是这次新增的：

> 1. **改变数据形状的操作（展平、转置、重命名）可能会让原有的安全规则失效**，
>    因为那些规则往往依赖于特定的数据结构。做这类变换时必须专门复查一遍安全假设
>    还成不成立，不能默认"数据内容没变，所以保护还在"。
>
> 2. **脱敏的粒度必须精确到字段，"整条过一遍"是危险的偷懒**。过度脱敏不会报错、
>    不会让程序崩溃，它只是悄悄地把数据之间的关联抹掉——**代价要等到下游模块
>    做不出东西时才暴露**。本次若不是在设计知识挖掘方案时顺手核对了一下会话交集，
>    很可能要到建完索引、发现"工作流程知识一条也挖不出来"时才会发现。
>
> 已在首版报告里写下的教训，第二版仍然踩了一次——**光"记录教训"不够，
> 写新脚本时要主动回查已有的教训清单。**

## 十四、第二版的统一数据格式

异构数据统一接入的核心难点是：**强行要求所有类型都有 `tool_name` 不合理，
但完全不校验又失去质量把关的意义**。采用的折中方案是「公共字段全类型必填 +
类型专有字段分别校验」：

```json
{
  "source": "claude_code | openclaw_lucy | claude_code_history | claude_code_config",
  "record_type": "tool_execution | user_input | config_item",
  "timestamp": "2026-07-31T09:31:13.404000+00:00",   // 统一后
  "timestamp_raw": "2026-07-31T09:31:13.404Z",       // 原始值，保留可追溯
  "timestamp_source": "iso8601 | epoch_ms | epoch_s | unknown",

  // tool_execution 专有
  "session_id": "...", "tool_name": "...", "tool_input": {...},
  "tool_output": "...", "is_error": false,

  // user_input 专有
  "text": "...", "project": "...", "has_pasted_content": false,

  // config_item 专有
  "config_scope": "global|local", "config_file": "settings.json",
  "config_path": "permissions.allow[0]", "config_value": "...",
  "preference_category": "操作习惯|输出风格|安全策略|其他",
  "is_answer_key": true
}
```

**向后兼容**：`record_type` 缺失时按 `tool_execution` 处理，因此首版产出的 14,047 条
记录无需重新生成即可通过校验；同时仍单独输出一份 `tool_execution_records.jsonl`，
让已依赖它的下游脚本（如知识检索的建索引）不必改动。

## 十五点五、这份数据能挖出多少「知识」（供知识检索模块使用）

题目内容(3)要求知识记忆覆盖**工作流程知识、历史案例、可复用模板**三类。
这三类**都不是 wiki 式的世界常识，而是「Agent 的操作性知识」**，只能从工具调用记录里挖。

对本数据集做的可挖掘量实测：

| 知识类型 | 由什么构成 | 实测可挖掘量 |
|---------|-----------|-------------|
| **历史案例** | 失败 → 修复 | **461 对**（出错记录 5,174 条中，同会话 5 步内有同工具成功调用的） |
| **工作流程知识** | 用户意图 → 工具调用序列 → 结果 | **120 条**，覆盖 9,094 次工具调用（64.7%） |
| **可复用模板** | 跨会话反复出现的流程 | 待从上述 120 条中抽象 |

**这组数字直接推翻了一个原本的设计方案**：原计划把每条工具调用记录切成一张"知识卡片"
（14,047 条 → 2~3 万块）。但那样做出来的是**日志**不是知识——
「第 8347 条：执行了 `ls -la`」检索出来毫无用处，约等于 grep 命令历史。

**单条工具调用是一个"事件"，知识产生于事件之间的关系。** 正确的知识单元是挖掘出来的
案例 / 流程 / 模板，规模约 600 条而非 2~3 万条——索引小 50 倍，但每一条都能回答一个真问题：

- 「怎么在磐石系统上装包」→ 工作流程知识
- 「报 undefined symbol 怎么办」→ 历史案例

**这也说明了为什么必须补「用户行为数据」这一路**：意图锚点来自 `history.jsonl`，
没有它，工具调用序列无法被切分成有意义的流程单元。

## 十六、第二版的已知限制

1. **数据分布仍然严重不均衡**：`tool_execution` 占 96.3%，`config_item` 仅 7 条。
   配置类少是客观事实（用户本来就没写多少配置），但它作为答案键的价值不取决于数量。
   真正的问题是**它只能验证 7 条偏好**，覆盖不到「操作习惯」类——那一类仍需
   行为预测法（按时间切分留出验证）来评。
2. **配置项的时间戳是文件修改时间**，只反映最后一次修改，不反映每一项各自何时写下。
   因此配置类数据**不适合参与按时间切分的实验**，只适合当静态答案键。
3. **`user_input` 的隐私风险高于工具记录**：它是自由文本，比结构化的命令更可能夹带
   隐私内容。已跑同一套脱敏，但首版第五节的局限性说明同样适用——
   正则无法可靠识别中文人名等自由文本实体，**需人工抽查兜底**。
4. **「跨场景」的数据支撑仍然单薄**：题目要求跨场景偏好适配与复用，我们有两个场景
   （本机开发 vs 飞书助手），但 openclaw_lucy 仅 188 条、占 2.7%（R3-21：
   R2-25 只改了 §六 的同一个数字，这个未被点名的小节留着旧的 1.3%，
   已按第三版 6,927 条口径更正）。用它论证跨场景会偏弱。
5. **`.trajectory.jsonl` 仍未处理**（同首版第六节第 1 条）。
6. **`tool_execution` 的真实时间跨度只有约4.1周（07-03~08-01），不是"10周"**——
   见第十二节的纠正说明。设计任何按时间切分的实验前，先确认用的是哪类记录的
   时间戳，别直接套用聚合统计里的跨度。
7. **`tool_execution` 中存在单日异常值**：2026-07-27 一天（仅2个会话）贡献了
   90.1% 的全部出错记录，是一次批处理任务的产物，不代表典型的一天。这不是脱敏
   或提取环节的问题——记录本身是真实、合法的——但**任何按天统计 `tool_execution`
   的下游分析都会被这一天严重带偏**（错误率、活跃度、工具使用频率等）。已在
   `知识检索/mine_cases.py` 里实现了通用检测函数 `detect_outlier_days()`
   （判据：单日占比超过阈值 + 涉及会话数极少，不是硬编码某个日期），任何模块
   在按天分析这份数据集前，建议先跑一遍这个检测。完整发现过程见
   《知识检索/说明报告.md》第二节与《可复现性体系/勘误与修正记录.md》第六节。

## 十六点五、第三版：数据层安全与质量修复（2026-08-05）

外部独立审查对 `Desktop/RAG` 全部交付内容做了一次对抗性复核，其中数据层
（本模块）被判定"❌必须返工"——不是"没做清洗"，而是"做了但不合格"，这更
危险，因为看起来是做过的。完整审查见项目根目录《独立评审报告与整改清单.md》
（该文件本身含漏洞位置信息，未随版本库分发）。本节记录返工内容与结果。

### 16.5.1 P0：真实凭据泄漏（最优先修复）

审查发现交付数据集里残留至少 6 类真实凭据（sudo 口令、第三方 LLM API key、
QQ 机器人 client secret、SSH 账户口令、qBittorrent 后台口令、上传目录
TOKEN），且**唯一泄漏 sudo 口令的地方是脱敏模块自己的源码**——
`KNOWN_SECRET_ROOTS` 词根表把真实口令硬编码在会进 git 历史的文件里。

修复：
- `sk-` 前缀 key 的正则字符集补上 `-`/`_`，阈值从16位降到12位（原正则在真实
  泄漏的 key 第6位遇到连字符就断了）
- 新增"关键词+上下文"规则（密钥/密码/token/secret/password/passwd 等
  紧跟一段非空白串即打码），覆盖低于长随机串阈值的短口令
- 补 `sshpass -p` 裸词形式、`chpasswd` 整行触发、MAC地址识别
- `KNOWN_SECRET_ROOTS` 与用户名/主机名假名化映射表都外部化到 `.gitignore`
  掉的本地文件（`多源数据整合/secrets_blocklist.txt`、**项目根目录的**
  `identity_map.txt`），仓库里只留 `.example` 模板，不再把真实敏感值随
  源码一起提交

**这套新规则跑起来后，在本轮重新提取的数据里又实测揪出两处规则本身没抓住
的真实密码**（qBittorrent 与另一台服务器的 web UI 密码，以"账号 admin /
**密码**"这种文档式写法出现，前后没有任何关键词紧邻，正则的"关键词+上下文"
规则天生抓不到这类写法，最终靠已知字面值兜底堵上）——这也是"边修边测边发现
新漏洞"这条项目一直在验证的方法论的又一次真实应验，不是纸面推演。

### 16.5.2 数据代表性：自指污染过滤

本项目自身的开发会话（这份说明报告、`anonymize.py` 源码本身等）此前混进了
数据集——审查发现 65 条记录含本项目关键词，其中 2 条甚至包含 `anonymize.py`
源码正文，构成"用本项目自己的数据支撑/评测本项目"的循环论证。

⚠️ 按"项目目录"过滤不可行：本环境所有 Claude Code 会话统一记在通用目录
`~/.claude/projects/C--Users-<USER>/` 下（VSCode 扩展的运行方式如此），
不是按 `cd 到具体项目目录` 分开存放的，一次物理会话可能混杂 RAG 项目工作
与完全无关的工作。改为**按单条记录内容过滤**：只要某条工具调用涉及的路径
指向本项目目录（`Desktop\RAG`），就跳过这一条，而不是跳过整个会话文件。

### 16.5.3 质检器补强：从"拒绝数恒为0"到真正起作用

原质检器（`merge_and_validate.py`）只检查字段是否存在、是否为空，从未真正
拒绝过任何输入——审查指出这样的校验器无法证明自己在工作，实测它放行的数据
里有 33.1% 整条完全重复、3.4% 编码损坏（GBK/UTF-8 转码失败留下的 U+FFFD）。

补强：
- **内容级去重**：按 `(session_id, tool_name, tool_input, tool_output)`
  四元组去重（不用整条记录哈希，因为 `timestamp` 字段的毫秒级差异会让
  真实重复记录哈希不同）
- **U+FFFD 编码损坏检测**：命中即拒绝
- 剔除的记录连同原因落盘到 `dataset/rejected.jsonl`，供复查（此前不合法
  记录只计数后丢弃，无法审计具体是哪一条）
- **类型与枚举校验（独立评审D-5，本轮补）**：此前只查字段"存在且非空"，
  `"is_error": "true"`（字符串冒充布尔值）、`execution_status` 传一个
  schema里没有的值，都不会被拦下。新增 `schema.json`（显式声明各记录类型
  的字段类型/枚举，不引入`jsonschema`第三方库——保留L1"纯Python、任何
  机器可跑"的约束，自己写了个约20行的轻量校验器）。用变异测试验证过
  确有检测能力（不是摆设）：字符串冒充bool的`is_error`、越界的
  `execution_status`枚举值都被正确拦下，`test_detectors.py` 新增3条

### 16.5.9 脱敏召回率/精确率实测（独立评审D-8/D-9）

全项目此前唯一的脱敏测试是 `measure_L1.py` 的 M-103（7条手工用例，只测
`redact_if_sensitive()` 一个函数），从未真正测过**召回率**（真正敏感的内容
有多少被打了码）、**精确率**、**误伤率**——"人工抽样看了几十条"不构成证据，
这三个数字才是。

新建标注测试集（`多源数据整合/labeled_redaction_testset.json`，第二轮
独立复核 R2-08 扩充后为27条应打码的正例+19条不该打码的负例，正例结构
与本项目真实发生过的泄漏事故一致但值本身是合成的，不含任何真实密钥）
与测量脚本（`measure_anonymize_quality.py`，接入`可复现性体系/
measure_L1.py`的M-113），跑 `_scrub_string()` 实测：

```
召回率：27/27 = 100.0%
精确率：27/27 = 100.0%
误伤率： 0/19 =   0.0%
```

**测量过程本身揪出并修复了4类真实bug**（不是纸面推演，是标注集实测才
暴露出来的）：

1. **`\b`词边界在汉字邻接时静默失效**：Python默认Unicode模式下汉字算`\w`
   字符，"电话13812345678"里"话"和"1"之间没有word/非word的过渡，手机号/
   IPv4/MAC三条正则的`\b`边界不成立、规则直接不触发。原有自测用例恰好在
   数字前留了空格（"手机号 13812345678"）才侥幸测出"通过"，掩盖了这个
   问题——真实数据里"电话:xxx"这类紧贴写法很常见。改用显式的"前后不是
   ASCII字母数字/下划线"断言，不依赖`\w`的Unicode语义。
2. **content级关键词表与字段名级关键词表不一致**：`SENSITIVE_KEY_PATTERNS`
   （判定dict key用）有"credential"，`REGEX_RULES`的关键词+上下文规则
   （判定字符串正文用）没有，导致"credential: xxx"这类嵌在正文里（不是
   作为dict key）的内容漏检。补上，两份表恢复一致。
3. **UUID格式被"32位以上长随机串"规则误伤**：本项目自己的`session_id`就是
   UUID格式，被当作疑似密钥打码会切断"用户意图↔工具调用"的关联链路（与
   第四节记录过的展平误伤是同一类"过度脱敏损伤数据可用性"问题）。加一条
   UUID标准格式（8-4-4-4-12）排除，不豁免任何其他形态的长随机串。
4. **（R2-08新发现）漏检+误伤各三类**：`sk-`规则缺左词边界导致
   `task-execution-record`这类词里的"sk-"子串被误判为key前缀；32位以上
   长随机串规则对64位SHA256、40位git commit hash、语义化技术包名
   （`kylin-ai-vector-engine-client-devel`）全部整体打码；关键词+上下文
   规则对"password policy document"这类关键词后紧跟正常英文单词的散文
   也整体打码。另外补齐了AWS/Slack/GitHub token前缀规则、`-p`紧贴密码
   （`mysql -pPASSWORD`）与`-u user:pass`两种此前完全没有规则覆盖的
   命令行写法。详见 `anonymize.py` 对应位置的注释与改动记录。

**已推翻的旧判断（勘误）**：上一版这里写的是"40位git commit hash仍会被
打码，加白名单会同时打开'真密钥伪装成hash格式就能免检'这个口子，风险
高于收益，不勉强修"。第二轮独立复核指出**这个权衡本身站不住**——64位
SHA256被打码不是"某类内容误伤"这么轻描淡写，**本项目自己的评测集冻结
锚定、可复现性记录全套机制都依赖SHA256**，对含哈希的产物跑脱敏等于
自毁证据链，是比"理论上可能被绕过"更具体、更确定会发生的损害；而本
项目实际发生过的全部真实泄漏（sudo口令/API key/QQ secret/SSH口令/
qBittorrent口令/PT做种机口令/上传TOKEN）没有一个是"纯十六进制长串"
形态，"攻击者故意把密钥伪装成hash格式"这个假想场景在本项目的真实
威胁模型里没有对应实例支撑。两害相权，加白名单收益更大，已改。

**如实标注局限**：27正+19负的标注集规模小于独立评审建议的100~200条，是
本轮时间投入下的合理取舍，但已经是从"0次真实测量"到"有实测数字"——
这个从无到有比规模不够更重要。

**已交付数据集的残留问题：已定位，已验证影响范围，暂缓修复（如实说明这个
决定的依据）**。修复上述`\b`边界bug后，回查已交付的`dataset/memory_source_
records.jsonl`（6,927条），发现 **27 处真实存在的私网IP因`\b`bug漏检**
（形如"至192.168.137.1"这类紧贴汉字未加空格的写法）。曾用
`rescrub_strings.py`对该文件做过一次增量再脱敏试验（只重跑字符串级的
`_scrub_string()`，不碰按字段名判定的`anonymize()`，理论上是幂等安全的），
但验证时发现**这个改动会让`mine_cases.py`重新挖掘时产出32条案例而非当前
冻结的27条**（IP文本变化改变了个别命令的相似度判定，波及案例过滤的边界
情况）——这意味着"只改数据、不动下游"这个预期不成立，会连带需要重建索引→
重新生成评测集→重新冻结→重测召回率，代价是又一轮几小时的全链路返工。

**权衡后决定暂缓**，理由：
1. `dataset/`整个目录被`.gitignore`排除，**从未推送到GitHub**，这27处IP
   只存在于本地这一份文件里，不构成真实的对外泄漏；
2. 全部27处都是`192.168.x.x`私网地址（内网拓扑信息），独立评审报告本身
   把这类信息列在"附带的非凭据类身份信息"里，优先级低于P0凭据泄漏；
3. `_scrub_string()`的3个bug修复本身已经生效并验证（见上方M-113实测），

   单独为这27处触发一轮返工。

`rescrub_strings.py`脚本保留在交付物里（标注了用途与这次的权衡过程），
供后续真正需要重跑数据层时使用；本轮**未**对已冻结的知识库/评测集/召回率

### 16.5.11 R2-06：交付的数据集无法从交付的输入复现

jsonl` 还晚。这类错误不报错、不崩溃，只有把两边的 mtime 放在一起看才会
发现。

**已修复**：新增 `assert_inputs_not_newer_than_output()`，`main()` 开头
默认执行——输入文件比已有输出更新时直接 `SystemExit`，拒绝让人在不知情
的情况下使用陈旧产物；提供 `--allow-stale-inputs` 显式绕过（见下）。
`test_detectors.py` 新增两条变异测试验证该函数在两种场景下都正确判断。

⚠️ **本次未重新执行合并、未把 6,927 改成 7,328**，原因与 R2-01/R2-22
的"代码修好但不重新生成部署产物"是同一类考虑，且这里的情况更极端：
本项目自身在 Claude Code 里的每一次工具调用都会被记进原始数据源，**这
意味着"让输入完全不比输出新"这件事，只要项目还在被使用就永远处于
移动状态**——重新合并一次，几分钟后随着继续工作又会产生新的"过期"。
6,927 这个数字是一次有意冻结的快照，本报告与几乎所有下游模块（知识
挖掘、索引、评测集、召回率、置信区间……）的数字都建立在这份快照之上；
真正重新合并会连锁改变几乎全部已发布数字，需要重新走一遍从数据层到
评测层的整条链路，工作量远超一次代码缺陷修复的合理范围，且价值有限
（该重新合并明天又会"过期"）。因此选择：**新增的检查按默认行为会挡住
未来任何一次疏忽的"忘记重跑"**（这正是 R2-06 要根治的问题），但对
"当前这份已经production-frozen的快照"允许用 `--allow-stale-inputs`
显式声明"我知道，这是有意保留的历史快照"而不是被动地对不上号。

## 附：本报告的数据如何验证

本报告中的数字均可核对，不必仅凭文字采信。

**任何机器（无需银河麒麟环境）：**

```bash
cd 可复现性体系
python reproduce_L1.py --check-only     # 用已有测量记录逐条核对
python reproduce_L1.py                  # 重跑全部 L1 测量再核对
```

**需要麒麟环境的部分**（768 维验证、embedding 延迟、官方向量引擎）：
见 `可复现性体系/measure_L2.py`。

**⚠️ 三点诚实说明：**

1. **测量记录本身不构成证明** —— 那些 JSON 我们能写，别人也能写。
   真正让数字站得住的是"你可以自己跑一遍"。
   可信度不来自「无法伪造」，而来自「容易被验证」。
2. **延迟类数字随硬件变化，不应期待跨机器一致** —— 实测同一段代码在麒麟虚机（2 vCPU）
   与开发机（24 核）上差约 2 倍。核对脚本对延迟只验证结论（是否达标、比值是否合理），
   不比对绝对毫秒数。每个数字产自什么环境，写在 `records/*.json` 的 `environment` 字段里。
3. **方法可复现 ≠ 数据可复现** —— 提取脚本任何人都能跑，但本项目这份数据集
   来自项目成员机器上的真实使用历史，**没有人能重新采集到同一份**。
   第三方验证方式是用随交付物提供的数据集重跑，而非重新采集。

被推翻的判断与修正过的数字，完整记录在 `可复现性体系/勘误与修正记录.md`。
方法与局限详见 `可复现性体系/可复现性说明.md`。
