## 一、先放结论

1. **常驻服务已跑通**，向量化结果与阶段01 **逐位一致**（相似度 0.9441 / 0.7118 / 0.5326，见第四节）。
2. **性能收益约等于零**（P50 486.7ms vs 484.2ms，1.0×）。立项理由「每次调用都要重新加载 339MB 模型」**是错的**——模型常驻在 `kylin-ai-runtime` 守护进程里，客户端进程从来就不需要自己加载它。
3. **但由此测出了真正的瓶颈**：向量化耗时与**文本长度**成正比，与进程启停无关。
4. **「知识检索响应 ≤500ms」这个硬指标是能达到的，且余量充裕**：查询向量化（30 字）P95 = **84.9ms**（首测 68.4ms，重跑后系统性偏慢，见 5.3 节与《勘误与修正记录》1.1 节），占 500ms 预算的 **17.0%**。
5. 这个测量直接改变了下一步（知识检索模块）的设计方向，见第七节。

**如实说明**：如果只看「有没有让程序变快」，这个任务的答案是「没有」。它的价值在于用实测纠正了一个错误判断，并把 500ms 指标从「不知道能不能达到」变成「已知达得到、余量 83%」。

## 三、设计说明

### 3.1 通信协议：长度前缀，而不是按行分隔

```
请求： <字节数>\n<该字节数的 UTF-8 原文>
响应： <768 个 float，空格分隔>\n     出错则 ERR <错误码>\n
```

**为什么不用「一行一条文本」**：本项目要向量化的是工具执行记录，`tool_output` 里必然含换行符，行分隔会被内容本身撑破。长度前缀不需要任何转义，内容里是什么字节都无所谓。

**与阶段01 的 `emb_vec` 相比**：`emb_vec` 通过命令行参数 `argv[1]` 传文本。实测本数据集单条最长 50KB，**没有超过 Linux 单参数 128KB 的上限**，所以 argv 方案在当前数据上并不会出错——这一点不应被夸大成改造理由。管道传输的真实好处是绕开了 shell 与 argv 的编码环节（阶段01 报告第四节已记录过中文经命令行传递的编码隐患）。

### 3.2 启动预热握手

部署手册记录过一个坑：模型（339MB）加载完成前调用向量化会报 `errCode: 24 Timeout`，这不是故障。

本服务在启动时**自己扛下这个坑**：`init_model` 之后循环做试探性向量化（每 2 秒一次，最多 120 秒），直到真的能出向量了，才向 stdout 打印 `READY`。调用方只要等到 `READY` 就可以放心用。

**这是本任务少数几个确定有价值的产出之一**：后续所有模块（建索引、评测、检索）都不必再各自处理这个坑。

### 3.3 Python 侧的一个具体坑：stderr 不能用 PIPE

`EmbeddingClient` 把子进程的 stderr 重定向到临时文件，而不是 `subprocess.PIPE`。

原因：PIPE 有容量上限，如果没人读，子进程写满后会阻塞；而主进程此时正阻塞等它的 stdout —— 双方互等，直接死锁。KYSDK 每次调用都会往 stderr 打日志，这个坑一定会踩到。落到文件就没有这个问题，出错时再把内容读出来附在异常里。

## 五、★核心发现★：立项假设被推翻

### 5.1 假设是什么，实测是什么

**原假设**：每次调用 `emb_vec` 都要走「建会话 → 初始化 → 加载 339MB 模型」，这个固定开销是性能瓶颈，改成常驻可大幅提速。

**实测**（同一批 10 条样本，两种架构，公平对比）：

```
架构                              样本         最小        P50        P95         最大         平均
新：emb_serverd 常驻                10     207.7ms     486.7ms     946.1ms     946.1ms     542.1ms
旧：emb_vec 每次起进程                10     244.2ms     484.2ms     912.7ms     912.7ms     540.7ms

P50 提速倍数：1.0×
```

**几乎完全一样。**

### 5.2 为什么会这样

关键证据：**常驻服务从启动到 `READY` 只花了 0.1 秒**。如果客户端进程真的需要自己加载 339MB 模型，这一步不可能是 0.1 秒。

结合旧架构单次调用最快只要 244ms（同样远低于加载一个 339MB 模型所需的时间），可以确定：

> **模型由 `kylin-ai-runtime` 守护进程常驻持有，客户端进程的 `text_embedding_init_model()` 只是与守护进程握手，并不真的加载模型文件。**

这也解释了部署手册里那个「首次运行报 errCode 24，等数十秒再跑就好」的现象——那是 **runtime 守护进程**在首次被请求时加载模型，加载完就一直驻留；之后所有客户端进程都直接复用，各自都不需要再加载。

**教训（与《多源数据整合》报告里那条同源）**：不要凭「架构上看起来应该很慢」下判断。这次的错误在于把「客户端调用了 init_model 这个函数」等同于「客户端加载了模型文件」，而没有先花十分钟测一下。**性能优化必须先测量再动手，否则可能花力气优化一个根本不存在的瓶颈。**

### 5.3 真正的瓶颈：文本长度

分档实测（每档 15 次，语料取自真实数据集）。**下表为 2026-08-04 重跑值** `[M-202]`（L2）：

| 长度档位 | 字数 | P50 | **P95** | 首测 P95（08-03） | 差异 |
|---------|-----|-----|--------|-----------------|------|
| 查询-短句 | 10 | 39.1ms | **49.1ms** | 36.4ms | +35% |
| **查询-长句** | **30** | 72.9ms | **84.9ms** | 68.4ms | **+24%** |
| 文档块 | 128 | 257.3ms | 276.9ms | 239.5ms | +16% |
| 文档块 | 256 | 514.9ms | 538.3ms | 417.9ms | +29% |
| 文档块 | 512 | 1138.1ms | 1195.1ms | 823.8ms | +45% |
| 文档块 | 1024 | 2502.1ms | 2542.9ms | 1764.7ms | +44% |
| 整条长记录 | 2048 | 6078.6ms | 6371.8ms | 4169.7ms | +53% |

**耗时与字数基本成正比**（字数翻倍，耗时约翻倍）。

⚠️ **关于两次测量的差异，如实说明**：重跑**系统性偏慢 16~53%**，七个档位无一例外，
不是随机噪声。可能原因（未做控制变量实验，无法确定归因）：两次测量之间向量引擎的共用库
从 15MB 涨到 97MB、守护进程常驻内存随之上升，而该虚机仅 3.9GB 内存；也可能是宿主机负载差异。
**结论不受影响**——见 6.1 节。完整记录见《可复现性体系/勘误与修正记录.md》1.1 节。

## 六、对硬指标的意义

### 6.1 「知识检索响应时间 ≤500ms」—— 达得到，余量充裕

必须区分两类文本，混在一起统计会得出完全错误的结论：

| 文本类型 | 长度 | 什么时候被向量化 | 是否计入 500ms 预算 |
|---------|------|----------------|-------------------|
| **查询文本**（用户提问） | 短，几字到几十字 | 每次检索时 | ✅ 计入 |
| **文档文本**（知识库内容） | 可能很长 | **只在离线建索引时一次** | ❌ 不计入（查询时不会重算） |

第一轮 `bench.py` 曾得出 P95 = 3348ms 的吓人数字，那是把 49~4342 字的文本混在一起统计的结果，**既不代表查询延迟也不代表建索引吞吐，两头不着**。这个方法缺陷是本次测量中发现并修正的。

按正确口径（2026-08-04 重跑值 `[M-202]`）：

```
查询向量化（30字）P95 = 84.9ms，占 500ms 预算的 17.0%
余下 415.1ms 留给索引检索、结果组装与网络开销
```

**结论：500ms 指标在向量化这一环上不构成风险，83% 的预算可以留给检索和后续处理。**

（首测记录为 68.4ms、占 13.7%。两次测量的差异见 5.3 节说明；无论取哪一次，
结论都是"余量充裕"，不影响达标判断。）

### 6.2 建索引的一次性成本（离线，不影响指标但影响开发节奏）

按实测 936 字/秒换算全量 14,047 条记录：

| 方案 | 入库总字数 | 单线程预计耗时 |
|------|-----------|--------------|
| 全文入库（tool_input + tool_output 全量） | 9,743,750 | **约 2.9 小时** |
| 紧凑知识卡片（意图截 200 字 + 输出截 300 字） | 3,149,408 | **约 56 分钟** |

压缩比 3.1×。

### 6.3 端侧内存总占用（独立评审R-2，2026-08-05补测）

此前所有"轻量化"量化都只测了向量库本身（详见《知识检索/存储后端选型对比
报告.md》第四节），**embedding 这一侧的常驻内存占用一个数字都没有**——
之前报告口头提过"339MB 模型"，但从未实测过它到底占用在哪个进程上、真实
数字是多少。补测（`向量化常驻服务/measure_e2e_memory.py`）：

```
kytensor（系统级AI模型服务，root进程）  RSS ≈ 1,403.8 MB
kylin-ai-runtime（会话桥接守护进程）    RSS ≈    69.8 MB
emb_serverd（本项目自己的客户端进程）   RSS ≈     7.7 MB
```

**关键发现：向量化一次查询前后，kytensor 与 kylin-ai-runtime 的 RSS 增量
分别是 0KB 与 28KB——"339MB 模型"这个此前口头沿用的说法是不准确的。**
真实情况是：embedding 模型并不加载进本项目自己的进程，而是常驻在系统级
的 `kytensor` 模型服务里（该服务同时托管了 ASR 语音识别、CLIP 图文检索
等十余个与本项目完全无关的模型，是麒麟系统的公共基础设施，不是本项目
专属）；本项目的 `emb_serverd` 只是一个约 7.6MB 的轻量桥接客户端。

**如何解读"1.4GB"这个数字**：不应把它算作本项目的内存成本——这块内存
无论本项目用不用 embedding 功能都会常驻（只要系统开启了麒麟AI能力），
是操作系统级共享资源，其分摊逻辑类似"不应把整个数据库服务器的内存都记
在某一个查询业务头上"。**本项目真实、可归因的端侧内存增量是 7.7MB
（emb_serverd）+ 28KB（kylin-ai-runtime会话建立），合计约 7.76MB**，这
是本次补测得到的诚实结论，比此前含糊的"339MB"框架更准确，也更有利
（更轻量）——但准确性优先于对自己有利，如实记录测量过程与两种解读。

⚠️ **测量局限**：本次测量是在 `kytensor` 已稳定运行、目标模型已因本项目
此前多次调用而常驻的**稳态**下做的（增量为0正是这个稳态的体现）；未测量
系统首次冷启动、`kytensor` 从零加载该模型时的一次性内存/耗时代价——
那次性成本不可避免地更高，但只发生一次且发生在系统级服务启动阶段，不
随本项目的调用频率或数据规模变化，因此不计入本项目的"端侧占用"评估
范围，但如实声明这里没有测量它。

## 七、对下一步（知识检索模块）的设计影响

这是本次测量最实际的产出——它把 B2 的一个设计决策从「凭感觉」变成「有依据」：

1. **知识卡片要做紧凑，不要把 `tool_output` 全文塞进去**。向量化耗时与字数成正比，全文入库要多花 2 小时，而超长的执行输出（比如几千行的编译日志）对语义检索的贡献很低。建议保留完整原文在存储层供命中后回溯，但**只对紧凑卡片做向量化**。
2. **切块大小不影响总耗时**。总成本取决于入库总字数，不取决于切成几块（512 字块 547ms、256 字块 278ms，单位字数耗时基本一致）。所以切块大小应当纯粹按**检索效果**来选，不必为性能妥协。
3. **建索引应做成可中断续跑**。一次要跑 1~3 小时，中途断了不能从头再来。
4. 若后续嫌慢，可考虑多进程并发向量化——但 VM 只有 2 vCPU，加速上限有限，且 runtime 守护进程是否支持并发请求需另行验证。

## 八、已知限制

1. **单并发**：一个 `emb_serverd` 进程同一时刻只处理一条请求。当前够用（建索引是单线程批量作业），后续若要并发需验证 runtime 守护进程的并发能力。
2. **性能数据依赖本机环境**：2 vCPU / 3.9GB 内存的虚拟机。换到物理机或不同配置，绝对数值会变，但「耗时与长度成正比」「查询延迟远低于 500ms」这两个结论的性质不会变。
3. **未测量长期运行的内存稳定性**：常驻进程每轮都调用了 `embedding_result_destroy()` 释放结果，但尚未做长时间压力测试确认无泄漏。建索引跑几万条时应留意进程内存占用。
4. **未验证 `emb_serverd` 在 runtime 重启后的自愈能力**：若 `kylin-ai-runtime` 中途被重启，常驻进程的会话会失效，当前实现会持续返回 ERR 而不会自动重连。建索引脚本需自行处理这种情况（重启客户端）。
5. **长查询有真实的500ms越界风险，已加告警（独立评审R-6，2026-08-05修复）**：上表256字文本向量化 P95=538.3ms，已经超过端到端500ms预算——OS Agent场景下携带上下文的查询轻易超过这个长度，此前代码没有任何长度检查或提示。`embedding_client.py` 的 `encode()` 现在对超过 `MAX_SAFE_QUERY_CHARS`（200字，按936字/秒实测吞吐外推≈214ms，留有余量）的输入打印告警到stderr。**设计取舍：只告警、不静默截断**——`encode()` 同时服务离线建索引（截断会丢知识单元信息）与在线查询（长了才是真问题）两种场景，函数本身分不清调用方是哪一种，因此把决定权交还调用方：在线查询路径若收到告警，应自行截断或分段编码。

### 附：向麒麟机器传文件的踩坑记录

磐石不可变系统 `/usr` 重置后，恢复脚本只装回了 sshd 本体，**`scp` 与 sftp-server 都不存在**，`pscp` 无论用 SFTP 还是 SCP 协议都会失败：

```
FATAL ERROR: Received unexpected end-of-file from server
bash: scp: 未找到命令
```

可用的替代通路是 base64 过 SSH 管道：

```powershell
# Windows 侧（PowerShell + plink）
$b64 = [Convert]::ToBase64String([IO.File]::ReadAllBytes($src))
$lines = ($b64 -split '(.{76})' | Where-Object { $_ }) -join "`n"
[IO.File]::WriteAllText($tmpFile, $lines + "`n")
Get-Content $tmpFile | plink -ssh -batch -pw <密码> user@host "base64 -di > /目标/路径"
```

**注意必须用 `base64 -di` 而不是 `base64 -d`**：PowerShell 管道给原生命令的输出会带 UTF-8 BOM（`EF BB BF`），还会把换行变成 CRLF，`base64 -d` 遇到这些会报「无效的输入」并产出 0 字节文件；`-i` 参数让它忽略非法字符。传完务必用 `md5sum` 与本地比对确认。

**⚠️ 三点诚实说明：**

1. **测量记录本身不构成证明** —— 那些 JSON 我们能写，别人也能写。
   真正让数字站得住的是"你可以自己跑一遍"。
   可信度不来自「无法伪造」，而来自「容易被验证」。
2. **延迟类数字随硬件变化，不应期待跨机器一致** —— 实测同一段代码在麒麟虚机（2 vCPU）
   与开发机（24 核）上差约 2 倍。核对脚本对延迟只验证结论（是否达标、比值是否合理），
   不比对绝对毫秒数。每个数字产自什么环境，写在 `records/*.json` 的 `environment` 字段里。
3. **方法可复现 ≠ 数据可复现** —— 提取脚本任何人都能跑，但本项目这份数据集
   来自项目成员机器上的真实使用历史，**没有人能重新采集到同一份**。
   第三方验证方式是用随交付物提供的数据集重跑，而非重新采集。
