## 1. 何时发现

**D2（2026-08-27）**，排查 D2 冲突挖掘产出为 0 的原因时发现，
**在本次修订涉及的任何新数据（D2~D7 留出集）产生裁决之前**。

发现路径：D2 排期设计上不该出 0（B 组当天就有指向 D1 anchor 文件的回选），
逐层排查 `mine_doc_revisions()` 时定位到 `_find_origin()` 向前搜索时把
"同会话内的 `Read`"误当作内容起源，导致所有"先 Read 再 Edit"的修订被
系统性打成 `same_sitting` 负例。

## 2. 修的是什么

`_find_origin()`——属于**候选挖掘**阶段的函数，不是判定规则。

修复方式：两轮搜索，`Write`/`Edit` 优先作为起源；只有当某文件在目标编辑
之前从未被 `Write`/`Edit` 过时，才退回去看 `Read` 记录。这堵住了"同会话内
先 `Read` 一次旧内容、再 `Edit` 它"这个本项目提示词设计里的通用模式被误判
为"起源就在同会话内"的漏洞。

**`is_conflict()` 与 `adjudicate()` 这两个判定/裁决函数一行未改。**

## 3. 证据

§一的验收 ④：用修复版（当时为独立文件 `mine_conflicts_test.py`，验收
通过后修复已合入 `mine_conflicts.py`、临时文件删除，git 历史留档）重跑
冻结的 36 对，结果仍 **35/36**，与原版（未修复）跑同样 36 对的结果一致。

旁证：同一份 D1+D2+D3 纯净数据（按 session_id 过滤，排除历史调试会话噪声），
正式版 `positive_candidates_total=1`、修复版 `=58`——供给侧的"假 0"被实锤，
且这个巨大的差值排除了"还有第二个隐藏 bug 同时在起作用"的可能（若还有别的
bug，58 和 1 之间不会是纯粹由这一处修复解释的落差）。

## 4. 对指标的影响

**`is_conflict()` 判定准确率（M-302，闸门指标）：中性，35/36 → 35/36，
Wilson CI 下界 85.8% 不变**。这次修订不是为了让主指标好看才做——修完前后
分子分母都没变，这一点在动机上没有争议。

> ⚠️ 但如实披露一个**没有**保持中性的子指标：`adjudicate()` 三层准确率
> （M-303）里，因为评测集新增了 K-0052（真实纳入，非凑数），**类型判断
> （T1~T4）从 8/18=44.4% 降到 8/19=42.1%**，reason_kind 从 17/18=94.4% 降到
> 17/19=89.5%。K-0052 的金标类型是 T1，`adjudicate()` 自动判成了 T4——这是
> 随样本扩充新暴露的一条真实类型误判，不是这次代码改动造成的回归（判定/
> 裁决逻辑未改），如实记录，不因指标下降而回避、也不因它只是"新加的一条"
> 就在报告里悄悄略过。

## 5. 为什么冻结仍然有效

修订发生在留出集（D2~D7）产生任何裁决之前，且 `adjudicate()` /
`is_conflict()` 的判定逻辑一行未改——"规则先于留出集数据"这条论证看的是
**判定函数**是否动过，本次改动完全在判定函数之外，因此该论证不受影响。

`mine_conflicts.py` 整份文件的 sha256 确实变了（`bebd5ccd…` →
`7378b51d…`），这是本项目第二次承认"规则代码变了"（第一次是 v1.2.0 的
脱敏补漏，但那次连内容语义都没变，只换 token）——这次是真实的候选挖掘
逻辑修复。09-02 复核比对的锚点相应更新为新哈希，见《冲突规则冻结记录.md》
§〇 与 §一 的说明。

## 6. 分界线口径：行号 → 数据日期

**变更**：开发集 / 留出集的分界线，由

```
旧：conflicts.jsonl 第 150 行起的候选 = 留出集   （冻结记录 §三 原文）
```

改为

```
新：候选 new.asserted_at <  2026-08-26  = 开发集（历史数据，规则在其上开发）
    候选 new.asserted_at >= 2026-08-26  = 留出集（D1~D7 采集窗口，规则未见过）
```

`2026-08-26` 是 D1 每日数据采集的起始日。

**为什么必须改**：行号定义**不耐重挖**。这次 `_find_origin()` 修复后要
重跑 `mine_conflicts.py`（母方案 §三 c），候选的相对顺序会变、
`candidate_id` 会重排——"第 150 行"在重挖之后不再指向冻结时的那条记录，
"第 150 行起 = 留出集"这个定义当场失效。09-02 跑完 D2~D7 挖掘器后行号
会再变一次。**数据日期不随挖掘器版本变化**：一条 memory/*.md 修订的
`asserted_at` 是它被写下的真实时刻，重挖多少次都一样，用它切分开发/留出
集，重挖、追加新数据都不影响已划定的边界。

**影响面**：
- 《冲突规则冻结记录.md》§三 已改写为按日期定义（并保留 149 / 36 作
  规模快照）；§〇 里"第 150 行起"的表述同步改为按日期。
- `可复现性体系/measure_conflicts.py` 的 `M-305` 新增 4 个指标：
  `dev_holdout_boundary_date`（`2026-08-26`）、`dev_candidate_count`、
  `holdout_candidate_count`、`undated_s4_signal_count`。冻结时实测：
  **开发集 149 / 留出集 0 / 无日期 0**（D2 挖掘器尚未跑，全部候选都在
  分界日期之前）。
- `可复现性体系/claims.json` 的 **C-312** 从 `conflicts_pool_lines`
  （行号快照）改指向 `dev_holdout_boundary_date`（分界日期字符串），
  `check: exact`。`conflicts_pool_lines=149` 仍由 M-305 登记，但只作
  规模快照、不再是任何主张的分界依据。
- `可复现性体系/metric_coverage.py` 的 `EXPECTED_TOTAL` 523 → 527
  （M-305 新增 4 个指标），`EXPECTED_COVERED` 不变（106）。

**这条不影响"规则先于数据"的论证**：分界线换算方式变了，但"规则代码
（`is_conflict()`/`adjudicate()`）在 D2~D7 数据进入之前就已定死哈希"这个
事实没变——反而更稳，因为新判据不依赖任何一次挖掘的行号快照。

### 重挖（§三 c）对 old 侧起源元数据的连带影响（不是 ground truth 改动）

`_find_origin()` 修复后重跑 `mine_conflicts.py`，凡"起源原本落在同会话
Read 快照、修复后追溯到更早 Write/Edit"的 doc_revision 候选，其 `old` 侧
`session_id`/`asserted_at` 都会相应变早。除 K-0052（上表，label 也变）外，
另有 **5 条已确认正例的 `old` 侧起源时间戳变早、但 label/type/reason_kind/
verdict 全部不变**：

| conflict_id | old.asserted_at：v1.2.0 → v1.3.0 | label |
|---|---|---|
| K-0021 | 2026-07-26 → 2026-07-17 | conflict（不变） |
| K-0026 | 2026-07-26 → 2026-07-18 | conflict（不变） |
| K-0048 | 2026-07-07 → 2026-07-06 | conflict（不变） |
| K-0088 | 2026-07-31 → 2026-07-17 | conflict（不变） |
| K-0137 | 2026-07-30 → 2026-07-29 | conflict（不变） |

- **对测量的影响：零**。`adjudicate()` 的 verdict 只看"谁更晚"，这 5 条
  new 侧仍晚于 old 侧，verdict 不变；type/reason_kind 由胜出方正文措辞
  决定、与时间戳无关。M-302（35/36）、M-303（verdict 19/19、type 8/19、
  reason 17/19）逐位不变。
- **方向是保守的**：修复让 old 知识的起源判得**更早**（不是更晚），
  即"旧知识存在得更久"，不会把任何一对判得比实际更像冲突。
- ADJUDICATIONS 里这 5 条手写的 `scope_of_old` 提到的是概略时点
  （"作为该文件在 07-26 时点的摘要仍准确"这类），修复后真实起源比它
  写的早约一周。这是**描述性批注、不是被测量的字段**，方向也保守
  （旧知识适用窗口只会更长），本次不逐条改写这些 prose（改了反而超出
  "只动 E-032"的范围）；如实记录于此。

### eval_id 重排（display artifact，不是数据被动过）

`review_and_freeze_conflicts.py` 给 eval 行按**最终文件里的行位置**顺排
`E-{i+1:03d}`（`ADJUDICATIONS` 块在前、负例块在后）。K-0052 从负例块
移进 `ADJUDICATIONS` 块后，它自己变成 `E-019`，其后所有行的 eval_id
顺移一位（如 v1.2.0 的 `E-028→K-0135` 在 v1.3.0 变 `E-029→K-0135`）。
**稳定标识始终是 `conflict_id`（K-xxxx，来自 `stable_key`）**；母方案的
盲测协议本身就规定"不显示 eval_id"，正是因为它是位置产物。按 conflict_id
逐条比对，v1.2.0 与 v1.3.0 之间 label 只有 K-0052 一处变化（见上）。
